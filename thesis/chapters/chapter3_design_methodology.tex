\chapter{System Design and Methodology}
\label{ch:design}

This chapter presents the system design of CodeGraph as a structural retrieval architecture for AI coding agents. It explains how source code is represented as a graph, how natural language tasks are translated into retrieval signals, and how these signals are propagated and ranked to produce relevant context. By combining lexical cues with structural relationships in a unified pipeline, CodeGraph is designed to retrieve context that is both relevant to the task and meaningful within the structure of the codebase. The chapter therefore focuses on the design decisions that shape this pipeline and on their role in making the system practical and effective for AI-assisted software engineering.

The pipeline comprises five stages: source code parsing, graph construction, seed selection, PPR-based ranking, and context delivery. The central design assumption is that lexical and structural evidence play complementary roles in retrieval. The task description provides the initial relevance signal through identifiers and keyword matches, while Personalized PageRank propagates that signal over the dependency graph to identify structurally supported regions of the codebase. As a result, regions reinforced by multiple structural connections gain prominence, whereas weakly connected or isolated matches lose influence in the final ranking.

This decomposition also supports practical retrieval performance. Parsing and graph construction are carried out before query execution, while per-query retrieval operates over an already constructed graph and is dominated primarily by the ranking computation. \Cref{tab:stage-complexity} summarizes the computational complexity associated with each stage.

The pipeline is further designed to behave conservatively when information is incomplete. Files with syntax errors yield no extracted entities, unresolved imports and ambiguous calls are omitted rather than inferred, and failure to construct a personalization vector results in an explicit empty output. This design favors precision and interpretability over speculative retrieval. The following sections examine each stage in detail, beginning with source code parsing and entity extraction.

\section{Source Code Parsing}
\label{sec:parsing}

Graph-based retrieval requires an explicit structural representation of the repository. A source file, in its raw textual form, does not yet expose the code units and relationships needed for graph construction. This section therefore explains how CodeGraph parses Python source files into a typed entity model that serves as the basis for the graph representation used in later stages.

A central design question is the level of granularity at which entities should be extracted. If the representation is too coarse, important code elements are grouped together and retrieval cannot distinguish between them. If it is too detailed, the graph becomes larger and noisier, which makes retrieval less efficient and less focused.

CodeGraph adopts a four-entity model consisting of files, classes, functions, and methods. This choice provides a practical middle ground: it captures the units through which Python code is typically organized and referenced, while preserving a graph size that remains suitable for efficient retrieval.

\subsection{Parsing with Tree-sitter}
\label{sec:parsing-treesitter}

The parsing stage uses Tree-sitter to convert each Python file into a set of typed code entities. In CodeGraph, these entities are files, classes, functions, and methods. Each one receives a qualified name, which acts as a repository-wide identifier and distinguishes entities that may share the same local name but appear in different files or scopes.

This naming scheme is important because later stages rely on it to create graph nodes consistently and to resolve references across the repository. \Cref{tab:entity-types} presents the four entity types together with their key properties and naming format.

\subsection{Import Resolution}
\label{sec:import-resolution}

Import statements express cross-file dependencies, but parsing alone yields only the raw import string rather than its target within the repository. Import resolution addresses this by mapping each resolvable import to a file on disk and converting it into an \texttt{IMPORTS} edge between the importing file and the imported module.

The resolver supports both absolute and relative imports by matching module paths against the repository structure. Standard-library and third-party imports are recognized separately and left out of the graph, since they do not correspond to source files inside the repository. When no reliable match can be found, the import is omitted rather than inferred, which keeps the dependency graph more precise and avoids introducing misleading edges.

\subsection{Call Resolution}
\label{sec:call-resolution}

Call resolution converts function call expressions into \texttt{CALLS} edges by determining which definition each call site refers to. This step is more difficult than import resolution because Python is dynamically typed: in many cases, the target of a call cannot be identified from syntax alone.

To address this, CodeGraph applies a three-level resolution strategy in descending order of confidence. A call is linked first to an imported definition when the callee name matches a successfully resolved import; if no such match exists, the resolver checks for a definition in the same file; failing that, it links the call only when there is a unique matching definition across the repository.

Calls that remain ambiguous or unresolved are omitted rather than guessed. This design favors graph precision over graph completeness, because a false \texttt{CALLS} edge can redirect PPR into an unrelated region of the graph, whereas a missing edge only limits the propagation path that would otherwise be available.

\subsection{Parser Limitations and Edge Cases}
\label{sec:parser-limitations}

The main limitations of the parsing stage come from the boundaries of static analysis, not from basic syntax handling. Circular imports are handled by separating parsing from dependency resolution: each file is indexed independently, import statements are recorded first, and \texttt{IMPORTS} edges are created only after the full set of files is known, which allows cyclic dependencies to be represented without recursive import chasing.

Dynamic imports are more difficult. When module names are constructed at runtime, for example through \texttt{importlib.import\_module()} or \texttt{\_\_import\_\_()}, the target cannot be determined reliably by static analysis, so these dependencies are omitted from the graph. This follows the same precision-first rule used elsewhere in the system: a false edge can misdirect propagation, while a missing edge mainly reduces how far relevance can spread.

Scalability is also manageable at the parsing level. Tree-sitter parses large files in linear time, so parsing itself remains efficient, while the more significant cost in larger repositories comes from graph construction, especially database writes, rather than from entity extraction. Very large files were not common in the evaluation set, so this issue did not materially affect the reported experiments.

\section{Graph Construction}
\label{sec:graph-construction}

With entities extracted and references resolved, the next stage constructs the repository representation used for retrieval. CodeGraph stores this representation as a weighted property graph in Neo4j, where nodes correspond to parsed code entities and edges encode structural relationships between them. This graph is the central data structure of the system: it preserves repository structure in a form that supports Personalized PageRank and allows relevance to propagate beyond direct lexical matches. At this stage, two design choices are especially important, the graph schema and the edge-weighting strategy, because they determine what structural information is represented and how strongly it influences retrieval.

\subsection{Node and Edge Schema}
\label{sec:graph-schema}

The graph schema mirrors the four-entity representation introduced in \cref{sec:parsing}. Nodes are created for files, classes, functions, and methods, and each node stores a qualified name together with core metadata such as name, file path, and, where available, signature, line number, and docstring. Structural relationships between these entities are represented through four edge types: \texttt{CONTAINS}, \texttt{CALLS}, \texttt{IMPORTS}, and \texttt{INHERITS\_FROM}. Together, these node and edge types capture the main structural patterns of a Python codebase, namely containment, invocation, module dependency, and class inheritance, while keeping the graph compact enough to remain interpretable and useful for retrieval. All edges are created with a uniform base weight of~1.0 before query-time IDF reweighting (\cref{sec:idf-reweighting}).

The node vocabulary matches \cref{tab:entity-types}; endpoint patterns and semantic meanings for each edge type are illustrated in \cref{fig:graph-schema}.

\subsection{IDF-Based Edge Reweighting}
\label{sec:idf-reweighting}

Uniform base weights assume that every structural connection contributes equally to retrieval, but this is not true in practice. Some targets are highly specific to the task, while others are generic utility nodes reused across large parts of the repository. If both receive the same edge weight, Personalized PageRank sends too much probability into broadly shared utility neighborhoods, which weakens the ranking of domain-specific code.

\Cref{fig:idf-reweighting} illustrates this intuition. Under uniform weighting, probability splits evenly between a task-relevant target and a utility hub. Under IDF reweighting, the edge toward the highly connected utility node is attenuated, so more relevance mass remains near the structurally specific part of the graph.

To account for this effect, CodeGraph assigns each edge a weight based on the in-degree of its target node:
\begin{equation}
    w(e) = \frac{1}{\log_2\!\bigl(\operatorname{in\_degree}(v) + 2\bigr)}
    \label{eq:idf-weight}
\end{equation}
Nodes with many incoming edges receive lower weights, while rare or specialized targets retain stronger weights. The logarithmic form reduces hub influence gradually rather than aggressively, and the $+2$ offset keeps the function finite for low-degree nodes. Empirical comparison against gentler and stronger alternatives supported the $\log_2$ formulation as the best balance for preserving informative shared functions while still demoting ubiquitous utilities.\footnote{Replacing the denominator with $\log_{10}(\mathrm{in\_degree}+1)$ dropped Recall@10 by 2.3\,pp; the inverse-linear form $1/(\mathrm{in\_degree}+1)$ dropped it by 8.1\,pp.}

\subsection{GDS Projection}
\label{sec:gds-projection}

Personalized PageRank is not executed directly on Neo4j's disk-backed storage graph. Instead, CodeGraph uses the Neo4j Graph Data Science library, which first projects the repository graph into an in-memory representation optimized for graph traversal.

The projection includes all four node types and all four edge types defined in the previous subsections. The IDF-derived edge weight is carried into the projected graph as the relationship weight used during ranking.

Edges are projected as undirected. This choice allows relevance to flow both downstream, toward the entities a function depends on, and upstream, toward the entities that depend on it. For repository-level assistance, this is important because an AI agent often needs context in both directions, not only the callees of a function but also its callers, dependents, or enclosing usage paths.

The projection is dropped and recreated for each retrieval call so that ranking always reflects the current edge weights produced by query-time IDF reweighting. Although this adds a small setup step, the cost remains modest: for a graph with 50,000 nodes and 200,000 edges, projection requires about 50\,ms and roughly 5\,MB of memory, which is minor relative to total query latency.

\section{Seed Selection}
\label{sec:seed-selection}

Personalized PageRank can only rank the repository meaningfully once it has a set of starting points in the graph. Seed selection provides these starting points by translating the natural-language task description into a personalization vector, that is, a probability distribution over graph nodes that determines where restart mass is placed during the random walk. This stage does not need to identify every relevant node perfectly, because PPR can amplify structurally consistent evidence, but it does need to place some probability inside the correct region of the graph. When no seed reaches that region, retrieval quality is capped regardless of how well the graph propagation itself is tuned.

CodeGraph constructs this personalization vector from three complementary signals: direct identifier matches, BM25 keyword retrieval, and file or path hints mentioned in the issue text. Their default weights, 0.6 for entity match, 0.3 for BM25, and 0.2 for issue path hints, reflect the relative reliability of each source. \subsection{Entity Match Signal}
\label{sec:entity-match}

Task descriptions often mention code entities directly, including class names, function names, module references, and other repository-specific identifiers. The entity match signal extracts these mentions from the task text using regex patterns designed for common Python naming conventions, including CamelCase identifiers, backtick-quoted names, dotted paths, and snake\_case forms. This makes the signal especially valuable in bug reports and issue descriptions that already refer to the code in the vocabulary of the repository itself.

Each extracted identifier is then looked up against graph nodes. When a name is highly ambiguous, its contribution is down-weighted by inverse-frequency scaling, specifically $1 / \log_2(n + 1)$, where $n$ is the number of graph matches for that name. As a result, a broad identifier such as \texttt{update} contributes much less total mass than a specific identifier that resolves to a single node. Because explicit identifier mentions are the strongest direct evidence of relevance, this signal receives the highest default weight, 0.6.


\subsection{BM25 Signal}
\label{sec:bm25-signal}

Not every task description contains an exact identifier, so the system also uses lexical retrieval to recover likely entry points from partial or approximate wording. For this signal, each graph entity is indexed as a small text document built from its short name, its qualified name, path tokens, and the first 200 characters of its docstring. This gives BM25 access not only to surface names, but also to limited contextual vocabulary associated with the entity.

A key preprocessing step is compound tokenization. Identifier names are split at CamelCase boundaries and underscores before indexing, so forms such as \texttt{SQLCompiler} become searchable through partial terms like \texttt{sql} and \texttt{compiler}. Without this step, lexical retrieval would miss many natural-language queries that describe an entity indirectly rather than by its exact spelling. At query time, the BM25 component returns the top 10 results, and these are added to the personalization vector with a default signal weight of 0.3.


\subsection{Issue Path Hint Signal}
\label{sec:issue-hint-signal}

Issue reports sometimes include concrete location cues, such as a filename, module path, or directory fragment. The issue path hint signal extracts these references from the task description and maps them to file nodes or to entities located under the corresponding path. Examples such as \texttt{django/db/models} or \texttt{compiler.py} do not always identify the exact target entity, but they can still place probability mass into the correct subsystem.

This signal is intentionally weaker than direct entity matching because path references are often broad. A directory mention may correctly identify the relevant area of the codebase without isolating the exact file or function that needs attention, so its default weight is set to 0.2.


\subsection{Personalization Vector Construction}
\label{sec:pvec-construction}

The final personalization vector is built by merging the three signals at the node level. If a node is retrieved by more than one signal, for example by both direct entity matching and BM25, its contributions are summed. The merged vector is then normalized so that $\|\vec{s}\|_1 = 1$, producing a valid probability distribution that can be passed directly to the GDS implementation of Personalized PageRank as the restart distribution.

A representative example is the task description, ``Fix the authentication failure in \texttt{auth/tokens.py} when \texttt{AuthError} is raised''. In this case, entity extraction identifies \texttt{AuthError}, BM25 contributes nearby authentication-related entities, and the path hint adds entities under \texttt{auth/tokens.py}. After summation and normalization, the resulting vector concentrates restart probability on the authentication subsystem, allowing PPR to propagate relevance outward through the local dependency structure.

The opposite case is also important. When a task description contains no recognizable identifier and only vague language, such as ``The application crashes on startup'', entity extraction contributes nothing and BM25 can only match shallow generic vocabulary. After normalization, the personalization vector is then dominated by weak lexical evidence, which helps explain why description-poor tasks contribute disproportionately to zero-recall failures. This is not a weakness of PPR itself, but a consequence of insufficient identifying information in the seed stage.

With the personalization vector constructed, the pipeline hands it to Personalized PageRank to propagate relevance through the graph structure.

% 3.5 Personalized PageRank Configuration
% =============================================================================
\section{Personalized PageRank Configuration}
\label{sec:ppr-config}

With seeds selected, the pipeline invokes Personalized PageRank to propagate relevance through the graph. As established in Chapter~2, PPR assigns each node a relevance score reflecting both its structural centrality and its proximity to the seed nodes, controlled by the damping factor $d$ that governs how far the random walk ventures from the seeds before restarting.

CodeGraph's PPR configuration exposes three parameters with meaningful consequences for retrieval quality: the restart mode (how probability is distributed across seeds), the damping factor (how far the walk ventures from seeds), and the top-$k$ cutoff (how many results to return). Each parameter was set through controlled benchmark evaluation rather than theoretical defaults. This section presents the rationale behind each choice and the evidence supporting it.

\subsection{Uniform vs.\ Weighted Restart Mode}
\label{sec:uniform-vs-weighted}

When PPR restarts from multiple seed nodes, a natural question arises: should seeds with higher confidence, say, an exact entity name match, receive more restart probability than seeds derived from weaker evidence like a partial BM25 match? CodeGraph implements two strategies that answer this differently.

\paragraph{Weighted restart mode.} Each seed receives restart probability proportional to its weight in the personalization vector $\vec{s}$. Seeds with higher BM25 scores or stronger entity matches receive more restart probability. This mode computes:
\begin{equation}
    \text{PPR}_{\text{weighted}} = \sum_i w_i \cdot \text{PPR}(\text{seed}_i)
    \label{eq:weighted-ppr}
\end{equation}
where $w_i$ is seed $i$'s normalized weight. The combination is mathematically exact because PPR is linear in the restart distribution.

\paragraph{Uniform restart mode (default).} All seeds receive equal restart probability regardless of their weights. This mode executes a single GDS \texttt{pageRank.stream()} call with all seed node IDs passed as \texttt{sourceNodes}, one graph traversal, not $|\text{seeds}|$.

\textbf{Why does uniform mode win?} The explanation centers on overconfident seed weights. When entity extraction picks up an ambiguous name, for example, \texttt{fit} matching 30~scikit-learn estimators, the entity match signal (weight~0.6) spreads restart probability across many incorrect nodes. BM25 seeds (weight~0.3) cannot compensate because their contribution is diluted in the weighted sum. Uniform mode avoids this failure by giving every seed, including the BM25 seeds that often locate the correct file neighborhood, equal restart probability. From that point, the graph structure itself arbitrates: the coherent seeds, which share structural paths through shared dependencies, receive compounding PPR mass at their intersection. The isolated incorrect seeds, which lack structural support, dissipate probability locally and are overtaken.

This finding reflects a general principle in seed-based graph retrieval: when seed quality is imperfect, seed diversity matters more than seed confidence. Trusting the graph to identify structural consistency is more robust than trusting the seed weighting to identify correctness.

\subsection{Damping Factor}
\label{sec:damping-factor}

The damping factor $d$ controls how far the random walk ventures from seed nodes before restarting. This parameter directly affects retrieval precision: higher values explore more distant nodes and reach a larger fraction of the graph; lower values concentrate probability near the seeds. CodeGraph uses $d = 0.70$ (restart probability $1 - d = 0.30$), compared to the standard default of $d = 0.85$.

A lower damping factor keeps the random walk closer to the seed nodes on each step. With improved seed quality (after the BM25 and entity extraction improvements from \cref{sec:seed-selection}), staying closer to the seeds improves early-rank quality: Recall@5 increased by +3\,pp (from 60.7\% to 63.7\%), while Recall@10 remained unchanged at 72.3\%. The lower damping factor also has a beneficial side effect on convergence speed: with $d = 0.70$, the random walk restarts more frequently, reducing the expected walk length and therefore the number of matrix-vector multiply iterations required to reach the $10^{-6}$ tolerance threshold. Empirically, PPR with $d = 0.70$ converges in approximately 6--10 iterations on the benchmark graphs.

The Recall@10 ceiling is unaffected because it is determined by which files receive \emph{any} nonzero PPR probability, a property governed by graph connectivity, not by the damping factor. The damping factor affects only the \emph{ranking} within the reachable set. In graph-theoretic terms, the expected random walk length under damping factor $d$ is $1/(1-d)$ hops: at $d = 0.70$ this is $\approx 3.3$ hops; at $d = 0.85$ it is $\approx 6.7$ hops. The longer walk at $d = 0.85$ reaches marginally more nodes, but the difference in reachable set cardinality is small relative to repository size, which explains why Recall@10 (a reachability metric at this scale) is insensitive to the change while Recall@5 (a ranking-sensitive metric) is not.

\subsection{Top-\textit{k} Configuration}
\label{sec:topk}

PPR produces a score for every node in the graph, but agents need a finite result set. The parameter $k$ controls how many top-ranked nodes to return. The default choice $k = 30$ balances coverage of relevant entities with practical context window limits: increasing $k$ from 20 to 30 resolved 5~additional benchmark instances whose gold files were ranked at positions~21--30, yielding a direct +1.7\,pp improvement in Recall@10. The marginal cost is negligible: the token budget mechanism in post-processing (\cref{sec:post-processing}) independently limits how much source code is served to the agent, so additional ranked results impose no latency penalty.

With PPR configuration established, the ranked list of entities moves into the post-processing stage, where graph-level scores are translated into agent-ready source code.

\section{Post-Processing and Context Delivery}
\label{sec:post-processing}

With the ranking stage complete, the retrieval pipeline still has one practical step left: transforming graph-level relevance scores into usable source-code context. Personalized PageRank returns a ranked list of entities, but an AI agent cannot act on node identifiers alone. It needs code snippets, precise locations, and a response format that can be consumed directly by a tool call. Post-processing performs this translation by deduplicating overlapping results, extracting source code at the appropriate granularity, enforcing a token budget, and packaging the final output in a structured form.

\subsection{File-Level Deduplication}
\label{sec:file-dedup}

The ranked list produced by PPR may contain several entities from the same file. If those are passed through naively, the returned context becomes repetitive and wastes the available budget. CodeGraph therefore removes the whole-file representation when at least two sub-entities from the same file already appear in the ranked results. This preserves the fine-grained ranking signal from functions, methods, and classes, while avoiding redundant file-level duplication that would otherwise consume tokens without adding new information.

\subsection{Source Code Extraction}
\label{sec:source-extraction}

After deduplication, each retained entity is converted into concrete source text by reading the file from disk using its stored path and line boundaries. This design choice is important because the unit of retrieval is not the repository file as a whole, but the specific code region that the ranking stage judged relevant. By extracting only the lines associated with the entity, the system returns focused evidence instead of burdening the agent with unrelated surrounding code.

\subsection{Token Budget Enforcement}
\label{sec:token-budget}

The candidate set returned by PPR and the final amount of code delivered to the agent are intentionally controlled by different mechanisms. The ranking stage may keep a broader top-30 candidate pool to preserve recall, while post-processing adds results in rank order only until the configured token budget is exhausted. For MCP calls, the default budget is 6{,}000 tokens when \texttt{token\_budget = 0}, and callers may override it when needed. This separation is methodologically important: it allows retrieval to remain recall-oriented while still respecting the downstream model's context-window constraints. Even in edge cases where the first result alone exceeds the limit, the system still returns that result so the agent always receives at least some context.

\subsection{Structured Response Formatting}
\label{sec:structured-response}

The final output is not just raw code, but a structured result in which each item includes the entity name, entity type, qualified name, file path, line range, relevance score, source code text, and token count. This response format turns retrieval output into something an agent can inspect, attribute, and act on programmatically. In other words, post-processing does not merely trim the ranked list, it converts retrieval output into an interface artifact suitable for tool-based agent workflows.

Taken together, these steps ensure that retrieval quality is not lost after ranking. Personalized PageRank identifies which parts of the repository are likely to matter, while post-processing decides how that evidence is exposed to the agent under realistic context constraints.

\label{sec:mcp-integration}

This section describes how CodeGraph exposes the retrieval pipeline to agents through the Model Context Protocol (MCP), an open standard that defines a message-passing interface for invoking external capabilities via structured tool calls and receiving structured results.

CodeGraph implements an MCP server that wraps the entire retrieval pipeline as a set of callable tools. The server is stateless per request, no session state is maintained between calls, while the Neo4j graph persists across invocations, eliminating the need to rebuild the graph for each query.

% 3.8 Design Limitations

\section{Design Limitations}
\label{sec:design-limitations}

Every design decision in CodeGraph trades coverage for tractability, precision, or implementation simplicity. In this chapter, the main limits come from static-only analysis, Python-only parsing, conservative edge resolution, and residual structural noise, not from accidental omissions. This section makes those trade-offs explicit so the evaluation results are interpreted within the system's real operating envelope.

\paragraph{Static-only analysis.}
CodeGraph builds its repository graph from static source-code analysis. The graph still captures structural relations such as \texttt{CONTAINS}, \texttt{IMPORTS}, \texttt{CALLS}, and \texttt{INHERITS\_FROM} when they can be resolved statically, so the limitation is not the absence of structure, but the absence of runtime-only links. Behaviors such as monkey-patching, \texttt{eval()}, and dynamic module loading through \texttt{importlib} do not appear in the graph, which means repositories that rely heavily on dynamic execution patterns will be only partially represented.

This is less damaging in the current evaluation setting because SWE-bench Lite uses well-structured Python repositories, but it would matter more in codebases where important dependencies are created at runtime rather than expressed in static program structure.

\paragraph{Python-only parsing.}
The current parser implementation supports only Python. The broader architecture is not inherently Python-bound, because the graph schema, the Personalized PageRank ranking stage, and the MCP interface are language-agnostic in design, but extending the system to another language would still require a new parser together with language-specific import and call-resolution logic. As a result, the present system does not transfer directly to polyglot repositories or to projects written primarily in other languages.

This limitation does not affect the reported benchmark because the evaluation uses SWE-bench Lite, a curated set of 300 issues drawn from Python projects. It does, however, limit how broadly the current implementation can be deployed without additional engineering work.

\paragraph{Incomplete call and import resolution.}
Edge resolution is intentionally conservative. When a callee is ambiguous, the system creates no \texttt{CALLS} edge rather than risking a false one, and import links that cannot be matched reliably to project files also produce no edge. This policy protects graph precision, because incorrect edges would create misleading propagation paths for Personalized PageRank, but it also reduces structural coverage.

In practice, this means that many duck-typed method calls, ambiguous global name matches, and unresolved cross-file references remain absent from the graph by design. Personalized PageRank can still propagate through the structure that does exist, but missing edges reduce the system's ability to reach some relevant files through call chains alone.

\paragraph{Residual utility-function and hub-node noise.}
IDF-based edge reweighting (\cref{sec:idf-reweighting}) reduces the influence of highly connected utility functions and hub-like nodes, but it does not eliminate that effect completely. Some generic helpers can still attract PageRank mass and displace more task-specific results, especially when the initial seeds are already close to those shared utilities. This remains a secondary failure mode even after the weighting correction.

That limitation is best understood as controlled rather than solved. The system applies IDF weighting before retrieval, which dampens structurally common targets, but the graph still contains those targets and their neighborhoods, so some residual noise remains unavoidable in a purely structural ranking pipeline.

Taken together, these limitations define the intended operating envelope of the current system. CodeGraph is best suited to well-structured Python repositories whose important relationships are visible in static structure. That framing is also consistent with the evaluation setup, which uses fixed repository snapshots from SWE-bench Lite rather than live, continuously changing workspaces.

Within that scope, the design remains effective and practical. Outside it, especially in highly dynamic or polyglot repositories, the same decisions that make the system simple and dependable also become stronger constraints on retrieval quality.

\section{Chapter Summary}
\label{sec:design-summary}

This chapter presented the design of the CodeGraph retrieval pipeline. The system transforms a Python repository into a weighted property graph via Tree-sitter parsing and two-pass graph construction, translates a natural language task description into a personalization vector via multi-signal seed selection, ranks all graph nodes by structural relevance via Personalized PageRank, and delivers the top-$k$ results to an AI agent through an MCP server interface.

Three organizing principles guided the design decisions described in this chapter. \emph{Parsimony} keeps the graph limited to static analysis, accepting known blind spots such as dynamic imports and duck-typed calls in exchange for simpler construction. \emph{Composability} gives each stage a clear input and output type, so parser, graph, seed, and ranking changes can be tested independently. \emph{Empiricism} ties parameter choices, including damping factor, top-$k$, signal weights, and token budget, to measured benchmark behavior rather than theoretical defaults.

Three decisions are especially important for retrieval quality. First, \emph{uniform PPR restart} outperforms weighted restart because it prevents overconfident seed weights from dominating the computation. Second, \emph{IDF-based edge reweighting} reduces the influence of ubiquitous call targets that would otherwise dilute PPR scores across the graph. Third, \emph{compound tokenization} in BM25 seed selection addresses vocabulary fragmentation in code identifiers. \Cref{ch:evaluation} quantifies the individual and combined impact of these choices through controlled ablations.

\Cref{ch:implementation} transitions from design to implementation, presenting the technology stack, code organization, data models, and evaluation harness that transform these architectural principles into a functioning system.
