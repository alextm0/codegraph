\chapter{Background and Related Work}
\label{ch:background}

This chapter builds the conceptual vocabulary needed to understand CodeGraph. We first establish the three core technologies that underpin structural code retrieval: static parsing, property-graph databases, and Personalized PageRank. We then survey the retrieval problem and its three methodological families: sparse, dense, and graph-based. Finally, we examine five concrete graph-based systems in detail and identify the research gaps that motivate this thesis.

% ============================================================
\section{Background}
\label{sec:background}
% ============================================================

This section teaches the reader three enabling technologies in the order they appear in the CodeGraph pipeline: Tree-sitter converts raw source files into structured syntax trees; Neo4j stores and queries the resulting dependency graph; and Personalized PageRank propagates relevance from query-matched seeds to structurally connected code entities.

\subsection{Tree-sitter and Static Analysis}
\label{sec:treesitter-bg}

Source code structure can be extracted through static analysis, which examines source text without program execution. The goal of this stage is to produce a structured representation of each source file that captures code units and their relationships, without requiring the code to be executed.

CodeGraph uses Tree-sitter~\cite{treesitter} as its parsing engine. Unlike traditional compiler-based parsers, Tree-sitter is designed around three properties that make it suitable for developer tooling:
\begin{itemize}
    \item \textbf{General:} It supports a wide range of programming languages through a unified grammar system.
    \item \textbf{Robust:} It can parse syntactically incomplete or erroneous code, which is common in active development environments.
    \item \textbf{Fast:} It builds an initial concrete syntax tree in sub-millisecond time and can incrementally update the tree as the file is modified.
\end{itemize}

\noindent Tree-sitter therefore serves as the foundational engine of a structural indexer, converting raw source files into high-fidelity syntax trees from which code entities and dependencies are extracted. \Cref{fig:ast-to-graph} illustrates the conceptual transformation from raw source text through a syntax tree to the typed dependency graph used in later stages.

\subsection{Graph Databases and Neo4j}
\label{sec:neo4j-bg}

The interconnected nature of source code, where files import modules, classes inherit from others, and functions call each other, is naturally modelled as a directed, typed graph. Representing this structure in a relational database requires complex multi-hop joins that degrade with query depth.

CodeGraph uses Neo4j, a property graph database, to store the repository graph. In Neo4j, entities are represented as nodes and relationships as edges, both of which carry key-value properties. This representation enables efficient execution of graph algorithms such as Personalized PageRank, which must traverse the full topology of the repository during every retrieval query.

\subsection{PageRank and Personalized PageRank}
\label{sec:pagerank-bg}

PageRank~\cite{page1999pagerank} is a link-analysis algorithm that ranks nodes in a graph by structural importance. The algorithm models a random walker who traverses the graph by following outgoing edges and, with a fixed restart probability, teleports to a random node. A node's importance is determined by the number and quality of edges pointing to it, since nodes that many high-importance nodes link to accumulate more probability mass from the random walk.

Personalized PageRank (PPR) modifies this walk by replacing the uniform restart distribution with a query-specific one. Rather than teleporting uniformly, the walker restarts from a small set of seed nodes drawn from the query context. This change transforms PageRank from a global ranking into a local relevance score: nodes near the seeds in the dependency graph receive high PPR mass, while structurally distant nodes receive little. For repository retrieval, this means that PPR propagates relevance from lexically matched seeds to the files and functions they depend on or are depended upon by, which is precisely the signal that sparse and dense methods cannot provide.

\section{Code Retrieval for LLM Agents}
\label{sec:related-work}
% ============================================================

This section establishes the retrieval problem that this thesis addresses and surveys three methodological families: sparse, dense, and graph-based retrieval. Each family represents a distinct model of what makes code relevant to a query, and each has a distinct failure mode that motivates the next.

\subsection{The Retrieval Problem}
\label{sec:retrieval-problem}

LLM-based coding agents face a fundamental selection problem: given a natural language task description and a large code repository, which source files should the agent examine? The context window constrains how much code an agent can reason over in a single query. For current production models, this limit ranges from 32{,}000 to 200{,}000 tokens~\cite{gpt4,claude3}, while a moderately sized Python repository such as Django contains several million tokens of source code.

This selection problem has an asymmetric cost structure. A false negative (failing to retrieve a file that the agent must modify) renders the task unsolvable regardless of the agent's reasoning quality. A false positive (retrieving an irrelevant file) incurs only a noise cost: it consumes context budget but does not prevent a correct solution. This asymmetry makes retrieval recall-oriented: the primary measure of quality is whether the relevant files appear within the top-$k$ results, rather than the precision of the full retrieved set.

\subsection{Retrieval-Augmented Generation for Code}
\label{sec:rag}

Retrieval-augmented generation (RAG)~\cite{lewis2020rag} addresses the context window limitation by treating the repository as an external knowledge base. A typical RAG pipeline retrieves candidate code entities and then uses an LLM to reason over the retrieved context. The quality of generation is bounded by retrieval: an LLM cannot produce a correct fix for code it was not shown.

RAG for code faces one core difficulty: bridging the gap between natural language task descriptions and structured source code. A bug report uses high-level, ambiguous prose, while retrieval targets are syntax-constrained code entities connected through explicit dependencies. Surface-level text similarity often fails to identify the relevant code. Recent empirical work confirms that retrieval quality, rather than reasoning capacity, is the dominant bottleneck in agent performance~\cite{yang2024swebench}.

\subsection{Sparse, Dense, and Graph-Based Retrieval}
\label{sec:retrieval-families}

We examine three retrieval families in ascending order of structural awareness, analyzing the strength and core failure mode of each. \Cref{tab:retrieval-comparison} summarizes their key characteristics; \cref{fig:retrieval-flow} illustrates their conceptual workflows.

\paragraph{Sparse retrieval.}
Sparse retrieval computes relevance as weighted term overlap between the query and indexed code tokens. BM25~\cite{bm25}, the dominant method in this class, scores each document using term frequency, inverse document frequency, and a saturation function that prevents high-frequency terms from dominating. Sparse methods require no learned parameters, scale to large corpora, and produce interpretable scores.

The core failure mode is lexical sensitivity. Relevance is measured at the token level, so a query term and a code identifier that express the same concept but differ in surface form will not match. In source code, this is pervasive: identifiers combine several semantic units into one token, such as \texttt{SQLCompiler}, \texttt{get\_absolute\_url}, or \texttt{BaseHasher}. A query mentioning SQL compilation does not match \texttt{SQLCompiler} under atomic tokenization. Sparse methods therefore work best when the vocabulary of the task description closely mirrors the vocabulary of the relevant source code.

\paragraph{Dense retrieval.}
Dense retrieval encodes queries and code entities into a shared vector space and ranks candidates by cosine similarity. Models such as CodeBERT~\cite{codebert}, GraphCodeBERT~\cite{graphcodebert}, and UniXcoder~\cite{unixcoder} are trained on large code corpora to align natural language descriptions with code representations, making them more tolerant of vocabulary variation than sparse methods.

Dense methods carry three limitations for repository-scale retrieval. First, they compute similarity from token sequences alone: the score assigned to a candidate is determined by its text, not by which modules it imports, which functions it calls, or which components depend on it. Second, competitive performance requires fine-tuning on code-query pairs that may not exist for a specific repository or language. Third, embedding scores are opaque: there is no path trace explaining why a candidate received a high score.

\paragraph{Graph-based retrieval.}
Graph-based retrieval represents code relationships as edges in a typed directed graph and propagates relevance from query-matched seeds to structurally connected entities. Unlike sparse and dense methods, which score candidates independently, graph-based methods model relevance as traversal along dependency edges.

Recent systems use this idea in different ways. GraphCoder projects~\cite{liu2024graphcoder} capture call and data-flow relationships through a code context graph for repository-level code completion. Athale and Vaddina~\cite{athale2025knowledge} construct a knowledge graph over repository structure and use graph queries to retrieve context for LLM-based generation. CodexGraph~\cite{liu2024codexgraph} connects LLMs to code repositories through Neo4j queries. These systems use sparse retrieval to identify seed nodes, then apply graph traversal or ranking algorithms, including Personalized PageRank, to reach structurally relevant entities.

\section{Graph-Based Code Retrieval Systems}
\label{sec:graph-systems}
% ============================================================

Having motivated graph-based retrieval as a family in \cref{sec:retrieval-families}, this section examines five concrete systems that represent the current state of the art. Each treats a repository as a typed directed graph but differs in how the graph is constructed, how seeds are selected, and how relevance propagates. \Cref{tab:graph-systems} in \cref{sec:gaps} summarises their design axes side by side; the subsections below describe each system and identify the unresolved limitation it leaves behind.

\subsection{RepoGraph: Line-Level Ego-Graph Retrieval}
\label{sec:repograph}

RepoGraph~\cite{ouyang2025repograph} constructs a line-level dependency graph of a repository, in which each node corresponds to a single line of source code and edges encode references between symbols defined or used on those lines. At retrieval time, RepoGraph identifies a set of seed lines from the task description and returns the $k$-hop \emph{ego-graph} around those seeds, that is, every line reachable within $k$ edges. Integrated into an agentic framework for SWE-bench Lite, the authors report a 32.8\% relative improvement in task resolution rate over a text-only baseline.

The central limitation of RepoGraph is that $k$-hop expansion is \emph{unranked}. Every node within $k$ hops is returned with equal standing, which creates a sharp tension between recall and context budget: $k=1$ is often too narrow to reach the relevant file, while $k=2$ typically explodes into dozens of nodes that must all be fitted into a fixed LLM context window. \Cref{fig:khop-explosion} illustrates this tension on a small graph: the relevant target lies outside the $k{=}1$ neighbourhood, but expanding to $k{=}2$ retrieves it alongside ten additional nodes with no signal to distinguish the target from the rest. The authors explicitly acknowledge this trade-off.

\subsection{LocAgent: BFS Traversal with Sparse Rescoring}
\label{sec:locagent}

LocAgent~\cite{chen2025locagent} targets the narrower problem of issue-to-file localisation: given a bug report, identify which file must be modified. It builds an entity-level graph (files, classes, functions) and combines a breadth-first traversal from query-matched seeds with a BM25 re-ranking step over the visited nodes. On their benchmark, LocAgent reports 92.7\% file-level localisation accuracy.

LocAgent demonstrates that graph structure improves localisation even when combined with conventional sparse scoring. The limitation is that BFS-based traversal is inherently local: relevance is determined by proximity to the seed set, not by global graph structure. A file that is structurally central to the repository, such as a core utility module transitively involved in many code paths, receives no signal from BFS unless it lies within the traversal radius. No fixed-radius traversal can capture the global structural importance of the repository's most connected entities.

\subsection{CodexGraph: LLM-Generated Cypher Queries}
\label{sec:codexgraph}

CodexGraph~\cite{liu2024codexgraph} takes a different approach to graph-based retrieval. Rather than defining a fixed retrieval algorithm, it exposes a Neo4j graph of the repository to an LLM agent and asks the agent to write Cypher queries to navigate it. The graph schema, nodes for files, classes, and methods with edges for \texttt{contains}, \texttt{inherits}, \texttt{has\_method}, and \texttt{uses}, closely mirrors the entity-level structure that several systems in this family adopt.

This design reuses the LLM's reasoning ability but pays a cost on every retrieval query: each round requires an additional LLM call to produce the Cypher expression, and incorrect queries must be detected and retried. Latency, token cost, and query correctness all depend on the language model. Non-determinism in the retrieval loop also makes the system difficult to evaluate and debug reproducibly.

\subsection{GraphCoder Projects: Code Context Graphs and Subgraph Matching}
\label{sec:graphcoder}

GraphCoder projects~\cite{liu2024graphcoder} target repository-level code completion rather than issue resolution. Each function is represented as a Code Context Graph (CCG) that combines control-flow and data-dependence edges at the statement level; candidate snippets are retrieved by computing subgraph edit distance between the completion context and candidate graphs. GraphCoder projects report a 6.06\% improvement in exact-match accuracy over strong RAG baselines.

GraphCoder projects validate that fine-grained structural signals improve code retrieval, but subgraph edit distance is expensive: in the worst case it is NP-hard, and even approximate variants scale poorly with graph size. This restricts the approach to narrow, local matching scenarios and makes it unsuitable for interactive, repository-scale retrieval.

\subsection{CodeGraphContext: Multi-Language Symbol Graph}
\label{sec:cgc}

CodeGraphContext (CGC)~\cite{cgc2024} is an open-source MCP-based system that indexes repositories across multiple programming languages using Tree-sitter and optionally SCIP. It supports a broad range of storage backends, including Kuzu, FalkorDB, and Neo4j, and exposes approximately 25 MCP tools covering symbol search, relationship traversal, dependency analysis, and portable graph bundles. CGC's primary query model is symbol-centric: given a symbol name or relationship type, the system answers structural lookups through these tools.

The breadth of CGC's surface area is also its core limitation for task-driven retrieval. With 25 tools and no retrieval-specific ranking algorithm, an agent using CGC must issue multiple queries and manually aggregate results to answer the question: which files does this task require? There is no single operation that translates a natural language task description into a globally ranked list of relevant code entities. This is the design choice that CodeGraph takes in the opposite direction: two tools, one of which runs Personalized PageRank over the full dependency graph to produce a ranked, token-budgeted result in a single call.

From \cref{tab:graph-systems}, \cref{fig:design-space}, and the broader survey of sparse, dense, and graph-based families in \cref{sec:retrieval-families}, four gaps emerge.

\paragraph{Gap 1: Ranked structural retrieval under a fixed context budget.}
Every modern LLM enforces a hard token limit, so retrieval must produce a ranked output that the agent can truncate at top-$k$ without losing the relevant item. Sparse and dense methods rank their outputs but ignore structure. Graph-based methods capture structure but fall into one of three failure modes: unranked $k$-hop expansion that explodes at $k=2$ (RepoGraph); expensive subgraph matching that does not scale to repository-sized graphs (GraphCoder projects); or LLM-generated queries whose output is neither ranked nor cheap (CodexGraph). CodeGraphContext is deterministic and cheap but does not produce a globally ranked list at all: the agent must issue multiple tool queries to assemble context. No surveyed system provides cheap, globally ranked, structure-aware retrieval under a hard token budget.

\paragraph{Gap 2: Lexical, semantic, and structural signals treated in isolation.}
Each retrieval family excels at one signal and is blind to the others. Sparse methods see tokens, dense methods see embeddings, graph methods see edges. In real repository tasks all three matter simultaneously: a bug report is written in natural-language prose, the relevant identifiers carry semantic content, and the file that must be modified is structurally coupled to whatever the seed nodes happen to match. The surveyed systems combine these signals only in serial stages: LocAgent runs BM25 as a rescoring step on top of BFS rather than as a unified relevance score. The literature offers no principled mechanism to let a strong structural signal lift a weak lexical seed, or vice versa.

\paragraph{Gap 3: Non-determinism and cost in the retrieval loop.}
CodexGraph places an LLM inside the retrieval loop: every retrieval query invokes a language model to generate a Cypher expression, inheriting its latency, monetary cost, and non-determinism. Determinism is rarely stated as an explicit design property in the surveyed systems, but it is a practical requirement for three reasons: interactive use (users expect sub-second responses), scientific evaluation (reproducibility requires the same input to produce the same output), and debugging (a retrieval failure must be diagnosable without replaying an LLM sample).

\paragraph{Gap 4: Evaluation on end-to-end repository-level tasks.}
GraphCoder projects report exact-match accuracy on code completion; LocAgent reports file-level localisation accuracy. Both are surrogate metrics that measure a single stage of a longer pipeline. Repository-level benchmarks such as SWE-bench~\cite{yang2024swebench} measure whether an agent can resolve a real GitHub issue end to end, and retrieval is only one component of that score. Few graph-based systems isolate the contribution of retrieval alone on such benchmarks, leaving open the empirical question of whether structural retrieval helps where it matters most.

\medskip

These four gaps are mutually reinforcing. A system that addresses only one, say, producing a ranked output, while still relying on an LLM in the retrieval loop, does not meaningfully close the overall problem. Any retrieval method that aims to serve LLM agents on real repository-level tasks must provide, at minimum: a globally ranked output, a unified treatment of lexical and structural signals, deterministic and cheap execution, and an evaluation that isolates retrieval quality on end-to-end tasks. \Cref{ch:design} returns to these four requirements and uses them to motivate the design of the system proposed in this thesis.
