\chapter{Background and Related Work}
\label{ch:background}

This chapter identifies the fundamental constraints of code retrieval for LLM-based agents. It provides technical background on the foundational technologies necessary for structural code analysis, specifically static parsing, graph databases, and ranking algorithms, and surveys established methodological families within the literature.

% ============================================================
\section{Background}
\label{sec:background}
% ============================================================

\subsection{Tree-sitter and Static Analysis}
\label{sec:treesitter-bg}

Source code structure can be extracted through \emph{static analysis}, which examines source text without program execution. Modern static analysis tools leverage incremental parsing libraries such as \texttt{tree-sitter}~\cite{treesitter}. Unlike traditional compiler-based parsers, \texttt{tree-sitter} is designed to be:
\begin{itemize}
    \item \textbf{General:} It supports a wide range of programming languages through a unified grammar system.
    \item \textbf{Robust:} It can parse syntactically incomplete or erroneous code, which is common in active development environments.
    \item \textbf{Fast:} It builds an initial concrete syntax tree (CST) in sub-millisecond time and can incrementally update the tree as the file is modified.
\end{itemize}
Such parsers can serve as the foundational engine for a structural indexer, converting raw source code into high-fidelity syntax trees from which dependencies (calls, imports, inheritance) are extracted.

\subsection{Graph Databases and Neo4j}
\label{sec:neo4j-bg}

The interconnected nature of source code (where files import modules, classes inherit from others, and functions call each other) is naturally modelled as a directed, typed graph.
 Relationally representing this structure in a standard SQL database requires complex joins that perform poorly for multi-hop traversals.

Graph databases, specifically property graph models like \texttt{Neo4j}, are designed to store and query highly connected data. In \texttt{Neo4j}, entities are represented as \textit{nodes} and relationships as \textit{edges}, both of which can store key-value properties. This allows for efficient execution of graph algorithms like Personalized PageRank, which must traverse the entire topology of the repository.

\subsection{PageRank and Ranking Algorithms}
\label{sec:pagerank-bg}

PageRank~\cite{page1999pagerank} is a link-analysis algorithm originally designed by Google to rank web pages by their structural importance. The algorithm models a random walker who traverses the graph by following edges. A node's importance is determined by the number and quality of links pointing to it.

While standard PageRank provides a global importance score for every node, \emph{Personalized PageRank} (PPR) modifies the random walk to bias it toward specific seed nodes. This variation is critical for retrieval: an agent does not need to know which files are globally important, but rather which files are structurally relevant to a specific query. PPR propagates relevance from query-matched seeds to their structural neighbours, making it an ideal candidate for software repository retrieval.

\section{Code Retrieval for LLM Agents}
\label{sec:related-work}
% ============================================================

LLM-based coding agents face a fundamental selection problem: given a natural language task description and a large code repository, which source files should the agent examine? This section defines this retrieval problem, establishes its constraints, and surveys three classes of methods (sparse, dense, and graph-based) that represent increasingly structural approaches to solving it.

\subsection{The Retrieval Problem}
\label{sec:retrieval-problem}
%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 

For current production models, this limit ranges from 32{,}000 to 200{,}000 tokens~\cite{gpt4,claude3}, while a moderately sized Python repository (Django being a representative example) contains several million tokens of source code.

This selection problem has an asymmetric cost structure. A false negative (failing to retrieve a file that the agent must modify) renders the task unsolvable regardless of the agent's subsequent reasoning quality. A false positive (retrieving an irrelevant file) incurs only a noise cost: it consumes context budget but does not prevent a correct solution.
 This asymmetry makes retrieval fundamentally \emph{recall-oriented}: the primary measure of retrieval quality is whether the relevant files appear within the top-$k$ results, rather than the precision of the entire retrieved set.

%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 
\subsection{Retrieval-Augmented Generation for Code}
\label{sec:rag}
%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 

Retrieval-augmented generation (RAG)~\cite{lewis2020rag} addresses the context window limitation by treating the repository as an external knowledge base. A typical RAG pipeline first retrieves candidate code entities, then uses an LLM to reason over the retrieved context. The quality of generation is strictly bounded by retrieval: an LLM cannot produce a correct fix for code it was not shown.

RAG for code faces a fundamental challenge: bridging the modal gap between natural language task descriptions and structured source code. A bug report uses high-level, ambiguous prose, while the retrieval targets are syntax-constrained code entities interconnected through explicit dependencies. Surface-level text similarity often fails to identify the relevant code. Recent empirical work confirms that retrieval quality, rather than reasoning capacity, is the dominant bottleneck in agent performance~\cite{yang2024swebench}. Evaluations on benchmarks such as SWE-bench demonstrate that agents with targeted retrieval mechanisms outperform those given larger but unfocused context~\cite{yang2024swebench}.

\subsection{Sparse, Dense, and Graph-Based Retrieval}
\label{sec:retrieval-families}
%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 

This section examines three classes of retrieval methods in turn, analyzing their strengths and fundamental limitations.
The key characteristics of these families are summarized in \cref{tab:retrieval-comparison}, and their respective conceptual workflows are illustrated in \cref{fig:retrieval-flow}.

\paragraph{Sparse retrieval.}
Sparse retrieval methods compute relevance as a weighted term overlap between the query and the indexed code tokens. BM25~\cite{bm25}, the dominant method in this class, scores each document using term frequency, inverse document frequency, and a saturation function that prevents overfitting to high-frequency terms. Sparse methods require no learned parameters, scale to large corpora, and produce interpretable scores. Their principal limitation is lexical sensitivity: relevance is measured at the token level, so a query term and a code identifier that express the same concept but differ in surface form will not match. In source code, this is a pervasive problem. Identifiers frequently combine multiple semantic units into a single compound token, such as \texttt{SQLCompiler}, \texttt{get\_absolute\_url}, or \texttt{BaseHasher}, using camelCase or underscore conventions. A query mentioning SQL compilation does not match the token \texttt{SQLCompiler} under atomic tokenization. Sparse methods are therefore most effective when the vocabulary of the task description closely mirrors the vocabulary of the relevant source code, and degrade when it does not.

\paragraph{Dense retrieval.}
Dense retrieval methods encode queries and code entities into a shared continuous vector space and rank candidates by cosine similarity. Models such as CodeBERT~\cite{codebert}, GraphCodeBERT~\cite{graphcodebert}, and UniXcoder~\cite{unixcoder} are trained on large code corpora to align natural language descriptions with code representations, enabling matching that is robust to vocabulary variation and paraphrase. However, dense methods have three limitations for repository-scale retrieval. First, they compute similarity from token sequences alone and have no structural awareness: the score assigned to a candidate file is determined entirely by its textual content, without regard to which modules it imports, which functions it calls, or which components depend on it. Second, achieving competitive performance typically requires fine-tuning on domain-specific code--query pairs, which may not be available for every repository or language. Third, embedding similarity scores are opaque: there is no principled way to trace why a specific candidate received a high score, making it difficult to diagnose retrieval failures or improve the system systematically.

\paragraph{Graph-based retrieval.}
Graph-based retrieval methods represent code relationships as edges in a typed directed graph and propagate relevance from query-matched seed entities to structurally connected entities. Unlike sparse and dense methods, which score candidates independently, graph-based methods model relevance as flowing along structural connections between code entities. Recent work demonstrates the effectiveness of this approach. GraphCoder~\cite{liu2024graphcoder} captures call and data-flow relationships through a code context graph to enhance repository-level code completion. Athale and Vaddina~\cite{athale2025knowledge} construct a knowledge graph over repository structure and use graph queries to retrieve context for LLM-based generation. CodexGraph~\cite{liu2024codexgraph} further demonstrates the utility of bridging LLMs and code repositories via graph databases. These systems use sparse retrieval to identify seed nodes in a code dependency graph, then apply graph traversal or ranking algorithms (such as Personalized PageRank) to reach structurally relevant entities.

\section{Graph-Based Code Retrieval Systems}
\label{sec:graph-systems}
% ============================================================

Having motivated graph-based retrieval as a family in \cref{sec:retrieval-families}, this section examines four concrete systems that represent the current state of the art. Each treats a repository as a typed directed graph, but differs in how the graph is constructed, how seeds are chosen, and how relevance is propagated through the graph. \Cref{tab:graph-systems} in \cref{sec:gaps} summarises their design choices side by side; the following subsections describe each system individually and identify the core limitation that each leaves unresolved.

%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 
\subsection{RepoGraph: Line-Level Ego-Graph Retrieval}
\label{sec:repograph}
%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 

RepoGraph~\cite{ouyang2025repograph} constructs a line-level dependency graph of a repository, in which each node corresponds to a single line of source code and edges encode references between symbols defined or used on those lines. At retrieval time, RepoGraph identifies a set of seed lines from the task description and returns the $k$-hop \emph{ego-graph} around those seeds, that is, every line reachable within $k$ edges. Integrated into an agentic framework for SWE-bench Lite, the authors report a 32.8\% relative improvement in task resolution rate over a text-only baseline.

The central limitation of RepoGraph is that $k$-hop expansion is \emph{unranked}. Every node within $k$ hops is returned with equal standing, which creates a sharp tension between recall and context budget: $k=1$ is often too narrow to reach the relevant file, while $k=2$ typically explodes into dozens of nodes that must all be fitted into a fixed LLM context window. \Cref{fig:khop-explosion} illustrates this tension on a small graph: the relevant target lies outside the $k{=}1$ neighbourhood, but expanding to $k{=}2$ retrieves it alongside ten additional nodes with no signal to distinguish the target from the rest. The authors explicitly acknowledge this trade-off.

\subsection{LocAgent: BFS Traversal with Sparse Rescoring}
\label{sec:locagent}
%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 

LocAgent~\cite{chen2025locagent} targets the narrower problem of \emph{issue-to-file localisation}: given a bug report, identify which file must be modified. It builds an entity-level graph (files, classes, functions) and combines a breadth-first traversal from query-matched seeds with a BM25 re-ranking step over the nodes visited during the traversal. On their benchmark, LocAgent reports 92.7\% file-level localisation accuracy.

LocAgent demonstrates that graph structure improves localisation even when combined with conventional sparse scoring. However, its BFS-based traversal is inherently local: relevance is determined by proximity to the seed set, not by global graph structure. A file that is structurally central to the repository, for example, a core utility module transitively involved in many code paths, receives no signal from BFS unless it happens to lie within the traversal radius. This locality constraint means that no fixed-radius traversal alone can capture the global structural importance of the repository's most connected entities.

%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 
\subsection{CodexGraph: LLM-Generated Cypher Queries}
\label{sec:codexgraph}
%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 

CodexGraph~\cite{liu2024codexgraph} takes a different route to graph-based retrieval. Rather than defining a fixed retrieval algorithm, it exposes a Neo4j graph of the repository to an LLM agent and asks the agent to \emph{write Cypher queries} to navigate it. The graph schema, nodes for files, classes, and methods, with edges for \texttt{contains}, \texttt{inherits}, \texttt{has\_method}, and \texttt{uses}, closely mirrors the entity-level structure that several systems in this family adopt. Retrieval, however, is expressed as natural language translated to graph queries on the fly.

This design elegantly reuses the LLM's reasoning ability, but pays a cost on every retrieval query: each round requires an additional LLM call to produce the Cypher expression, and incorrect queries must be detected and retried. Latency, token cost, and query correctness all depend on the language model. A retrieval step that is deterministic and query-time cheap would sidestep these costs entirely.

%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 
\subsection{GraphCoder: Code Context Graphs and Subgraph Matching}
\label{sec:graphcoder}
%, ,, ,, ,, ,, ,, ,, ,, ,, ,, , 

GraphCoder~\cite{liu2024graphcoder} targets repository-level code \emph{completion} rather than issue resolution. It represents each function as a Code Context Graph (CCG) that combines control-flow and data-dependence edges at the statement level, and retrieves candidate snippets by computing subgraph edit distance between the current completion context and candidate graphs in the repository. GraphCoder reports a 6.06\% improvement in exact-match accuracy over strong RAG baselines.

GraphCoder validates that fine-grained structural signals (control flow, data flow) improve code retrieval, but subgraph edit distance is an expensive operation: in the worst case it is NP-hard, and even approximate variants scale poorly with graph size. This restricts GraphCoder to narrow, local matching scenarios and makes it unsuitable for interactive, repository-scale retrieval. The key insight,  that structural edges carry retrieval signal,  stands even if the specific matching algorithm is replaced by a cheaper alternative.

\label{sec:gaps}

Read together, they also reveal a consistent set of limitations. This section makes those limitations explicit by staying in diagnostic mode, describing what the literature does not yet offer, and defers any discussion of how this thesis addresses them to \Cref{ch:design}.

From \cref{tab:graph-systems}, \cref{fig:design-space}, and the broader survey of sparse, dense, and graph-based families in \cref{sec:retrieval-families}, four gaps emerge.

\paragraph{Gap 1: Ranked structural retrieval under a fixed context budget.}
Every modern LLM enforces a hard token limit, so retrieval must produce a \emph{ranked} output that the agent can truncate at top-$k$ without losing the relevant item. Sparse and dense methods rank their outputs but ignore structure. Graph-based methods capture structure but fall into one of three failure modes: unranked $k$-hop expansion that explodes at $k=2$ (RepoGraph); expensive subgraph matching that does not scale to repository-sized graphs (GraphCoder); or LLM-generated queries whose output is neither ranked nor cheap (CodexGraph). No surveyed system provides cheap, globally ranked, structure-aware retrieval under the hard token budget of modern agents.

\paragraph{Gap 2: Lexical, semantic, and structural signals treated in isolation.}
Each retrieval family excels at one signal and is blind to the others. Sparse methods see tokens, dense methods see embeddings, graph methods see edges. In real repository tasks all three matter simultaneously: a bug report is written in natural-language prose, the relevant code identifiers carry semantic content, and the file that must be modified is structurally coupled to whatever the seed nodes happen to match. The surveyed systems combine these signals only in serial stages, LocAgent, for example, runs BM25 as a rescoring step on top of BFS, rather than as a unified relevance score. The literature offers no principled way to let a strong structural signal lift a weak lexical seed, or vice versa.

\paragraph{Gap 3: Non-determinism and cost in the retrieval loop.}
CodexGraph places an LLM \emph{inside} the retrieval loop: every retrieval query invokes a language model to generate a Cypher expression. This inherits the LLM's latency, monetary cost, and non-determinism for a core pipeline operation. Determinism is rarely stated as an explicit design property in the surveyed systems, but it is a practical requirement for three distinct reasons: interactive use (users expect sub-second responses), scientific evaluation (reproducibility requires that the same input produce the same output), and debugging (a retrieval failure must be diagnosable without replaying an LLM sample). This property is absent from the most flexible graph-based system in the literature and not examined in the others.

\paragraph{Gap 4: Evaluation on end-to-end repository-level tasks.}
GraphCoder reports exact-match accuracy on code completion; LocAgent reports file-level localisation accuracy. Both are surrogate metrics that measure a single stage of a longer pipeline. Repository-level benchmarks such as SWE-bench~\cite{yang2024swebench} measure whether an agent can resolve a real GitHub issue end to end, and retrieval is only one component of that score. Few graph-based systems isolate the contribution of retrieval alone on such benchmarks, which leaves open the empirical question of whether structural retrieval helps where it matters most, on realistic, repository-level engineering tasks.

\medskip

These four gaps are mutually reinforcing. A system that addresses only one, say, producing a ranked output, while ignoring the others, say, still relying on an LLM in the retrieval loop, does not meaningfully close the overall problem. Any retrieval method that aims to serve LLM agents on real repository-level tasks must provide, at a minimum: a globally ranked output, a unified treatment of lexical and structural signals, deterministic and cheap execution, and an evaluation that isolates retrieval quality on end-to-end tasks. \Cref{ch:design} returns to these four requirements and uses them to motivate the design of the system proposed in this thesis.
