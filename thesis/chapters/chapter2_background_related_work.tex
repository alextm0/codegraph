\chapter{Background and Related Work}
\label{ch:background}

This chapter provides the technical and methodological background needed to situate CodeGraph within the broader landscape of repository-level code retrieval.

Building on these foundations, the chapter defines the retrieval problem addressed in this thesis, compares three major approaches to code retrieval, sparse, dense, and graph-based, and reviews four representative graph-based systems to identify the limitations that motivate CodeGraph.

% ============================================================
\section{Background}
\label{sec:background}
% ============================================================

A structural retrieval pipeline must transform raw source code into a machine-usable representation, organize the extracted entities and relations in a form that supports efficient traversal, and rank the resulting context by task-specific structural relevance.

This section introduces the three technical foundations that make such a pipeline possible: syntax-aware static analysis, graph storage and analytics, and Personalized PageRank.

\subsection{Tree-sitter and Static Analysis}
\label{sec:treesitter-bg}

Static analysis derives structural information from source code without executing the program~\cite{cousot1996abstract}. In repository retrieval, its role is to recover code entities and relations in a form that later stages can store, traverse, and rank.

Tree-sitter~\cite{treesitter} is well suited to this task because it parses source files into syntax trees that can be queried and transformed into higher-level program units~\cite{comex2023}. It is particularly useful for repository analysis because it supports many languages through a unified grammar framework, remains useful even when code is incomplete or locally invalid, and supports incremental parsing as files change~\cite{treesitterdocs}.

In this thesis, Tree-sitter provides the parsing foundation from which repository entities and structural relations are extracted.

\subsection{Graph Storage and Ranking with Neo4j Graph Data Science}
\label{sec:neo4j-gds-bg}

Source code is naturally represented as a graph: files contain classes and functions, modules import other modules, classes inherit from one another, and functions call other functions~\cite{robinson2013graph}. Because this structure is directed, typed, and highly interconnected, graph storage is often a better fit than a purely relational representation for multi-hop dependency analysis.

Neo4j~\cite{neo4j2024docs} is a property graph database in which entities are stored as nodes and relationships as edges, with properties attached to both. This model supports direct traversal over repository relations while preserving metadata such as entity type, file path, and relationship category.

For graph analytics, the Neo4j Graph Data Science library~\cite{neo4jgds2024catalog} separates persistent storage from in-memory analytical execution. This makes it possible to project only the nodes, edges, and weights needed for ranking, then run graph algorithms over that projected structure~\cite{neo4jgds2024pagerank}.

In this thesis, Neo4j and GDS provide the storage and execution environment used for structural retrieval over the repository graph.

\subsection{Personalized PageRank}
\label{sec:ppr-bg}

PageRank~\cite{brin1998pagerank} is a link-analysis algorithm that estimates node importance by propagating probability mass through a directed graph. In its original form, it produces a global measure of structural importance based on graph connectivity.

Personalized PageRank~\cite{jeh2003ppr} adapts this idea by replacing the global restart distribution with a query-specific set of seed nodes. This makes it suitable for retrieval tasks, because relevance is propagated outward from entities initially associated with the query rather than from a uniform notion of graph centrality.

In repository retrieval, this allows structurally related code entities to receive high scores even when they are not direct lexical matches for the original task description.

\section{Code Retrieval for LLM Agents}
\label{sec:related-work}
% ============================================================

This section frames the retrieval problem addressed in this thesis and situates CodeGraph within the broader landscape of repository-level code retrieval. It then examines three major approaches to code retrieval, sparse, dense, and graph-based, highlighting the relevance signal each captures and the failure mode that motivates the next.

\subsection{The Retrieval Problem}
\label{sec:retrieval-problem}

LLM-based coding agents face a fundamental selection problem: given a natural-language task description and a large code repository, which code entities should the agent inspect? Because the model can reason only over the context it is given, retrieval must identify a small set of files, functions, or classes that are sufficient for the task at hand.

This problem is constrained by the context window. Even when modern models support tens of thousands of tokens, real repositories are typically far larger than what can be provided in a single prompt. Retrieval is therefore not a convenience layer, but a necessary selection mechanism that determines which parts of the repository become visible to the agent~\cite{gpt4,claude3}.

The cost of retrieval errors is also asymmetric. If retrieval fails to return a file that must be inspected or modified, the task becomes effectively unsolvable regardless of the agent's reasoning ability. By contrast, retrieving an irrelevant file usually imposes only a noise cost by consuming part of the available context budget. For this reason, repository retrieval is fundamentally recall-oriented: the central question is not whether every retrieved item is relevant, but whether the truly relevant items appear within the top-$k$ results.

\subsection{Retrieval-Augmented Generation for Code}
\label{sec:rag}

Retrieval-augmented generation~\cite{lewis2020rag} addresses this limitation by treating the repository as an external knowledge source and supplying the model with only the subset of code selected at query time. In a typical code RAG pipeline, retrieval identifies candidate entities or files, and the language model then reasons over that retrieved context to localize faults, explain behavior, or propose edits.

In this setting, generation quality is bounded by retrieval quality. An agent cannot correctly modify code that was never retrieved, and it cannot reliably reason about dependencies that remain outside the provided context. This makes retrieval a first-order systems problem rather than a simple preprocessing step.

RAG for code is difficult because it must bridge two different representational spaces. User queries are expressed in natural language, often at a high level of abstraction, while repositories consist of syntax-constrained program entities linked by explicit structural dependencies. A bug report may describe symptoms, intent, or expected behavior, whereas the relevant retrieval targets are concrete functions, classes, imports, and call relationships. Pure surface-level similarity is therefore often insufficient to recover the code that actually matters.

This mismatch explains why repository retrieval remains a bottleneck for coding agents. Strong downstream reasoning is useful only after the right context has been retrieved. The retrieval stage must therefore do more than match words, it must connect the semantics of the task description to the structure of the codebase~\cite{yang2024swebench}.

\subsection{Sparse, Dense, and Graph-Based Retrieval}
\label{sec:retrieval-families}

We examine three retrieval families in ascending order of structural awareness, analyzing the strength and core failure mode of each. \Cref{tab:retrieval-comparison} summarizes their key characteristics; \cref{fig:retrieval-flow} illustrates their conceptual workflows.

\paragraph{Sparse retrieval.}
Sparse retrieval computes relevance as weighted term overlap between the query and indexed code tokens. BM25~\cite{bm25}, the dominant method in this class, scores each document using term frequency (TF), inverse document frequency (IDF), and a saturation function that prevents high-frequency TF values from dominating. Sparse methods require no learned parameters, scale to large corpora, and produce interpretable scores.

The core failure mode is lexical sensitivity. Relevance is measured at the token level, so a query term and a code identifier that express the same concept but differ in surface form will not match. In source code, this is pervasive: identifiers combine several semantic units into one token, such as \texttt{SQLCompiler}, \texttt{get\_absolute\_url}, or \texttt{BaseHasher}. A query mentioning SQL compilation does not match \texttt{SQLCompiler} under atomic tokenization. Sparse methods therefore work best when the vocabulary of the task description closely mirrors the vocabulary of the relevant source code.

\paragraph{Dense retrieval.}
Dense retrieval encodes queries and code entities into a shared vector space and ranks candidates by cosine similarity. Models such as CodeBERT~\cite{codebert}, GraphCodeBERT~\cite{graphcodebert}, and UniXcoder~\cite{unixcoder} are trained on large code corpora to align natural language descriptions with code representations, making them more tolerant of vocabulary variation than sparse methods.

Dense methods carry three limitations for repository-scale retrieval. First, they compute similarity from token sequences alone: the score assigned to a candidate is determined by its text, not by which modules it imports, which functions it calls, or which components depend on it. Second, competitive performance requires fine-tuning on code-query pairs that may not exist for a specific repository or language. Third, embedding scores are opaque: there is no path trace explaining why a candidate received a high score.

\paragraph{Graph-based retrieval.}
Graph-based retrieval represents code relationships as edges in a typed directed graph and propagates relevance from query-matched seeds to structurally connected entities. Unlike sparse and dense methods, which score candidates independently, graph-based methods model relevance as traversal or propagation along dependency edges.

Recent systems instantiate this idea in different ways. RepoGraph~\cite{ouyang2025repograph} uses line-level ego-graph retrieval, LocAgent~\cite{chen2025locagent} combines graph traversal with sparse indexing for code localization, CodexGraph~\cite{liu2024codexgraph} exposes repository structure through LLM-generated graph queries, and LARGER~\cite{hu2026larger} uses lexically anchored local graph expansion inside the agent loop.

Together, these systems show that graph structure can improve retrieval reach, but they also expose unresolved trade-offs in ranking, determinism, and cost.

\section{Graph-Based Code Retrieval Systems}
\label{sec:graph-systems}
% ============================================================

Graph-based code retrieval starts from the observation that repository-level relevance is not determined only by lexical similarity. In software repositories, relevant code is often connected through structural relations such as file organization, calls, imports, inheritance, and definition-use dependencies. Graph-based systems therefore represent code entities as nodes and repository relations as edges, then use this structure to identify code that may be relevant even when it does not use the same terminology as the query.

The systems reviewed in this section share this structural motivation, but they differ in graph granularity and retrieval control. Some operate at the line or statement level, while others model files, classes, functions, and repository-level entities. Some retrieve local neighbourhoods around query-matched seeds, while others expose the graph through agent tools or graph-database queries. These choices matter because they determine how much structural context can be recovered, how predictable the retrieval process remains, and whether the final output can be reduced to a ranked top-$k$ result under a fixed context budget. \Cref{tab:graph-systems} in \cref{sec:gaps} summarises the four systems along the design axes that most directly expose these trade-offs.

\subsection{RepoGraph: Line-Level Ego-Graph Retrieval}
\label{sec:repograph}

RepoGraph~\cite{ouyang2025repograph} models a repository at the line level: each node corresponds to a line of code, nodes encode whether a line functions as a definition or reference, and edges capture invocation and structural containment relations. Retrieval is performed by matching a search term to a central node and extracting a $k$-hop ego-graph around that node. The retrieved subgraph is then flattened or summarised before being passed to the downstream agent.

This design gives RepoGraph a clear strength: it can expose immediate structural context with high resolution. A one-hop neighbourhood remains close to the matched symbol and often captures the nearby definitions, references, and interactions needed for a local coding task. In the reported SWE-bench analysis, the average one-hop retrieval contains 11.6 nodes and 37.1 edges, which keeps the retrieved context relatively compact for prompt construction~\cite{ouyang2025repograph}.

The weakness appears when the radius grows. At two hops, the average retrieved neighbourhood expands to 54.5 nodes and 89.9 edges, and direct flattening increases the average token count from 2{,}310.7 tokens to 10{,}505.3 tokens~\cite{ouyang2025repograph}. The paper also reports that the two-hop flattened variant performs worse than the one-hop flattened variant, with a lower resolve rate despite containing more structural information~\cite{ouyang2025repograph}. This shows that expanding the neighbourhood is not equivalent to improving retrieval quality. Without ranking, larger ego-graphs can mix useful dependencies with irrelevant surrounding code. \Cref{fig:khop-explosion} illustrates this tension on a small graph: the relevant target lies outside the $k{=}1$ neighbourhood, but expanding to $k{=}2$ retrieves it alongside ten additional nodes with no signal to distinguish the target from the rest.

RepoGraph is therefore most useful as evidence for the value and risk of line-level graph retrieval. It shows that structural expansion can recover context missed by ordinary lexical search, but it also shows that unranked neighbourhood expansion creates a direct trade-off between recall, noise, and context budget. The absence of ranking under a fixed context budget is examined as Gap~1 in \cref{sec:gaps}.

\subsection{LocAgent: Graph-Guided Code Localisation}
\label{sec:locagent}

LocAgent~\cite{chen2025locagent} focuses on code localisation rather than general repository retrieval. Its task is to identify the repository entities that are likely to require modification for a given issue description. To support this, LocAgent constructs a heterogeneous directed graph whose node types include directories, files, classes, and functions, and whose edge types include structural nesting, imports, invocations, and inheritance.

The retrieval process combines sparse entity indexing with graph traversal. LocAgent first searches over repository entities using identifiers, entity names, and BM25-based keyword indexes. It then uses a graph traversal tool that performs type-aware breadth-first search from selected entities, allowing the agent to control traversal direction, relation types, entity types, and hop distance. This makes localisation a guided navigation problem rather than a purely lexical retrieval problem.

The advantage of this design is that it captures repository relations that may cross directory boundaries. Two files may be far apart in the folder hierarchy but structurally close because they call each other, inherit from the same abstraction, or participate in the same dependency path~\cite{chen2025locagent}. LocAgent uses the graph to make these relations available to the agent during localisation.

The limitation is that retrieval remains local and agent-directed. Breadth-first traversal explores a neighbourhood around the selected seed entities, so the result depends on where the search begins, which relation types are followed, and how far the traversal is allowed to expand. This improves structural navigation, but it does not produce a single global ranking over all repository entities. LocAgent is therefore best understood as a strong graph-guided localisation framework, not as a deterministic repository-wide ranking method.

\subsection{CodexGraph: LLM-Generated Graph Queries}
\label{sec:codexgraph}

CodexGraph~\cite{liu2024codexgraph} takes a more expressive approach by storing the repository in a graph database and allowing an LLM agent to query that database. The repository is extracted through static analysis into a task-agnostic schema whose nodes include modules, classes, and functions, while edges represent relations such as \texttt{CONTAINS}, \texttt{INHERITS}, and \texttt{USES}.

The key design difference is that CodexGraph does not rely on a fixed graph traversal rule. Instead, a primary LLM interprets the user's coding question, formulates natural-language retrieval intentions, and passes them to a translation LLM that generates executable graph queries. The system then iterates: the agent inspects retrieved information, decides whether enough context has been gathered, and issues further queries if needed.

This design is useful because it makes retrieval flexible. A graph database can represent several relation types at once, and LLM-generated queries can adapt to the task instead of following a predefined neighbourhood radius. This is especially valuable when a coding question requires reasoning across classes, functions, imports, and usage relations rather than retrieving a fixed-size local context.

The cost is that retrieval becomes model-mediated. CodexGraph reports higher token consumption because query outputs can be long and difficult to control, and it notes that the system can encounter loops that prevent executable graph queries from being generated~\cite{liu2024codexgraph}. As a result, the retrieval process depends not only on the graph, but also on the LLM's ability to formulate correct queries and decide when to stop. For this thesis, CodexGraph is important because it shows the expressive power of graph-database retrieval, while also illustrating the cost of placing an LLM directly inside the retrieval loop.

\subsection{LARGER: Lexically Anchored Graph Expansion}
\label{sec:larger}

LARGER~\cite{hu2026larger} proposes a more agent-compatible hybrid between lexical search and graph retrieval. Its starting point is that coding agents already rely heavily on lexical search, but lexical search often misses structural relations such as imports, call chains, type hierarchies, and code-test links. LARGER therefore treats lexical matches as structural entry points: it aligns lexical search results to graph anchors, then exposes confidence-filtered local neighbourhoods around those anchors within the agent's existing search loop.

This design is stronger than raw ego-graph expansion because it does not expose graph structure as a separate retrieval stage. Instead, graph evidence is delivered inside the same observation channel already used by the agent. The system maintains an active set of plausible anchor nodes and performs local expansion only around those nodes, avoiding blind traversal over the full repository graph~\cite{hu2026larger}.

The empirical results make LARGER a strong recent baseline. Across localisation, test generation, and codebase question-answering benchmarks, LARGER reports improvements of up to 13.9 points in Acc@5 and 12.2 points in Recall@5 over strong baselines~\cite{hu2026larger}. It also reports consistent gains on LocBench, MuLocBench, SWE-Atlas Test Writing, and SWE-Atlas Codebase QA~\cite{hu2026larger}.

Even so, LARGER remains a local-expansion method. Its retrieval process is organized around lexical anchors and confidence-filtered neighbourhoods, not around a repository-wide propagation or ranking objective. This makes it practical and effective for agent integration, but it still leaves open the question that motivates this thesis: how to transform lexical seeds into a deterministic, globally ranked structural result that can be truncated directly to top-$k$ under a fixed context budget.

\subsection{Ranked structural retrieval under a fixed context budget}

Modern LLM agents operate under a hard token budget. For retrieval to be useful in this setting, it must produce a ranked output that can be truncated at top-$k$ while still preserving the relevant item. Sparse and dense methods already return ranked lists, but they do not model repository structure. Graph-based methods model structure, yet the surveyed systems still fail to provide a cheap global ranking: RepoGraph relies on unranked $k$-hop expansion, LARGER depends on lexically anchored local expansion without repository-wide ranking, and CodexGraph places query generation inside an LLM-mediated loop.

The first gap is therefore not the absence of graph structure itself. The missing capability is a retrieval method that is structure-aware, globally ranked, and cheap enough to serve as a first-stage retrieval step for repository-scale LLM agents.

\subsection{Lexical, semantic, and structural signals are still treated separately}

Existing retrieval families remain centred on one dominant signal at a time. Sparse methods prioritise token overlap, dense methods prioritise embedding similarity, and graph-based methods prioritise structural connectivity. In real repository tasks, however, these signals interact. Issue descriptions are written in natural language, identifiers carry semantic information, and the file that must be modified is often structurally connected to the initial seed even when lexical overlap is weak.

The literature does combine these signals, but mostly in serial stages rather than through a unified relevance function. LocAgent~\cite{chen2025locagent}, for example, combines graph traversal with BM25-based rescoring, yet the signals are still applied as separate operations rather than as one integrated ranking model.

The second gap is therefore a modelling gap. The literature still lacks a principled way to let lexical, semantic, and structural evidence influence retrieval jointly rather than one signal merely filtering or rescoring another.

\subsection{Determinism and cost inside the retrieval loop}

Retrieval is not only a relevance problem. It is also a systems problem. If retrieval is slow, expensive, or non-deterministic, it becomes difficult to use in interactive tools and difficult to evaluate scientifically. CodexGraph~\cite{liu2024codexgraph} makes this trade-off especially visible because it places an LLM directly inside the retrieval loop, so each retrieval step inherits model latency, monetary cost, and non-determinism.

This matters for at least three reasons. Interactive systems require fast responses, evaluation requires reproducibility, and debugging requires failures that can be traced to a stable computation rather than to a sampled model output. The surveyed literature rarely treats determinism as a primary design requirement, yet for repository retrieval it is a practical constraint rather than a secondary optimization.

\subsection{Evaluation on end-to-end repository tasks}

A final gap concerns evaluation. LARGER~\cite{hu2026larger} reports gains on localisation and codebase QA benchmarks, and LocAgent~\cite{chen2025locagent} reports file-level localisation accuracy. These metrics are useful, but they evaluate a single stage of a broader software-engineering pipeline rather than the full repository-level task.

Benchmarks such as SWE-bench~\cite{yang2024swebench} measure whether an agent can resolve a real issue end to end, where retrieval is only one component of final performance. The literature still leaves open an important empirical question: whether better structural retrieval consistently improves results on realistic repository-scale engineering tasks rather than only on intermediate surrogate metrics.

Together, these four gaps define the requirements that motivate the design of CodeGraph in \Cref{ch:design}.
