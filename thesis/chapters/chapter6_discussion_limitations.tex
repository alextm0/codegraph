\chapter{Discussion and Limitations}
\label{ch:discussion}

The results presented in \cref{ch:evaluation} established that CodeGraph provides a performance gain over standard lexical baselines. 
 However, the metrics alone do not fully capture the qualitative lessons learned during the system's development. This chapter interprets what these results tell us about the nature of graph-based retrieval, discusses the implications for AI coding agents, and identifies the practical boundaries that limit the system's generalizability.

% =============================================================================
\section{Interpretation of Results}
\label{sec:interpretation}
% =============================================================================

CodeGraph's main result is that better Seed Extraction makes graph-based retrieval more effective. The challenge is to translate abstract natural language symptoms into precise starting nodes in a code graph. The performance trajectory in \cref{ch:evaluation} shows which changes improved that translation.

\subsection{Seed Quality as the Dominant Bottleneck}
The evaluation shows that seed quality, not algorithm tuning, is the primary bottleneck in CodeGraph. The most impactful performance jump, rising from 42.0\% to the final 74.0\% Recall@10, was driven by refinements to the seed extraction process, such as compound tokenization and inverse-frequency weighting. Our observation of a bimodal distribution in the results further supports this: when the seeds land near the correct region, the structural propagation stage almost always pushes the target file into the top ranks. This suggests that the retrieval ceiling is set by the reachability of the target from the initial seeds, rather than by the finesse of the ranking algorithm.

\subsection{PPR as Signal Amplification}
Personalized PageRank behaves like a filter that boosts consistent structural signals and suppresses noise from misleading seeds. Our finding that uniform restart outperforms weighted restart confirms that the graph topology itself is often more reliable than the raw BM25 scores of individual seeds. By treating all seeds equally, we allow the graph's connectivity to decide which starting points are most likely to be relevant. PPR effectively amplifies the regions where multiple independent signals converge, while diluting the influence of outlier seeds that have no structural support in the codebase.

\subsection{When Graph Structure Helps}
The effectiveness of CodeGraph is tied to both the style of the bug report and the organization of the repository. The system is strongest when bug descriptions name specific functions or modules, providing clear lexical anchors. Structurally, it performs best in repositories with clear module boundaries and cohesive directories. It is weakest in description-impoverished cases where symptoms are abstract (e.g., the app crashes), or in repositories with large, heterogeneous directories where many unrelated files share a similar vocabulary. These failures, categorized as semantic gaps, indicate where pure lexical-structural retrieval reaches its limit.

\section{Implications for AI Coding Agents}
\label{sec:implications}
% =============================================================================

The retrieval rate achieved by the system changes where an AI coding agent spends its effort. When CodeGraph places the target file near the top of the result list, the agent can use more of its context window to understand the bug and write the fix. The search problem does not disappear, but it becomes a smaller part of the task.

Deterministic graph navigation also reduces a common failure mode in agent workflows: guessing file locations that do not exist or following relationships that are only implied by language. Through MCP, the agent receives paths, entities, and relationships extracted from the repository itself. This does not make the agent's reasoning deterministic, but it gives the reasoning step a concrete substrate: files that exist, edges that were parsed, and scores that can be inspected.

\section{Technical Boundaries and Generalizability}
\label{sec:technical-limitations}
% =============================================================================

CodeGraph's results depend on assumptions that do not hold for every repository. This section separates limitations of the static graph from limitations of the evaluation protocol.

\paragraph{Static Analysis Boundary.} 
CodeGraph cannot see dynamic behaviors like runtime module loading or monkey-patching. These dynamic patterns create missing edges in the static graph, contributing to connectivity gaps where a target file is structurally isolated from its seeds. Without runtime signals, the graph remains an incomplete map of the program's actual execution flow.

\paragraph{Ecosystem and Language Scope.} 
The current system is Python-specific. Adapting it to other languages would require targeted investment in new parsers and resolution logic. Furthermore, the evaluation used SWE-bench Lite, which consists of popular, well-structured open-source projects. The performance of CodeGraph on proprietary or legacy codebases, which may feature poorer naming conventions, more dynamic patterns, or monolithic directories with weak boundaries, might be lower than what we observed in this benchmark.

\paragraph{Metric Proxies.}
The use of Recall@10 assumes that retrieving the correct file is equivalent to solving the retrieval portion of the task. While this is a standard proxy, it does not measure whether the agent can correctly interpret the file or if the bug requires edits across many files that are not as easily ranked. We also evaluate only the first retrieval step, which does not capture the human-like iterative pattern of an agent exploring a repository over multiple turns.

\paragraph{Scalability.} 
PPR is efficient at the scale of the SWE-bench repositories evaluated in this thesis, but million-node graphs and continuous updates remain open engineering problems. Interactive use also requires the graph to stay fresh while an agent or developer edits files, which is harder than rebuilding a static snapshot.
