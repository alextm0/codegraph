\chapter{Evaluation and Results}
\label{ch:evaluation}

This chapter evaluates CodeGraph's effectiveness in locating relevant source files for real-world software bugs using only natural-language issue descriptions. By testing the system against 300 instances from the widely recognized SWE-bench Lite dataset, we establish a rigorous standard to prove CodeGraph's efficiency. Using this common industry benchmark allows us to measure how well our graph-based architecture performs compared to traditional text-based retrieval methods.

Our evaluation shows that the optimal CodeGraph configuration achieves a 74.0\% Recall@10 rate, marking a 32 percentage point improvement over the initial baseline. Throughout this chapter, we analyze the specific design choices that drove this improvement: diagnosing the core challenge of reachability, demonstrating how precise seed extraction bridges the gap between natural language and code, and defining the boundaries of what pure graph structure can achieve.

The chapter is structured as follows:
\begin{itemize}
    \item \Cref{sec:eval-framework} details the testing environment, the SWE-bench dataset, and the evaluation metrics.
    \item \Cref{sec:eval-trajectory} maps the performance improvements across different system iterations.
    \item \Cref{sec:eval-diagnostics} explores the reachability bottleneck that informed our architectural focus.
    \item \Cref{sec:eval-seeds} and \cref{sec:eval-ablations} examine the specific engineering refinements and structural validation of the system.
    \item \Cref{sec:eval-synthesis} concludes with an analysis of CodeGraph's strengths and its current boundaries.
\end{itemize}

% ============================================================
\section{Evaluation Framework}
\label{sec:eval-framework}
% ============================================================

We use the SWE-bench Lite benchmark, which consists of 300 real GitHub issues paired with their repositories and human-written fixes. For each issue, CodeGraph receives only the issue text and the repository, and must rank source files by relevance. We then measure how often the target file appears in the top-k positions of this ranking.

% ------------------------------------------------------------
\subsection{The SWE-bench Lite Benchmark}
\label{sec:eval-swebench}
% ------------------------------------------------------------

SWE-bench Lite is a curated subset of 300 issues from SWE-bench, covering 12 popular Python projects such as Django, SymPy, and scikit-learn. Each instance contains three pieces of information:
\begin{enumerate}
    \item The original issue text as written on GitHub.
    \item A snapshot of the repository at the commit before the fix.
    \item The human-written patch that was merged to resolve the issue.
\end{enumerate}

This benchmark is well-suited for evaluating retrieval systems. The issues describe realistic bugs and feature requests, the repositories are large and heterogeneous, and the gold patch tells us exactly which file or files the agent needed to touch. The evaluation harness automates the process of graph construction, retrieval, and metric calculation across the full dataset. \subsection{Metrics and Protocol}
\label{sec:eval-metrics}
% ------------------------------------------------------------

We evaluate retrieval at the file level. For each issue, we identify the primary file modified in the gold patch and treat it as the target. We report three metrics:

\begin{itemize}
    \item \textbf{Recall@$k$ (R@$k$):} Fraction of issues where the target file appears in the top-$k$ results. R@10 is our main metric, because most agents can only inspect 5--20 files per task.
    \item \textbf{Mean Reciprocal Rank (MRR):} The average of $1 / \text{rank}$ for the target file, which penalizes systems that consistently rank the correct file near the bottom of the list.
    \item \textbf{Zero-recall count:} Number of issues where the target file does not appear in the top-10 results at all. This highlights complete failures of reachability, not just ranking quality.
\end{itemize}

The evaluation protocol simulates a realistic agent loop. For each SWE-bench Lite issue, the harness loads or builds the code graph, runs CodeGraph retrieval using only the issue text as input, and compares the ranked file list against the target file from the patch (illustrated in \cref{fig:eval-pipeline}).

\subsection{Baselines}
\label{sec:eval-baselines}
% ------------------------------------------------------------

We compare CodeGraph against three baselines:
\begin{itemize}
    \item \textbf{Random:} Files are ranked uniformly at random. This establishes the performance floor.
    \item \textbf{BM25-only:} A sparse lexical retriever over the same entity corpus used for seeds. This isolates the added value of graph-based ranking over pure text similarity.
    \item \textbf{One-hop ego graph:} An unranked structural baseline that returns all neighbours within one hop of the seed nodes. This tests whether graph structure without ranking is sufficient.
\end{itemize}

All baselines run on the same SWE-bench Lite instances and repositories as CodeGraph, under the same evaluation protocol.

\section{The Path to 74\% Retrieval Accuracy}
\label{sec:eval-trajectory}
% ============================================================

\Cref{tab:trajectory-results} summarizes how CodeGraph's retrieval accuracy improved over several iterations. We start from a weighted-restart configuration that achieves 42.0\% R@10, compared to 49.7\% for BM25 alone. Switching to uniform PPR restart immediately lifts R@10 to 60.7\%, showing that the graph can correct noisy seeds if it is not over-weighted towards ambiguous identifiers. Refining seed extraction through compound tokenization, an expanded BM25 corpus, and inverse-frequency weighting pushes R@10 further to 72.3\%. Finally, increasing the candidate pool from 20 to 30 files recovers a small band of instances where the gold file was ranked 21--30, bringing the overall performance to its optimal level without increasing query latency.

\section{The Discovery of Reachability}
\label{sec:eval-diagnostics}
% ============================================================

When we inspected the distribution of ranks for the target file, we found a bimodal pattern: for most issues, the target file is either in the top-5 results or not in the top-10 at all. Only 15 out of 300 instances (5\%) fall in the middle ranks (ranks 6--10). This pattern holds across configurations and repositories.

This is strong evidence that the PPR ranking step is not the primary bottleneck. Once a seed lands in the structural neighbourhood of the target file, PPR almost always pushes that file into the top-5. The dominant failure mode is reachability: if no seed lies on a path to the target, no amount of ranking can recover it. This observation motivated the seed-first improvements in \cref{sec:eval-seeds}.

\section{Systematic Seed Refinement for Enhanced Reachability}
\label{sec:eval-seeds}
% ============================================================

The diagnostic finding of the bimodal distribution established that the retrieval ceiling is set by seed quality. This section details the five systematic improvements that unlocked the final performance gain by ensuring robust reachability.

\begin{enumerate}
    \item \textbf{Uniform PPR restart (Algorithm Alignment):} As established in \cref{sec:eval-diagnostics}, equal seed weights prevent ambiguous entity matches from dominating the random walk.
    \item \textbf{Compound Tokenization (Lexical Recovery):} Standard lexical indexing often fails to resolve compound identifiers, such as \texttt{SQLCompiler}. By decomposing these into their constituent terms (\texttt{sql} and \texttt{compiler}), the system recovers matches that would otherwise remain invisible to the lexical index.
    \item \textbf{Expanded BM25 Corpus (Contextual Scope):} Indexing file paths, class names, and qualified method names alongside docstrings allowed natural-language queries to resolve to structural entities more reliably.
    \item \textbf{Inverse-Frequency Entity Weighting (Noise Reduction):} Penalizing common names like \texttt{update} or \texttt{save} ensured that high-frequency identifiers did not overwhelm the personalization vector.
    \item \textbf{Candidate Budget Optimization ($k=30$):} Increasing the returned candidate count from 20 to 30 accounted for instances where PPR correctly identified the target neighbourhood but ranked the gold file just outside the top-20.
\end{enumerate}

These refinements represent a targeted engineering effort to bridge the gap between natural language symptoms and structured source code. The effectiveness of this Seed-First approach is further validated when compared against alternative structural augmentations.

\section{Ablation Studies and Architectural Validation}
\label{sec:eval-ablations}
% ============================================================

To isolate the contributions of individual system components and justify our final configuration, we conducted a series of ablation studies. These experiments systematically remove or modify specific features to measure their impact on retrieval performance, providing a rigorous empirical basis for the CodeGraph architecture.

% ------------------------------------------------------------
\subsection{Algorithm Selection: The Impact of Uniform Restart}
\label{sec:eval-ablation-algorithm}
% ------------------------------------------------------------

The most impactful algorithmic finding was the superiority of \emph{uniform restart} over confidence-weighted seeds. In our initial configuration (Weighted PPR), we assigned restart probabilities proportional to the BM25 confidence scores of the retrieved seeds. This achieved only 42.0\% R@10.

By switching to a uniform restart distribution (60.7\% R@10), we allowed the graph topology to naturally arbitrate between competing signals. This improvement proves that the graph structure is a more reliable filter for relevance than initial lexical similarity. When seeds are noisy or ambiguous, over-weighting them based on confidence scores tends to amplify false positives, whereas a uniform distribution allows the personalization mass to aggregate where the structural evidence is strongest.

% ------------------------------------------------------------
\subsection{Hyperparameter Tuning: Budget and Damping}
\label{sec:eval-ablation-tuning}
% ------------------------------------------------------------

We performed extensive sweeps over the candidate budget $k$ and the PPR damping factor $\alpha$ to ensure the stability of the system.

\begin{itemize}
    \item \textbf{Candidate Budget ($k$):} Increasing the returned candidate pool from 20 to 30 files yielded a final performance gain. This optimization recovered instances where the gold file was structurally proximate to the seeds but ranked just outside the top-20 tier due to the high density of related files in certain modules.
    \item \textbf{Damping Factor ($\alpha$):} We tested values ranging from 0.10 to 0.85. While the system remained robust across a wide band, we found that higher values (e.g., $\alpha=0.70$) maintained strong performance without the over-spreading issues seen with very low damping. This confirmed that the CodeGraph architecture successfully balances local seed relevance with global structural context.
\end{itemize}

% ------------------------------------------------------------
\subsection{Structural Frontier: Validation via Co-location}
\label{sec:eval-ablation-structural}
% ------------------------------------------------------------

To test the limits of the graph schema, we explored augmenting the structure with \texttt{CO\_LOCATED} edges between sibling files in the same directory. Surprisingly, this resulted in a slight regression ($-1.0$pp).

Qualitative analysis revealed a probability dilution effect: in large, heterogeneous directories like \texttt{django/\allowbreak db/\allowbreak models/}, the new edges created a dense subgraph that caused PPR mass to dissipate across semantically unrelated neighbours. This finding serves as a critical architectural validation: it confirms that CodeGraph's strength lies in its seed-driven precision and dependency-based paths, rather than naive structural density. Our final configuration therefore prioritizes high-fidelity seed extraction over artificial graph expansion.

\section{Qualitative Synthesis and Structural Limits}
\label{sec:eval-synthesis}
% ============================================================

The quantitative success of CodeGraph is deeply tied to the structural characteristics of the underlying repositories. This section synthesizes the per-repository performance and the failure taxonomy to define the structural limit of graph-based retrieval.

\paragraph{Codebase Structure and Retrieval Success.}
As shown in \cref{tab:per-repo}, performance varies across repositories. The system achieves near-perfect recall on scikit-learn (9\% failure rate) and matplotlib (13\%). These repositories feature distinct subpackages with clear, non-overlapping domains, allowing BM25 to identify precise seeds and PPR to amplify them within cohesive module clusters.

In contrast, Django (27\% failure) and SymPy (31\%) present a greater challenge due to large, functionally heterogeneous directories. When a directory like \texttt{django/\allowbreak db/\allowbreak models/} contains over 25 files spanning distinct ORM and migration logic, seeds may land in the correct directory but the wrong file. Without explicit dependency edges between sibling files, probability does not propagate to the target, resulting in zero recall.

\noindent An analysis of the 78 zero-recall instances identifies two primary failure modes:

\begin{itemize}
    \item \textbf{Connectivity Gaps (40 instances):} These occur when seeds land in the correct directory, but the target file remains structurally isolated from them. Without an explicit dependency path, such as an import or function call, Personalized PageRank cannot propagate relevance to the target. This finding suggests that graph-based retrieval is limited by the inherent modularity and connectivity of the codebase.
    \item \textbf{Semantic Gaps (38 instances):} These failures arise when a bug report describes symptoms using abstract natural language that does not overlap with the lexical identifiers in the source code. In these cases, the lexical index fails to identify any relevant seeds, preventing the graph-based engine from starting in the correct neighborhood. Bridging this gap requires semantic reasoning or dense embeddings to connect natural language descriptions to code entities.
\end{itemize}

\paragraph{Conclusion:}
These failure modes define the structural limit of the CodeGraph approach. While highly effective for navigating explicitly connected components, the system is bounded by the precision of initial lexical matching and the density of the dependency graph. Future integration of dense retrieval methods, as discussed in \cref{ch:conclusion}, may address these remaining gaps.
