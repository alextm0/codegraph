\chapter{Implementation}
\label{ch:implementation}

\Cref{ch:design} described what CodeGraph does and why each design decision was made. This chapter describes how. Where Chapter~3 stated ``entity names are extracted from task descriptions using lexical patterns,'' this chapter shows the six regular expressions that make that extraction precise. Where Chapter~3 stated ``import resolution maps module paths to file paths,'' this chapter presents the progressive segment-stripping algorithm that handles the ambiguity of Python's package hierarchy. The boundary between the two chapters follows a simple rule: if a reader who has absorbed Chapter~3 could have guessed the implementation detail, it belongs there; if only reading the code would reveal it, it belongs here.

Chapter~4 also serves as the bridge to \cref{ch:evaluation}. The evaluation harness, ablation framework, and metric computation described in \cref{sec:eval-harness} are the mechanical prerequisites for interpreting the results in Chapter~5.

The chapter is organized as follows. \Cref{sec:project-structure} surveys the codebase layout and technology choices. \Cref{sec:parser-impl} covers the three non-obvious aspects of the parser. \Cref{sec:graph-impl} examines graph construction and name resolution in depth. \Cref{sec:pipeline-orchestration} describes the retrieval pipeline sequencing. \Cref{sec:ppr-impl} shows the GDS API specifics for PPR execution. \Cref{sec:mcp-impl} describes the MCP server integration. \Cref{sec:cli-impl} briefly covers the command-line interface. \Cref{sec:eval-harness} presents the evaluation harness. \Cref{sec:impl-summary} closes with a summary.

Each technology choice in \cref{tab:module-map} follows from a specific design requirement identified in \cref{ch:design}:

\begin{itemize}
    \item \textbf{tree-sitter.} \Cref{sec:parsing} requires error-tolerant parsing of partial files---a prerequisite when indexing real-world repositories that often contain Python~2 syntax, work-in-progress files, or other constructs that cause Python's built-in \texttt{ast} module to raise \texttt{SyntaxError} and abort. tree-sitter produces a concrete syntax tree regardless of syntax errors, allowing incomplete files to contribute partial entity information.

    \item \textbf{Neo4j + GDS.} The graph operations in \cref{sec:ppr-config} require both a persistent property graph (for MERGE-based idempotent writes and Cypher queries) and native PPR execution. The Neo4j Graph Data Science (GDS) library projects the persistent graph into an in-memory representation optimized for sparse matrix operations, enabling PPR convergence in 150--200\,ms on repositories with tens of thousands of nodes.

    \item \textbf{FastMCP.} The MCP server described in \cref{sec:mcp-integration} must support the STDIO transport that Claude Desktop and Claude Code expect from local tool servers. FastMCP is the official Anthropic-maintained Python SDK for building MCP servers, providing the \texttt{@mcp.tool()} decorator, lifespan management, and STDIO transport with a minimal API.

    \item \textbf{rank-bm25.} Seed selection (\cref{sec:seed-selection}) requires a lexical similarity signal that operates without an embedding model. BM25 runs on CPU, requires no GPU, has no network dependency, and completes index construction in under one second for typical repository sizes. This keeps the full pipeline self-contained and installable via a single \texttt{pip install}.

    \item \textbf{tiktoken.} The token-budget enforcement in \cref{sec:post-processing} requires accurate token counting. tiktoken's \texttt{cl100k\_base} encoding (used by GPT-4 and Claude) produces counts accurate to within 1\% for typical Python source code, with negligible latency overhead.
\end{itemize}

\section{Parser Implementation}
\label{sec:parser-impl}

The parser's job is to transform raw source files into typed \texttt{FileEntities} records---frozen dataclasses carrying lists of \texttt{FunctionEntity}, \texttt{ClassEntity}, \texttt{MethodEntity}, \texttt{ImportEntity}, and \texttt{CallEntity} objects. \Cref{ch:design} described the design rationale. This section covers three non-obvious implementation aspects that the design description does not capture.

\subsection{Decorated-Definition Unwrapping}
\label{subsec:decorated-defs}

Python decorators pose a parsing challenge. When a function is decorated, tree-sitter wraps it in a \texttt{decorated\_definition} node whose children are the decorator list and the actual \texttt{function\_definition} node. A naive walk that checks \texttt{node.type == "function\_definition"} misses all decorated functions. The same problem affects classes: \texttt{@dataclass} and \texttt{@classmethod} decorators are common in modern Python.

The extractor pattern handles this with a two-step check at each child node:

\begin{lstlisting}[style=pseudostyle, caption={Decorated-definition unwrapping pattern (simplified from \texttt{extractors.py}). All five extractors (functions, classes, methods, imports, calls) apply the same pattern.}, label={lst:decorated-def}]
for node in root.children:
    actual = node
    if node.type == "decorated_definition":
        # Unwrap: find the first function_definition or
        # class_definition child of the decorator wrapper.
        for child in node.children:
            if child.type in ("function_definition",
                              "class_definition"):
                actual = child
                break
        else:
            continue          # Skip unknown decorated forms.
    if actual.type != "function_definition":
        continue
    # ... extract name, signature, docstring from actual ...
\end{lstlisting}

The pattern appears identically in \texttt{extract\_functions}, \texttt{extract\_classes}, \texttt{extract\_methods}, and in the method-level inner loop. Keeping the unwrapping logic explicit at each call site, rather than extracting it into a helper, keeps each extractor self-contained and readable in isolation.

\subsection{Entity Name Extraction from Free-Form Text}
\label{subsec:entity-names}

The seed selection stage (Section~3.4) requires a function that can extract likely code identifiers from a natural language task description. The challenge is precision: a generic word tokenizer returns thousands of tokens, most of which do not match any graph node; but a tokenizer that is too conservative misses identifiers and degrades seed quality.

\texttt{extract\_entity\_names()} applies six regular expressions to the input text, each targeting a syntactically distinct class of Python identifier:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The six regex patterns in \texttt{extract\_entity\_names()} (\texttt{seed\_selection.py:153--166}). Each pattern targets a distinct identifier class. The patterns are applied in priority order; duplicates are removed with first-occurrence semantics.}, label={lst:regex-patterns}]
# Multi-segment CamelCase: "AuthService", "BlogPost"
camel_multi  = re.findall(r"\b[A-Z][a-z]+(?:[A-Z][a-z]+)+\b", text)

# Single-word CamelCase with internal uppercase: "QuerySet", "HTMLParser"
# Requires a lowercase->uppercase transition to exclude plain English words.
camel_single = re.findall(r"\b[A-Z][a-z]+[A-Z]\w+\b", text)

# All-caps prefix + title-case word: "SQLCompiler", "HTTPSConnection"
camel_allcaps= re.findall(r"\b[A-Z]{2,}[A-Z][a-z]\w*\b", text)

# snake_case: at least one underscore separating lowercase segments
snake        = re.findall(r"\b[a-z][a-z0-9]*(?:_[a-z][a-z0-9]*)+\b", text)

# Backtick-quoted identifiers (common in GitHub issue descriptions)
backtick     = re.findall(r"`([A-Za-z_][A-Za-z0-9_.]+)`", text)

# Dotted module paths: "models.queryset", "sql.compiler" (2--5 lowercase segments)
dotted       = re.findall(r"\b[a-z][a-z0-9]*(?:\.[a-z][a-z0-9_]*){1,4}\b", text)
\end{lstlisting}

Each pattern is designed to avoid common English words. The \texttt{camel\_single} pattern requires a lowercase-to-uppercase transition (\texttt{[A-Z][a-z]+[A-Z]}) rather than just \texttt{[A-Z][a-z]+}, which would match ordinary capitalized words like ``Fix'' or ``The.'' The \texttt{snake} pattern requires at least one underscore, which excludes single lowercase words. The \texttt{backtick} pattern exploits the convention in GitHub issue descriptions of quoting code identifiers in backticks.

The six pattern groups feed into a deduplication loop that preserves first-occurrence order, so that higher-confidence patterns (CamelCase, which is almost never ordinary English) take priority over lower-confidence ones (dotted paths, which occasionally match non-code text like ``e.g.'').

\texttt{extract\_entity\_names()} runs automatically on every pipeline invocation---its results augment any explicit entities the caller provides---so its precision directly affects the seed distribution and, consequently, retrieval quality. \Cref{ch:evaluation} confirms that the seed quality improvements introduced alongside this function account for the largest single-iteration gain in the ablation study.

\subsection{Compound Tokenization for BM25}
\label{subsec:compound-tokenization}

Standard tokenizers treat identifiers like \texttt{SQLCompiler} or \texttt{handle\_subquery} as atomic tokens. A BM25 query for ``SQL compilation'' will not match a document containing only \texttt{SQLCompiler}, because the tokenizer never produces the constituent tokens \texttt{sql} and \texttt{compiler}. The \texttt{tokenize()} function addresses this with two substitution steps:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The \texttt{tokenize()} function (\texttt{seed\_selection.py:429--444}). CamelCase splitting uses two regex passes: the first inserts a space at every lowercase-to-uppercase boundary, the second handles consecutive uppercase runs (e.g.\ \texttt{SQLCompiler}).}, label={lst:tokenize}]
def tokenize(text: str) -> list[str]:
    # Split CamelCase: "handleSubQuery" -> "handle Sub Query"
    text = re.sub(r'([a-z0-9])([A-Z])', r'\1 \2', text)
    # Handle consecutive caps: "SQLCompiler" -> "SQL Compiler"
    text = re.sub(r'([A-Z]+)([A-Z][a-z])', r'\1 \2', text)
    # Split on all non-alphanumeric (underscores split too)
    tokens = re.split(r"[^a-z0-9]+", text.lower())
    return [tok for tok in tokens if len(tok) > 1]
\end{lstlisting}

The two-pass approach is necessary because a single \texttt{([a-z0-9])([A-Z])} substitution does not handle strings like \texttt{SQLCompiler}: the boundary is between two consecutive uppercase letters, not between a lowercase and an uppercase letter. The second pass, \texttt{([A-Z]+)([A-Z][a-z])}, catches this case by inserting a space before the last uppercase letter in a run when it is followed by a lowercase letter, producing \texttt{SQL Compiler}.

This function is applied to both the query (the task description) and to every document in the BM25 corpus (node name + file path + signature + docstring). Applying the same tokenizer to both sides is necessary for BM25 to match them: if the query produces \texttt{["sql", "compiler"]} but the document still contains \texttt{"SQLCompiler"} as a single token, no match occurs.

\section{Graph Construction and Name Resolution}
\label{sec:graph-impl}

Graph construction is the most engineering-intensive stage of the pipeline. Its output---a Neo4j property graph with four node types and four edge types---must be correct for PPR to produce meaningful results. This section describes the two-pass construction strategy, the qualified name scheme that serves as the graph's primary key, and the resolution algorithms for imports and function calls.

\subsection{Two-Pass Construction and Batched Writes}
\label{subsec:two-pass}

The \texttt{build\_graph()} function follows a two-pass strategy. Pass~1 creates all node records and CONTAINS edges within a single transaction: File, Function, Class, and Method nodes are written, together with the File$\to$Function, File$\to$Class, and Class$\to$Method containment edges. Pass~2 creates the cross-file edges---CALLS, IMPORTS, and INHERITS\_FROM---using the complete node index built in Pass~1.

The two-pass ordering is necessary because call and import resolution requires forward references. A function in \texttt{auth\_service.py} may call \texttt{hash\_password()} defined in \texttt{crypto.py}; resolving this edge requires \texttt{crypto.py}::hash\_password to exist in the graph before the CALLS edge can be written. Processing all files sequentially in a single pass would require two full traversals of the entity list regardless; the two-pass design makes this explicit and ensures that all MERGE targets exist before any MATCH-based edge creation occurs.

All writes use the \texttt{UNWIND + MERGE} pattern, never individual CREATE statements. A representative example:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={Batched Function node creation using \texttt{UNWIND + MERGE} (\texttt{graph\_builder.py:186--199}). The entire batch of Function nodes for all parsed files is written in a single Cypher transaction. \texttt{MERGE} on \texttt{qualified\_name} ensures idempotency: re-running \texttt{rebuild} updates existing nodes rather than creating duplicates.}, label={lst:unwind-merge}]
result = tx.run(
    """
    UNWIND $nodes AS n
    MERGE (f:Function {qualified_name: n.qualified_name})
    SET f.name = n.name, f.file_path = n.file_path,
        f.line_number = n.line_number, f.end_line = n.end_line,
        f.signature = n.signature, f.docstring = n.docstring
    RETURN count(f) AS created
    """,
    nodes=nodes,
)
\end{lstlisting}

A uniqueness constraint on \texttt{qualified\_name} is created by \texttt{ensure\_constraints()} before any writes. The constraint serves two purposes: it enforces the invariant that every node has a unique primary key, and it enables Neo4j to use an index lookup (O(log n)) for each \texttt{MERGE} operation rather than a full scan.

\subsection{Qualified Name Scheme}
\label{subsec:qname}

Every node in the graph is identified by a \texttt{qualified\_name} string. The scheme follows the pattern \texttt{file\_path::entity\_name}, where \texttt{file\_path} uses forward slashes and is relative to the project root, and \texttt{entity\_name} encodes the full dotted path within the file:

\begin{itemize}
    \item \textbf{File:} \texttt{src/auth/service.py}
    \item \textbf{Function:} \texttt{src/auth/service.py::authenticate}
    \item \textbf{Class:} \texttt{src/auth/service.py::AuthService}
    \item \textbf{Method:} \texttt{src/auth/service.py::AuthService.authenticate}
\end{itemize}

Three design choices in this scheme deserve explanation. First, the double-colon separator (\texttt{::}) disambiguates the file path from the entity name. Python module paths use dots (e.g.\ \texttt{auth.service}) and method names use dots (e.g.\ \texttt{AuthService.authenticate}), so a dot-only separator would be ambiguous. Second, forward slashes are normalized at write time regardless of OS, ensuring that a graph built on Windows and queried on Linux (or vice versa) uses consistent keys. Third, the full dotted path within the file, including the class prefix for methods, avoids collisions between a method \texttt{AuthService.authenticate} and a top-level function also named \texttt{authenticate} in the same file.

The \texttt{qualified\_name} is also the string used by BM25 seed lookup and the \texttt{get\_relevant\_context} MCP tool's \texttt{mentioned\_entities} parameter: a caller that passes \texttt{"AuthService.authenticate"} as an entity name is matched against the \texttt{name} property of Method nodes, not against \texttt{qualified\_name} directly, but the qualified name is what ultimately identifies the node in all downstream operations.

\subsection{Import Resolution}
\label{subsec:import-resolution}

Import resolution maps a dotted Python module path (e.g.\ \texttt{user\_auth.services.auth\_service}) to a file path in the parsed repository (e.g.\ \texttt{services/auth\_service.py}). The challenge is that Python module paths encode the package hierarchy, which may or may not match the directory hierarchy depending on how the project is structured. A path like \texttt{django.db.models.query} might correspond to \texttt{django/db/models/query.py} in a flat installation, or to \texttt{django/db/models/query.py} relative to a deep package root.

The resolution strategy is \emph{progressive segment stripping}: convert the dotted path to a file path suffix, then try progressively fewer leading segments until a match is found:

\begin{lstlisting}[style=pseudostyle, caption={Import resolution via progressive segment stripping (\texttt{resolution.py:165--194}). The algorithm tries up to \texttt{len(parts)} suffix lengths, stopping at the first match. A final fallback tries the full dotted path as a suffix.}, label={lst:import-resolution}]
function resolve_import(module_path, all_file_paths):
    parts = module_path.split(".")
    # Try stripping 1, 2, ... leading segments.
    for skip in range(1, len(parts)):
        suffix = "/".join(parts[skip:]) + ".py"
        for fp in all_file_paths:
            if fp == suffix or fp.endswith("/" + suffix):
                return fp       # First match wins.
    # Fallback: full dotted path as suffix.
    suffix = "/".join(parts) + ".py"
    for fp in all_file_paths:
        if fp == suffix or fp.endswith("/" + suffix):
            return fp
    return None                 # Unresolvable (e.g., third-party).
\end{lstlisting}

The algorithm works because Python packages are typically installed such that the last few segments of a dotted import path correspond directly to subdirectory and file names. Stripping the leading segments---which correspond to the top-level package name---recovers the relative suffix. For \texttt{user\_auth.services.auth\_service}, stripping the first segment produces \texttt{services/auth\_service.py}, which matches a known file path. The algorithm handles both absolute imports (\texttt{from django.db.models import QuerySet}) and relative imports (prefixed with dots, which are stripped before the algorithm runs).

This approach achieves an import resolution rate of approximately 80\% on the SWE-bench Lite benchmark repositories. The 20\% that fail are primarily third-party packages (e.g.\ \texttt{numpy}, \texttt{requests}) whose source files are not in the indexed directory, conditional imports guarded by try/except blocks, and dynamic imports using \texttt{importlib}.

\subsection{Call Resolution}
\label{subsec:call-resolution}

Call resolution maps a callee expression---a name like \texttt{hash\_password} or an attribute access like \texttt{obj.authenticate}---to a node \texttt{qualified\_name} in the graph. Function calls are the most common relationship in a Python codebase and the most ambiguous to resolve: a name like \texttt{save} or \texttt{get} may appear in dozens of classes, and guessing the wrong target introduces a spurious edge that misdirects PPR probability.

The resolution algorithm applies a priority chain:

\begin{lstlisting}[style=pseudostyle, caption={Call resolution priority chain (\texttt{resolution.py:80--123}). The algorithm prefers the most specific context available: an explicit import, then same-file definitions, then a globally unique name. Ambiguous cases are dropped rather than guessed.}, label={lst:call-resolution}]
function resolve_callee(callee_name, lookup, file_path, import_map):
    candidates = lookup.get(callee_name, [])
    if not candidates:
        return None             # Unknown name; not in project graph.

    # Priority 1: callee was explicitly imported in this file.
    imported_file = import_map.get(callee_name)
    if imported_file:
        for qname in candidates:
            if qname.startswith(imported_file + "::"):
                return qname

    # Priority 2: callee is defined in the same file (unambiguous).
    same_file = [q for q in candidates
                 if q.startswith(normalize(file_path) + "::")]
    if len(same_file) == 1:
        return same_file[0]
    if len(same_file) > 1:
        return None             # Multiple local definitions; skip.

    # Priority 3: exactly one candidate globally.
    if len(candidates) == 1:
        return candidates[0]

    return None                 # Globally ambiguous; skip.
\end{lstlisting}

The explicit decision to return \texttt{None} for ambiguous cases is load-bearing. An alternative strategy of picking the first candidate would introduce CALLS edges to arbitrary nodes for common method names, directing PPR probability away from the correct region. The cost of the conservative strategy is lower call resolution coverage (approximately 60--80\% depending on the repository); the benefit is that the edges that are created are reliable.

Two additional mechanisms complement the priority chain. First, Python built-in names are filtered out before resolution using a frozen set built from \texttt{dir(builtins)}:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The \texttt{\_PYTHON\_BUILTINS} frozenset (\texttt{resolution.py:25}). Built at module import time and never mutated. All names exported by Python's \texttt{builtins} module---built-in functions (\texttt{len}, \texttt{print}, \texttt{range}), built-in types (\texttt{list}, \texttt{dict}, \texttt{int}), exceptions (\texttt{ValueError}, \texttt{TypeError}), and constants (\texttt{True}, \texttt{None})---are excluded from CALLS edge creation.}, label={lst:builtins}]
_PYTHON_BUILTINS: frozenset[str] = frozenset(dir(builtins))
\end{lstlisting}

Second, dotted callee expressions like \texttt{self.validate} or \texttt{obj.method} skip the built-in filter (dotted names are never built-ins) but still apply the same priority chain, using only the method name component as the lookup key.

These numbers characterize the implementation's capability, not the evaluation metric---unresolved edges are simply absent from the graph, and the system works with whatever edges are present.

\section{Retrieval Pipeline Orchestration}
\label{sec:pipeline-orchestration}

The retrieval pipeline is a thin orchestrator: \texttt{run\_retrieval\_pipeline()} in \texttt{pipeline.py} sequences four function calls---seed extraction, IDF reweighting, GDS projection, PPR---without implementing any logic itself. All logic lives in the four packages it delegates to. This section describes the sequencing decisions that are not obvious from the function signatures alone.

\subsection{Per-Call IDF Reweighting and Projection Refresh}
\label{subsec:per-call-idf}

\texttt{ensure\_graph\_ready()} is called at the start of every retrieval invocation. It performs two operations in sequence: reapply IDF weights to all edges in Neo4j, then drop and recreate the GDS in-memory projection. Both steps are unconditional.

The motivation is consistency. IDF weights are computed from the graph's current in-degree distribution. If a repository is re-indexed (\texttt{codegraph rebuild}) between two retrieval calls, the in-degree distribution changes, and any cached GDS projection would be stale. Rather than track whether the graph has changed---which would require a versioning mechanism---the implementation adopts the simpler invariant: the GDS projection is always freshly computed from the current Neo4j state. The cost is approximately 50\,ms per call (dominated by the GDS projection creation), which is acceptable given that the total retrieval latency is under 250\,ms.

\subsection{IDF Weight Computation in Cypher}
\label{subsec:idf-cypher}

The IDF weight formula---$w = 1 / \log_2(\text{in\_degree} + 2)$---is applied as a single Cypher query that updates all edges in one pass:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The IDF edge-weight Cypher query (\texttt{post\_processing.py:65--74}). A single query aggregates the in-degree for each target node, then updates the \texttt{weight} property of every incoming edge. Neo4j's \texttt{log()} function is natural log; division by \texttt{log(2.0)} converts to $\log_2$.}, label={lst:idf-cypher}]
result = session.run(
    """
    MATCH (target)
    WITH target, COUNT { (()-[]->(target)) } AS in_deg
    MATCH (src)-[r]->(target)
    SET r.weight = 1.0 / (log(toFloat(in_deg) + 2.0) / log(2.0))
    RETURN count(r) AS updated
    """
)
\end{lstlisting}

Computing IDF directly in Cypher rather than pulling all edges into Python and updating them individually avoids a round-trip of potentially hundreds of thousands of edges. Neo4j executes the aggregation and update as a single server-side operation.

The \texttt{+~2} term in the denominator prevents division by zero for isolated nodes (in-degree~0) and ensures that even singleton nodes receive a finite, non-unit weight ($\log_2(2) = 1$, so the minimum weight is $1 / 1 = 1.0$). Nodes with in-degree~1 receive weight $1 / \log_2(3) \approx 0.63$; nodes with in-degree~10 receive weight $1 / \log_2(12) \approx 0.28$; and hub nodes with in-degree~100 receive weight $1 / \log_2(102) \approx 0.15$.

\subsection{BM25 Index Lifecycle}
\label{subsec:bm25-lifecycle}

The BM25 index is built by \texttt{prepare\_bm25\_index()}, which fetches all searchable nodes (Function, Method, Class, File) from Neo4j and constructs a \texttt{BM25Okapi} object. Building the index takes 100--500\,ms depending on repository size and is the dominant latency component of seed selection.

During MCP server operation, the index is rebuilt on every call, which is acceptable for interactive use (one call every several seconds at most). During the evaluation harness, which processes 300 instances sharing the same graph for a given \texttt{(repo, base\_commit)} group, the index is built once per group and passed as a pre-built \texttt{bm25\_index} argument to \texttt{extract\_seeds()}. For a typical group of 10--15 instances, this reuse provides a 10--15$\times$ speedup for the seed selection step.

\subsection{Auto-Entity Augmentation}
\label{subsec:auto-entity}

Every call to \texttt{run\_retrieval\_pipeline()} automatically extracts entity names from the task description using \texttt{extract\_entity\_names()} (described in \cref{subsec:entity-names}). The extracted names are merged with any \texttt{mentioned\_entities} passed by the caller, with deduplication:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={Auto-entity augmentation in \texttt{run\_retrieval\_pipeline()} (\texttt{pipeline.py:51--55}). Automatically extracted names augment caller-supplied entities, ensuring that identifiers in the task text are always searched even when the caller does not pass \texttt{mentioned\_entities}.}, label={lst:auto-entity}]
auto_entities = extract_entity_names(task_description)
existing = set(mentioned_entities or [])
augmented_entities = list(mentioned_entities or []) + [
    e for e in auto_entities if e not in existing
]
\end{lstlisting}

The augmentation runs unconditionally. An MCP tool caller that passes \texttt{mentioned\_entities=["QuerySet"]} will also benefit from entity names like \texttt{SQLCompiler} extracted automatically from the task description. Caller-supplied entities take priority (they appear first in \texttt{augmented\_entities}) and are matched with full entity-match weight; auto-extracted names appear after them and are subject to the same entity-match scoring.

\section{PPR Execution via Neo4j GDS}
\label{sec:ppr-impl}

\Cref{sec:ppr-config} described the mathematical role of Personalized PageRank and the rationale for the damping factor and top-$k$ parameters. This section covers the GDS API specifics that the mathematical description leaves open.

\subsection{Graph Projection}
\label{subsec:gds-projection}

Before PPR can run, the Neo4j graph must be projected into an in-memory GDS representation. The \texttt{project\_graph()} function creates this projection:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={GDS graph projection (\texttt{ppr.py:96--106}). All four node labels and four relationship types are included. Orientation is \texttt{UNDIRECTED} so PPR can follow edges in both directions. The \texttt{weight} property is exposed to GDS as the edge weight for the \texttt{relationshipWeightProperty} parameter in PPR.}, label={lst:gds-projection}]
node_spec = ["File", "Function", "Class", "Method"]
relationship_spec = {
    rel_type: {
        "orientation": orientation,   # "UNDIRECTED" by default
        "properties": "weight"
    }
    for rel_type in relationship_types
}
create_result = gds.graph.project(
    _PROJECTION_NAME, node_spec, relationship_spec
)
projection = create_result.graph
\end{lstlisting}

The \texttt{UNDIRECTED} orientation is the single most important algorithmic choice in the GDS integration. PPR on a directed graph cannot propagate probability against an edge's direction, so a seed in a callee function would never reach its callers---which are often the most relevant context for a bug fix. An undirected projection treats every relationship as bidirectional: a CALLS edge from \texttt{auth\_service.py::authenticate} to \texttt{crypto.py::hash\_password} allows probability to flow in both directions, connecting callers and callees symmetrically.

\subsection{Uniform PPR Mode}
\label{subsec:uniform-ppr}

The default retrieval mode, \texttt{"uniform"}, runs a single \texttt{gds.pageRank.stream()} call with all seed node IDs supplied via the \texttt{sourceNodes} parameter:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={Uniform PPR execution (\texttt{ppr.py:232--243}). GDS handles the personalization internally when \texttt{sourceNodes} is provided: it distributes the restart probability uniformly across the listed nodes. The result is a pandas DataFrame sorted by \texttt{nodeId}.}, label={lst:ppr-stream}]
result_df = gds.pageRank.stream(
    projection,
    maxIterations=config.max_iterations,       # 20
    dampingFactor=config.damping_factor,        # 0.70
    tolerance=config.tolerance,                 # 1e-7
    sourceNodes=list(seed_weights.keys()),      # Neo4j internal IDs
    relationshipWeightProperty="weight",
)
top_rows = (result_df
    .sort_values("score", ascending=False)
    .head(config.top_k))
\end{lstlisting}

The \texttt{sourceNodes} parameter triggers the personalized variant of PageRank in GDS: instead of distributing restart probability uniformly across all nodes (standard PageRank), GDS concentrates restart probability on the listed source nodes. When \texttt{sourceNodes} contains multiple IDs, GDS distributes the restart probability uniformly across them---this is the ``uniform'' interpretation.

\subsection{Weighted PPR Mode and the GDS~2.x Workaround}
\label{subsec:weighted-ppr}

The \texttt{"weighted"} retrieval mode (retained as an ablation baseline) requires non-uniform personalization: seeds with higher signal weights should receive proportionally more restart probability. The natural implementation---passing seed weights directly to the GDS \texttt{personalizationProperty}---was not possible in GDS~2.x, which dropped support for this parameter in a minor version update without deprecation warnings.

The implementation works around this by exploiting the mathematical linearity of PPR. Because PPR is linear in the personalization vector, a weighted sum of per-seed PPR results is exactly equal to the single PPR run with a weighted personalization vector:

\[
    \text{PPR}_{\text{weighted}} = \sum_{i} w_i \cdot \text{PPR}(\text{seed}_i)
\]

The \texttt{run\_ppr\_weighted()} function runs \texttt{gds.pageRank.stream()} once per seed with \texttt{sourceNodes=[seed\_id]}, collects the resulting score dictionaries, and combines them with the appropriate weights. For a typical seed set of 3--6 nodes, this approach issues 3--6 GDS calls rather than one, adding approximately 50\,ms to the total retrieval latency---an acceptable overhead for an ablation study mode. The uniform mode is the production default precisely because it achieves the same result as an equal-weight personalization vector in a single GDS call.

\section{MCP Server Integration}
\label{sec:mcp-impl}

The MCP server in \texttt{src/codegraph/mcp/} exposes the retrieval pipeline to AI agents as a set of callable tools. This section describes the server lifecycle, the tool registration pattern, and the configuration resolution chain.

\subsection{FastMCP Lifespan Pattern}
\label{subsec:lifespan}

The Neo4j driver and GDS client are long-lived resources: they maintain connection pools and should not be created per tool call. FastMCP's lifespan mechanism provides an \texttt{@asynccontextmanager} that runs server startup code, yields a state object into every tool call via the request context, and runs shutdown code when the server terminates:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The \texttt{\_lifespan} context manager (\texttt{server.py:71--122}, condensed). \texttt{ServerState} carries the driver, GDS client, and retrieval configuration. The \texttt{yield state} statement hands control to FastMCP's tool dispatch loop; the \texttt{finally} block ensures the driver is closed on any exit path, including exceptions.}, label={lst:lifespan}]
@dataclass
class ServerState:
    driver: Driver
    gds: GraphDataScience
    project_root: str
    ppr_config: PPRConfig
    signal_weights: dict[str, float]
    default_token_budget: int
    default_top_k: int

@asynccontextmanager
async def _lifespan(server: FastMCP) -> AsyncIterator[ServerState]:
    db_manager = get_database_manager()
    db_manager.initialize(str(config_path))
    driver = db_manager.get_driver()
    gds = create_gds_client(driver)
    state = ServerState(driver=driver, gds=gds, ...)
    try:
        yield state
    finally:
        db_manager.close_driver()    # Always runs.
\end{lstlisting}

The \texttt{ServerState} dataclass uses typed fields rather than a generic dictionary, which means type errors in tool implementations are caught at development time. The \texttt{finally} block in \texttt{\_lifespan} ensures that the driver closes its connection pool even if a tool call raises an unhandled exception.

\subsection{STDIO Transport}
\label{subsec:stdio}

The server uses STDIO transport (stdin/stdout), the standard for local MCP servers integrated with Claude Desktop and Claude Code. Under STDIO transport, the host process (the AI agent's runtime) launches the server as a child process and communicates via JSON-RPC messages piped through stdin and stdout. No TCP socket, port, or firewall rule is required; the server is isolated to the user's local machine.

\subsection{Tool Registration}
\label{subsec:tool-registration}

Each MCP tool is registered using FastMCP's \texttt{@mcp.tool()} decorator. The decorator registers the Python function as a tool, using its docstring as the tool description and its type annotations as the JSON schema for input validation. The registration pattern in \texttt{server.py} keeps the decorated functions thin: they extract the \texttt{ServerState} from the request context and delegate immediately to an \texttt{*\_impl()} function defined in \texttt{tools.py}:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={Tool registration and delegation pattern (\texttt{server.py:130--143}). The \texttt{@mcp.tool()} decorator is a thin wrapper; all logic lives in \texttt{get\_relevant\_context\_impl()} in \texttt{tools.py}. This separation makes tools testable without MCP infrastructure: unit tests call \texttt{*\_impl()} directly.}, label={lst:tool-registration}]
@mcp.tool()
def get_relevant_context(
    task_description: str,
    mentioned_entities: list[str] | None,
    current_file: str | None,
    top_k: int,
    token_budget: int,
    ctx: Context,
) -> str:
    """Find structurally relevant code for a task."""
    state = ctx.request_context.lifespan_context
    return get_relevant_context_impl(
        task_description, mentioned_entities,
        current_file, top_k, token_budget, state
    )
\end{lstlisting}

\subsection{Configuration Resolution Chain}
\label{subsec:config-chain}

The server resolves its configuration file from three sources in priority order: a \texttt{--config} CLI argument, the \texttt{CODEGRAPH\_CONFIG} environment variable, and a default path relative to the package installation directory. This chain allows the same MCP server binary to serve different project configurations by setting the environment variable in the MCP server configuration of the host agent, without requiring separate installations.

\section{Evaluation Harness}
\label{sec:eval-harness}

The evaluation harness in \texttt{evaluation/} implements the SWE-bench Lite runner, ablation framework, and metric computation that support the experiments in \cref{ch:evaluation}. This section describes the engineering details that are prerequisite for interpreting those results correctly.

\subsection{SWE-bench Runner Architecture}
\label{subsec:runner-arch}

The runner (\texttt{swe\_bench\_runner.py}) follows a five-step data flow per benchmark instance:

\begin{enumerate}
    \item \textbf{Repository preparation:} clone or cache the repository at the specified \texttt{base\_commit} using \texttt{repo\_manager.clone\_or\_cache()}.
    \item \textbf{Parsing:} call \texttt{parse\_directory()} on the checked-out repository tree to produce a \texttt{list[FileEntities]}.
    \item \textbf{Graph construction:} call \texttt{clear\_database()}, then \texttt{build\_graph()} to write fresh nodes and edges for this commit state.
    \item \textbf{Retrieval:} call \texttt{extract\_seeds()} to build the personalization vector from the instance's issue text, then \texttt{run\_ppr\_from\_node\_ids()} to obtain the ranked result list.
    \item \textbf{Evaluation:} extract the predicted file list from the PPR results; compare against the gold file list from the instance's patch; compute and write per-instance metrics.
\end{enumerate}

A critical implementation detail in step~4 is that retrieval bypasses the MCP layer entirely. The MCP server applies a token budget: \texttt{format\_context()} truncates the result list to fit within the configured token limit. A pilot run discovered that this truncation caused every instance to report zero recall because the truncated list contained only one or two files, rarely including the gold file. The runner calls \texttt{run\_ppr\_from\_node\_ids()} directly and uses the full top-$k$ ranked list for scoring.

\subsection{Instance Grouping Optimization}
\label{subsec:grouping}

Many SWE-bench Lite instances share the same \texttt{(repo, base\_commit)} pair. Parsing and graph construction for a large repository like Django or SymPy takes 5--30\,s; running these steps once per instance would make a 300-instance run take over 40 hours. The grouping optimization processes each unique \texttt{(repo, base\_commit)} pair once: clone, checkout, parse, and build the graph, then run the cheap per-instance retrieval step for all instances in the group.

Groups are formed by \texttt{\_group\_instances()}, which partitions the instance list by \texttt{(repo, base\_commit)} key and sorts them by earliest original dataset index to preserve deterministic ordering. A typical SWE-bench Lite run has approximately 50--100 unique groups among 300 instances, reducing the number of parse-and-build cycles by 3--6$\times$ and reducing total wall-clock time from $>$40\,h to 12--14\,h.

The BM25 index is also built once per group and reused across all instances in the group (\cref{subsec:bm25-lifecycle}), avoiding repeated index construction for the same repository state.

\subsection{Ablation Framework}
\label{subsec:ablations}

\subsection{Metric Computation}
\label{subsec:metrics}

The primary metrics are Recall@$k$ and Mean Reciprocal Rank (MRR). Both operate on ranked file lists:

\begin{lstlisting}[style=pseudostyle, caption={Recall@$k$ and MRR implementations (\texttt{metrics.py:6--33}). Both functions take a gold file list and a predicted ranked list. Recall@$k$ measures the fraction of gold files appearing in the top $k$ predictions; MRR reports the reciprocal rank of the first correct prediction.}, label={lst:metrics}]
function recall_at_k(gold_files, predicted_files, k):
    gold = set(gold_files)
    top_k = set(predicted_files[:k])
    return |gold $\cap$ top_k| / |gold|   # 0.0 if gold is empty

function mrr(gold_files, predicted_files):
    gold = set(gold_files)
    for rank, pred in enumerate(predicted_files, start=1):
        if pred in gold:
            return 1.0 / rank
    return 0.0
\end{lstlisting}

Gold files are extracted from the SWE-bench instance's diff patch: any file path appearing in a \texttt{diff --git a/... b/...} header is treated as a gold file. Predicted files are the distinct file paths from the top-$k$ PPR results, in rank order. A result returns a file path, not a function or method, so PPR results from the same file are deduplicated before scoring.

The \texttt{aggregate\_metrics()} function computes mean and median for Recall@5, Recall@10, and MRR across all instances, together with a count of instances with zero recall. The zero-recall count is reported separately because it is the primary diagnostic for understanding failure modes: a run with 74\% mean Recall@10 but 80 zero-recall instances out of 300 has a very different failure profile from one with 50 zero-recall instances.

\section{Summary}
\label{sec:impl-summary}

This chapter described the non-obvious engineering decisions in CodeGraph's implementation. The codebase spans approximately 6,370 lines across six library packages and 3,380 lines in the evaluation harness. Four engineering decisions diverged meaningfully from the high-level design in \cref{ch:design}:

\begin{itemize}
    \item \textbf{Resolution priority chain} (\cref{sec:graph-impl}): The call resolution algorithm explicitly drops ambiguous edges rather than guessing, trading CALLS coverage (70\% average) for edge reliability. This conservative choice prevents PPR from being misled by spurious connections to common method names.

    \item \textbf{GDS~2.x weighted-mode workaround} (\cref{sec:ppr-impl}): The absence of \texttt{personalizationProperty} in GDS~2.x was discovered during integration. The linear combination workaround is mathematically exact and adds only 50\,ms to weighted-mode latency, but the discovery that GDS had silently dropped this parameter motivated switching to uniform mode as the default.

    \item \textbf{Per-call IDF recomputation} (\cref{sec:pipeline-orchestration}): Recomputing IDF weights and dropping the GDS projection on every retrieval call adds 50\,ms overhead but eliminates a class of subtle consistency bugs that would arise from stale projections after graph rebuilds.

    \item \textbf{Instance grouping in evaluation} (\cref{sec:eval-harness}): Grouping SWE-bench instances by \texttt{(repo, base\_commit)} reduces benchmark wall-clock time from $>$40 hours to 12--14 hours by amortizing the expensive parse-and-build step across all instances sharing the same repository state.
\end{itemize}

With the implementation described, \cref{ch:evaluation} presents the systematic experiments that quantify how each design and implementation decision contributes to retrieval quality.
