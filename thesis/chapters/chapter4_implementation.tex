\section{System Architecture}
\label{sec:system-architecture}
% =============================================================================

In this chapter, we translate the architectural blueprint established in \cref{ch:design} into a working implementation. We trace the full pipeline from the local filesystem to the ranked code context delivered to an AI agent. Our objective is to detail how we realize theoretical constructs---specifically static parsing, resolution fallbacks, and structural ranking---in software to ensure the system reliably retrieves correct code context while maintaining sub-second latency.

We organize the system into five sequential stages, as illustrated in \cref{fig:system-architecture}. First, the parser extracts structural entities from the repository. Next, the resolver establishes links between these entities. We load the resulting graph into a specialized database. When an AI agent requests context, the ranking engine traverses this graph to identify relevant code. Finally, the interface layer packages these results for agent consumption.

\section{The Parser: Extracting Structure from Code}
\label{sec:the-parser}
% =============================================================================

The foundational stage of CodeGraph is the ingestion pipeline, where we transform raw software repositories into structured representations of code entities.

We use Tree-sitter, an incremental parsing tool called via its Python bindings, for the extraction process. We prefer Tree-sitter over traditional abstract syntax tree (AST) libraries because it produces a Concrete Syntax Tree (CST) that maps directly to source byte offsets. This byte-level fidelity ensures that our parser preserves formatting and recovers from syntax errors: a critical requirement in development environments where code is frequently in an intermediate, non-compiling state.

Rather than indexing every variable assignment or loop, we implement a custom extraction algorithm that traverses the CST to identify four architectural entities: \texttt{File}, \texttt{Class}, \texttt{Function}, and \texttt{Method}. \noindent For each entity, we store the following metadata:
\begin{itemize}
    \item \textbf{Qualified Name (QN):} A globally unique identifier used as the primary node key, such as \texttt{auth.py::}\texttt{AuthService.login}.
    \item \textbf{Line Boundaries:} The start and end line numbers used to extract code snippets for the context package.
    \item \textbf{Signatures and Docstrings:} The textual corpus used for BM25 keyword matching during seed selection.
\end{itemize}

\section{The Resolver: Connecting the Pieces}
\label{sec:the-resolver}
% =============================================================================

We begin by extracting independent entities, but this is only the first step. To construct a graph capable of propagating relevance, we must determine how these entities interact. Our resolver converts raw string references into concrete graph edges.

\subsection{Import Resolution}

Import statements declare cross-file dependencies. Our implementation maps Python import strings into physical filesystem paths. For absolute imports, such as \texttt{import core.utils}, the resolver maps the dotted path relative to the project root. For relative imports, such as \texttt{from ..models import User}, it resolves parent directories before mapping. We identify external packages and standard library imports via dependency manifests and intentionally omit them to avoid creating dangling nodes that point outside the repository scope.

\subsection{Call Resolution: The Fallback Protocol}

Linking a function call expression, such as \texttt{verify()}, to the correct definition node in a dynamically typed language like Python requires a rigorous strategy. \noindent We employ a three-level Resolution Fallback Protocol, executed in descending order of confidence:

\begin{enumerate}
    \item \textbf{Explicit Imports:} We first check the file's import statements. If the called name matches a name imported from another module, we link the call to the corresponding entity in that module.
    \item \textbf{Local Scope:} If no import matches, we search for a function or method defined within the same file. This handles intra-file calls and class-level method invocations.
    \item \textbf{Global Scope:} As a final resort, we query the entire repository index for any entity with a matching name. This broad search captures calls where the import logic is too complex for static analysis.
\end{enumerate}

\subsection{Precision over Recall}

Across all resolution logic, we enforce a strict policy: precision over recall. If a global search finds multiple candidates due to ambiguous naming, such as multiple \texttt{update} methods, we deliberately ignore the connection. Because Personalized PageRank propagates along all edges, a single false edge can catastrophically misroute relevance mass into an unrelated subgraph. Dropping ambiguous connections slightly reduces recall but preserves the structural integrity of the graph.

Real-world edge cases further validate this decoupled approach. The system handles circular imports naturally without recursive loops because we analyze files independently. We cannot resolve dynamic imports, such as \texttt{importlib.import\_module()}, statically without execution tracing and therefore safely ignore them.

\section{The Database: Storing the Graph}
\label{sec:the-database}
% =============================================================================

After parsing the code and resolving connections, we persist the data into a structural graph. CodeGraph uses Neo4j, a specialized graph database optimized for relationship-centric storage. This architectural choice allows multi-hop traversals to execute in milliseconds, providing a performance advantage over the recursive joins required by traditional relational databases.

\subsection{Schema and Constraints}

We designed the graph schema to reflect our four-entity model (\texttt{File}, \texttt{Class}, \texttt{Function}, \texttt{Method}). We connect these nodes using four relationship types, as shown in \cref{fig:database-schema}. We use a visual hierarchy where containers (\texttt{File} and \texttt{Class}) are structurally prominent, while functional units (\texttt{Function} and \texttt{Method}) represent the leaf nodes of the hierarchy.

To ensure performance and correctness, we enforce strict database-level constraints. A uniqueness constraint on the \texttt{qualified\_name} property prevents duplicate entities during repository updates. Additionally, we establish indexes on the \texttt{file\_path} and \texttt{name} properties to accelerate the full-text queries used during seed selection.

\subsection{Two-Pass Construction: Handling Forward References}

We load the node types introduced in \cref{sec:the-database} (\cref{fig:database-schema}) in two sequential passes to resolve forward references. We face a sequencing challenge when loading source code into a graph: a function in \texttt{main.py} may call a utility defined in \texttt{utils.py}, but if we process \texttt{main.py} first, the target node does not yet exist and the relationship creation fails.

\noindent To resolve this, we implement a two-pass loading mechanism:
\begin{enumerate}
    \item \textbf{Pass 1 (Entity Creation):} The system traverses the entire repository to create all structural nodes (\texttt{File}, \texttt{Class}, \texttt{Function}, \texttt{Method}) and their internal \texttt{CONTAINS} edges. By the end of this pass, every possible call target exists as a unique node in the database.
    \item \textbf{Pass 2 (Linkage):} With the node population complete, the system executes a second pass to process the staged \texttt{IMPORTS} and \texttt{CALLS} relationships, safely linking nodes that were created in Pass 1.
\end{enumerate}

We execute all database writes using parameterized Cypher queries with batched \texttt{UNWIND} and \texttt{MERGE} clauses. This approach ensures idempotency; if we re-process a file, the system updates existing properties rather than creating duplicate nodes. Listing~\ref{lst:cypher-merge} demonstrates the MERGE pattern for both node and relationship creation.

\begin{lstlisting}[language=SQL, style=pseudostyle, mathescape=false, caption={Cypher query for idempotent two-pass construction using MERGE.}, label={lst:cypher-merge}]
// Pass 1: Node Creation (Idempotent)
UNWIND $nodes AS node
MERGE (n:Function {qualified_name: node.qn})
  ON CREATE SET n.file_path = node.path
  ON MATCH SET  n.file_path = node.path

// Pass 2: Relationship Creation
UNWIND $edges AS rel
MATCH (a {qualified_name: rel.source}), 
      (b {qualified_name: rel.target})
MERGE (a)-[:CALLS]->(b)
\end{lstlisting}

\subsection{GDS Projection}

Standard Cypher queries operate on the transactional database. However, executing graph algorithms like PageRank over millions of edges requires an in-memory representation. We use the Neo4j Graph Data Science (GDS) library to create an optimized undirected projection of the underlying graph. This projection allows the ranking algorithm to navigate bidirectionally, identifying both dependencies and their usage. We recreate this projection per query to ensure it reflects the latest state of the repository.

\subsection{Seed Selection and Personalization Vector}

The ranking process is initiated by identifying graph entry points, known as seeds, derived from the natural language task description. \noindent We construct a personalization vector by fusing multiple signals:
\begin{itemize}
    \item \textbf{Entity Match:} Regex extraction identifies code identifiers, such as \texttt{AuthError}, in the prompt, matching them directly to graph nodes.
    \item \textbf{BM25 Search:} The engine executes a keyword search against the indexed entity names and docstrings to capture partial matches.
    \item \textbf{Current File:} If the agent specifies an active file context, nodes within that file receive a slight proximity boost.
\end{itemize}

These signals are summed and normalized into a probability distribution. For instance, if a direct entity match scores heavily while BM25 returns several secondary candidates, the normalization ensures the vector sums to 1.0. This vector dictates the restart distribution for the random walk, injecting the lexical query directly into the structural graph.

\subsection{Query-Time IDF Reweighting}

Before executing the traversal, we must address the hub node problem: generic utility functions called from hundreds of locations inevitably attract disproportionate relevance mass, obscuring domain-specific logic. 

To mitigate this, we implement a query-time Inverse Document Frequency (IDF) reweighting step. Prior to creating the GDS projection, a Cypher update calculates the in-degree for every target node. The weight of an incoming edge $(i, j)$ is adjusted using an inverse-logarithmic formula:
\begin{equation}
    w_{ij} = \frac{1}{\log(1 + \text{in-degree}_j)}
\end{equation}
Consequently, a highly connected utility function, such as \texttt{isinstance()}, receives a mathematically penalized edge weight compared to a specialized business logic method, ensuring relevance mass flows towards meaningful architectural components.

\subsection{PPR Execution}

With the personalization vector constructed and the weighted GDS graph projected, the engine invokes the Personalized PageRank algorithm. We configure the GDS procedure with a uniform \texttt{sourceNodes} parameter based on the seed vector, a damping factor of $0.70$ to restrict the walk to the local neighborhood, and a maximum iteration threshold. The final output is a list of code entities ranked by their total relevance score.

\section{The Interface: Serving AI Agents}
\label{sec:the-interface}
% =============================================================================

The internal ranking engine identifies structural dependencies with high precision, but this capability is inaccessible to autonomous agents without a standardized communication bridge. CodeGraph resolves this by implementing a Model Context Protocol (MCP) server. This section details the implementation of the server, specifically focusing on the use of the FastMCP framework, the mechanics of stateful resource management, and the automated context construction pipeline.

\subsection{Server Implementation and Tool Registration}

The server is implemented using the FastMCP Python framework, which provides a high-level abstraction over the JSON-RPC 2.0 communication layer. By default, the server communicates with the host application via Standard Input/Output (stdio). This transport layer ensures that the server can run as a lightweight subprocess, minimizing the resource footprint on the developer's machine.

The implementation exposes a single tool, \texttt{get\_relevant\_context}, registered via a Python decorator. This decorator automatically generates the required JSON-RPC schema, including parameter descriptions and type constraints. This automated schema generation ensures that the AI agent receives a deterministic contract for tool invocation.

\subsection{Persistent State and Resource Management}

To sustain sub-250\,ms query latencies, the server must avoid the overhead of re-establishing database connections for every reasoning step. We achieve this by initializing core components, the Neo4j driver, the GDS client, and the structural ranker, at the server's module level.

Upon startup, the FastMCP server creates a persistent connection pool to the Neo4j instance. This persistent state is maintained throughout the server's lifecycle. When a tool is invoked, the ranker reuses the existing GDS projection and connection pool, as shown in the simplified implementation pattern in Listing~\ref{lst:mcp-server-impl}.

\begin{lstlisting}[language=Python, style=pythonstyle, caption={Implementation pattern for the stateful MCP tool using FastMCP.}, label={lst:mcp-server-impl}]
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("CodeGraph")
ranker = Ranker(neo4j_url=CONFIG.url)

@mcp.tool()
async def get_relevant_context(task_description: str):
    """Retrieve ranked code context for a given task."""
    results = await ranker.find_relevant_code(task_description)
    return assemble_context_package(results)
\end{lstlisting}

\subsection{Token-Aware Context Construction}

Once the Personalized PageRank algorithm identifies the highest-ranked entities, we transform these abstract graph nodes into a formatted text package. This construction process is governed by a strict, token-aware greedy algorithm.

The server uses a local Byte Pair Encoding (BPE) tokenizer to calculate the token count of every candidate code snippet in real-time. The construction loop iterates through the ranked results, reading raw source code from the filesystem based on the line boundaries stored in the graph. \noindent To ensure high information density, we apply two filters:
\begin{itemize}
    \item \textbf{File-Level Deduplication:} If multiple methods from the same file appear in the top results, the server includes the entire file once and skips subsequent hits for that file, avoiding redundant header inclusions.
    \item \textbf{Dynamic Budgeting:} The server maintains a running sum of tokens. If adding the next ranked file would exceed the requested budget, defaulting to 15,000 tokens, the file is discarded and the package is finalized.
\end{itemize}

\subsection{Error Handling and Feedback Loops}

Given that AI agents often operate autonomously, the implementation includes robust error propagation. If the ranking engine fails to identify relevant seeds due to an overly vague task description, the server does not return an empty response. Instead, it transmits a structured error message suggesting the agent refine its query with specific class or function names. This feedback loop allows the model to self-correct its retrieval strategy without human intervention.

\section{Summary}

In this chapter, we detailed the implementation of the CodeGraph pipeline, tracing the transition from raw source code to ranked context delivered via MCP. Key implementation wins include the use of the Tree-sitter parser for error-resilient extraction, the two-pass Neo4j construction for resolving forward references, and the stateful FastMCP server for low-latency delivery. These choices prioritize structural precision and low query latency, providing a robust foundation for autonomous agent interaction. The following chapter evaluates this implementation against industry benchmarks to quantify its retrieval effectiveness.
