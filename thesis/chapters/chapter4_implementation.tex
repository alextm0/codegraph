\chapter{Implementation}
\label{ch:implementation}

While \cref{ch:design} established the architectural principles and design decisions of CodeGraph, this chapter details the technical realization of those components. We focus on the specific algorithms, data structures, and integration patterns that enable precise code retrieval in large-scale repositories. This includes the regular expressions used for entity extraction, the progressive segment-stripping algorithm for import resolution, and the configuration of the graph database for efficient retrieval.

This chapter also describes the evaluation harness and ablation framework presented in \cref{sec:eval-harness}, which serve as the mechanical foundation for the empirical results analyzed in \cref{ch:evaluation}.

The chapter is organized as follows. \Cref{sec:project-structure} surveys the codebase layout and technology choices. \Cref{sec:parser-impl} covers the technical details of the parser implementation. \Cref{sec:graph-impl} examines graph construction and name resolution. \Cref{sec:pipeline-orchestration} describes the retrieval pipeline sequencing. \Cref{sec:mcp-impl} details the MCP server and CLI integration. \Cref{sec:eval-harness} presents the evaluation harness. \Cref{sec:impl-summary} concludes with a summary of the implementation.

Each technology choice in \cref{tab:module-map} follows from a specific design requirement identified in \cref{ch:design}:

\begin{itemize}
    \item \textbf{tree-sitter.} \Cref{sec:parsing} requires error-tolerant parsing of partial files, which is a prerequisite when indexing real-world repositories that may contain legacy syntax or work-in-progress files that cause built-in AST modules to fail. tree-sitter produces a concrete syntax tree regardless of syntax errors, allowing incomplete files to contribute partial entity information.

    \item \textbf{Neo4j + GDS.} The graph operations in \cref{sec:ppr-config} require both a persistent property graph: for MERGE-based idempotent writes and Cypher queries, and native PPR execution. The Neo4j Graph Data Science (GDS) library projects the persistent graph into an in-memory representation optimized for sparse matrix operations, enabling PPR convergence in 150--200\,ms on repositories with tens of thousands of nodes.

    \item \textbf{FastMCP.} The MCP server described in \cref{sec:mcp-integration} must support the STDIO transport that Claude Desktop and Claude Code expect from local tool servers. FastMCP is the official Python SDK for building MCP servers, providing tool registration, lifespan management, and STDIO transport.

    \item \textbf{rank-bm25.} Seed selection (\cref{sec:seed-selection}) requires a lexical similarity signal that operates without an embedding model. BM25 runs on CPU, requires no GPU, has no network dependency, and completes index construction in under one second for typical repository sizes.

    \item \textbf{tiktoken.} The token-budget enforcement in \cref{sec:post-processing} requires accurate token counting. tiktoken's encoding produces counts accurate to within 1\% for typical Python source code with negligible latency overhead.
\end{itemize}

\section{Parser Implementation}
\label{sec:parser-impl}

The parser transforms raw source files into typed \texttt{FileEntities} records, which are frozen dataclasses containing lists of \texttt{FunctionEntity}, \texttt{ClassEntity}, \texttt{MethodEntity}, \texttt{ImportEntity}, and \texttt{CallEntity} objects. While \cref{ch:design} established the design rationale, this section details the implementation of three critical aspects of the parser.

\subsection{Decorated-Definition Unwrapping}
\label{subsec:decorated-defs}

Python decorators present a parsing challenge. When a function is decorated, tree-sitter wraps it in a \texttt{decorated\_definition} node where the children are the decorator list and the actual \texttt{function\_definition} node. A naive traversal that checks only for \texttt{function\_definition} nodes misses all decorated functions. This also applies to classes where decorators like \texttt{@dataclass} or \texttt{@classmethod} are frequent.

The extractor pattern addresses this with a two-step check at each node:

\begin{lstlisting}[style=pseudostyle, caption={Decorated-definition unwrapping pattern (simplified from \texttt{extractors.py}). All five extractors (functions, classes, methods, imports, calls) apply the same pattern.}, label={lst:decorated-def}]
for node in root.children:
    actual = node
    if node.type == "decorated_definition":
        # Unwrap: find the first function_definition or
        # class_definition child of the decorator wrapper.
        for child in node.children:
            if child.type in ("function_definition",
                              "class_definition"):
                actual = child
                break
        else:
            continue          # Skip unknown decorated forms.
    if actual.type != "function_definition":
        continue
    # ... extract name, signature, docstring from actual ...
\end{lstlisting}

The pattern is applied in \texttt{extract\_functions}, \texttt{extract\_classes}, and \texttt{extract\_methods}. Maintaining the unwrapping logic explicitly within each extractor ensures they remain self-contained and facilitates individual testing.

\subsection{Entity Name Extraction from Free-Form Text}
\label{subsec:entity-names}

The seed selection stage (\cref{sec:seed-selection}) requires a mechanism to extract likely code identifiers from natural language task descriptions. The objective is to achieve high precision: while a generic tokenizer returns many tokens that do not match graph nodes, an overly conservative approach may miss critical identifiers and degrade seed quality.

The \texttt{extract\_entity\_names} function applies six regular expressions to the input text, targeting syntactically distinct classes of Python identifiers:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The six regex patterns in \texttt{extract\_entity\_names()} (\texttt{seed\_selection.py:153--166}). Each pattern targets a distinct identifier class. The patterns are applied in priority order; duplicates are removed with first-occurrence semantics.}, label={lst:regex-patterns}]
# Multi-segment CamelCase: "AuthService", "BlogPost"
camel_multi  = re.findall(r"\b[A-Z][a-z]+(?:[A-Z][a-z]+)+\b", text)

# Single-word CamelCase with internal uppercase: "QuerySet", "HTMLParser"
# Requires a lowercase->uppercase transition to exclude plain English words.
camel_single = re.findall(r"\b[A-Z][a-z]+[A-Z]\w+\b", text)

# All-caps prefix + title-case word: "SQLCompiler", "HTTPSConnection"
camel_allcaps= re.findall(r"\b[A-Z]{2,}[A-Z][a-z]\w*\b", text)

# snake_case: at least one underscore separating lowercase segments
snake        = re.findall(r"\b[a-z][a-z0-9]*(?:_[a-z][a-z0-9]*)+\b", text)

# Backtick-quoted identifiers (common in GitHub issue descriptions)
backtick     = re.findall(r"`([A-Za-z_][A-Za-z0-9_.]+)`", text)

# Dotted module paths: "models.queryset", "sql.compiler" (2--5 lowercase segments)
dotted       = re.findall(r"\b[a-z][a-z0-9]*(?:\.[a-z][a-z0-9_]*){1,4}\b", text)
\end{lstlisting}

Each pattern avoids common English words. For example, \texttt{camel\_single} requires a lowercase-to-uppercase transition (\texttt{[A-Z][a-z]+[A-Z]}) to exclude standard capitalized words like Fix or The. The \texttt{snake} pattern requires at least one underscore, and the \texttt{backtick} pattern identifies identifiers typically quoted in technical descriptions.

The resulting groups are processed in a deduplication loop that preserves the order of first occurrence. This ensures that higher-confidence patterns like CamelCase take priority over lower-confidence ones like dotted paths, which may occasionally match non-code text. Precision in this step is critical as it directly influences the seed distribution and retrieval quality.

\subsection{Compound Tokenization for BM25}
\label{subsec:compound-tokenization}

Standard tokenizers treat identifiers such as \texttt{SQLCompiler} or \texttt{handle\_subquery} as atomic tokens. A BM25 query for "SQL compilation" would fail to match a document containing only \texttt{SQLCompiler} if the constituent tokens \texttt{sql} and \texttt{compiler} are never produced. The \texttt{tokenize} function addresses this through two substitution steps:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The \texttt{tokenize()} function (\texttt{seed\_selection.py:429--444}). CamelCase splitting uses two regex passes: the first inserts a space at every lowercase-to-uppercase boundary, the second handles consecutive uppercase runs (e.g.\ \texttt{SQLCompiler}).}, label={lst:tokenize}]
def tokenize(text: str) -> list[str]:
    # Split CamelCase: "handleSubQuery" -> "handle Sub Query"
    text = re.sub(r'([a-z0-9])([A-Z])', r'\1 \2', text)
    # Handle consecutive caps: "SQLCompiler" -> "SQL Compiler"
    text = re.sub(r'([A-Z]+)([A-Z][a-z])', r'\1 \2', text)
    # Split on all non-alphanumeric (underscores split too)
    tokens = re.split(r"[^a-z0-9]+", text.lower())
    return [tok for tok in tokens if len(tok) > 1]
\end{lstlisting}

The two-pass approach handles strings like \texttt{SQLCompiler} by inserting a space before the final uppercase letter in a run when it is followed by a lowercase letter. This tokenizer is applied to both the query and every document in the BM25 corpus, ensuring that lexical matching occurs across the semantic gap of identifier names.

\section{Graph Construction and Name Resolution}
\label{sec:graph-impl}

Graph construction is an engineering-intensive stage where raw parsed data is transformed into a Neo4j property graph consisting of four node types and four edge types. This section describes the two-pass construction strategy, the qualified name scheme that serves as the graph's primary key, and the resolution algorithms for imports and function calls.

\subsection{Two-Pass Construction and Batched Writes}
\label{subsec:two-pass}

The \texttt{build\_graph} function follows a two-pass strategy. Pass 1 creates all node records and CONTAINS edges within a single transaction: File, Function, Class, and Method nodes are written, together with the File$\to$Function, File$\to$Class, and Class$\to$Method containment edges. Pass 2 creates the cross-file edges, including CALLS, IMPORTS, and INHERITS\_FROM, using the complete node index built in Pass 1.

The two-pass ordering is necessary because call and import resolution requires forward references. For example, a function in \texttt{auth\_service.py} may call \texttt{hash\_password} defined in \texttt{crypto.py}; resolving this edge requires the target node to exist in the graph before the CALLS edge can be created. The two-pass design ensures that all MERGE targets exist before any MATCH-based edge creation occurs.

All writes use the \texttt{UNWIND + MERGE} pattern to ensure efficiency and idempotency:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={Batched Function node creation using \texttt{UNWIND + MERGE} (\texttt{graph\_builder.py:186--199}). The entire batch of Function nodes for all parsed files is written in a single Cypher transaction. \texttt{MERGE} on \texttt{qualified\_name} ensures idempotency: re-running \texttt{rebuild} updates existing nodes rather than creating duplicates.}, label={lst:unwind-merge}]
result = tx.run(
    """
    UNWIND $nodes AS n
    MERGE (f:Function {qualified_name: n.qualified_name})
    SET f.name = n.name, f.file_path = n.file_path,
        f.line_number = n.line_number, f.end_line = n.end_line,
        f.signature = n.signature, f.docstring = n.docstring
    RETURN count(f) AS created
    """,
    nodes=nodes,
)
\end{lstlisting}

A uniqueness constraint on \texttt{qualified\_name} is created before any writes. This enforces the invariant that every node has a unique primary key and enables Neo4j to use index lookups for each \texttt{MERGE} operation.

\subsection{Qualified Name Scheme}
\label{subsec:qname}

Every node in the graph is identified by a \texttt{qualified\_name} string. The scheme follows the pattern \texttt{file\_path::entity\_name}, where \texttt{file\_path} is relative to the project root and \texttt{entity\_name} encodes the full dotted path within the file:

\begin{itemize}
    \item \textbf{File:} \texttt{src/auth/service.py}
    \item \textbf{Function:} \texttt{src/auth/service.py::authenticate}
    \item \textbf{Class:} \texttt{src/auth/service.py::AuthService}
    \item \textbf{Method:} \texttt{src/auth/service.py::AuthService.authenticate}
\end{itemize}

The double-colon separator (\texttt{::}) disambiguates the file path from the entity name, as dots are used for both module and method names. Forward slashes are normalized to ensure consistency across different operating systems. Finally, including the full dotted path within the file avoids collisions between methods and top-level functions sharing the same name.

\subsection{Import Resolution}
\label{subsec:import-resolution}

Import resolution maps a dotted Python module path to a file path in the parsed repository. The challenge is that Python module paths encode a package hierarchy that may not correspond directly to the directory hierarchy.

The resolution strategy uses progressive segment stripping: the dotted path is converted to a file path suffix, and leading segments are progressively stripped until a match is found:

\begin{lstlisting}[style=pseudostyle, caption={Import resolution via progressive segment stripping (\texttt{resolution.py:165--194}). The algorithm tries up to \texttt{len(parts)} suffix lengths, stopping at the first match. A final fallback tries the full dotted path as a suffix.}, label={lst:import-resolution}]
function resolve_import(module_path, all_file_paths):
    parts = module_path.split(".")
    # Try stripping 1, 2, ... leading segments.
    for skip in range(1, len(parts)):
        suffix = "/".join(parts[skip:]) + ".py"
        for fp in all_file_paths:
            if fp == suffix or fp.endswith("/" + suffix):
                return fp       # First match wins.
    # Fallback: full dotted path as suffix.
    suffix = "/".join(parts) + ".py"
    for fp in all_file_paths:
        if fp == suffix or fp.endswith("/" + suffix):
            return fp
    return None                 # Unresolvable (e.g., third-party).
\end{lstlisting}

This approach recovers the relative suffix by stripping the top-level package name. It achieves an import resolution rate of approximately 80\% on the SWE-bench Lite benchmark repositories. Failures are primarily due to third-party packages not present in the indexed directory, conditional imports, or dynamic imports.

\subsection{Call Resolution}
\label{subsec:call-resolution}

Call resolution maps a callee expression to a node \texttt{qualified\_name} in the graph. These relationships are common but often ambiguous. For instance, a method named \texttt{save} may appear in multiple classes; incorrect resolution would introduce spurious edges that misdirect the PPR algorithm.

The resolution algorithm applies a priority chain:

\begin{lstlisting}[style=pseudostyle, caption={Call resolution priority chain (\texttt{resolution.py:80--123}). The algorithm prefers the most specific context available: an explicit import, then same-file definitions, then a globally unique name. Ambiguous cases are dropped rather than guessed.}, label={lst:call-resolution}]
function resolve_callee(callee_name, lookup, file_path, import_map):
    candidates = lookup.get(callee_name, [])
    if not candidates:
        return None             # Unknown name; not in project graph.

    # Priority 1: callee was explicitly imported in this file.
    imported_file = import_map.get(callee_name)
    if imported_file:
        for qname in candidates:
            if qname.startswith(imported_file + "::"):
                return qname

    # Priority 2: callee is defined in the same file (unambiguous).
    same_file = [q for q in candidates
                 if q.startswith(normalize(file_path) + "::")]
    if len(same_file) == 1:
        return same_file[0]
    if len(same_file) > 1:
        return None             # Multiple local definitions; skip.

    # Priority 3: exactly one candidate globally.
    if len(candidates) == 1:
        return candidates[0]

    return None                 # Globally ambiguous; skip.
\end{lstlisting}

The decision to return \texttt{None} for ambiguous cases is critical. Picking an arbitrary candidate would misdirect probability flows. While this conservative strategy may reduce coverage, it ensures that the resulting edges are reliable. Coverage typically ranges from 60\% to 80\% depending on the repository.

Additionally, Python built-in names are filtered using a predefined set, and dotted callee expressions skip the built-in filter but still apply the same priority chain using the method name component.

\section{Retrieval Pipeline Orchestration}
\label{sec:pipeline-orchestration}

The retrieval pipeline is a high-level orchestrator. The \texttt{run\_retrieval\_pipeline} function in \texttt{pipeline.py} sequences four operations: seed extraction, IDF reweighting, GDS projection, and PPR execution. This section details the sequencing decisions required for pipeline consistency and efficiency.

\subsection{Per-Call IDF Reweighting and Projection Refresh}
\label{subsec:per-call-idf}

The \texttt{ensure\_graph\_ready} function is invoked at the start of every retrieval call. It performs two operations: reapplying IDF weights to all edges in Neo4j and then refreshing the GDS in-memory projection. Both steps are performed unconditionally.

This approach ensures consistency. Since IDF weights are computed from the graph's current in-degree distribution, any re-indexing between retrieval calls would render a cached GDS projection stale. To avoid the complexity of a versioning mechanism, the implementation ensures the GDS projection is freshly computed from the current Neo4j state. The associated latency is approximately 50\,ms, which is acceptable within the total retrieval window of under 250\,ms.

\subsection{IDF Weight Computation in Cypher}
\label{subsec:idf-cypher}

The IDF weight formula, $w = 1 / \log_2(\text{in\_degree} + 2)$, is applied through a single Cypher query that updates all edges:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The IDF edge-weight Cypher query (\texttt{post\_processing.py:65--74}). A single query aggregates the in-degree for each target node, then updates the \texttt{weight} property of every incoming edge. Neo4j's \texttt{log()} function is natural log; division by \texttt{log(2.0)} converts to $\log_2$.}, label={lst:idf-cypher}]
result = session.run(
    """
    MATCH (target)
    WITH target, COUNT { (()-[]->(target)) } AS in_deg
    MATCH (src)-[r]->(target)
    SET r.weight = 1.0 / (log(toFloat(in_deg) + 2.0) / log(2.0))
    RETURN count(r) AS updated
    """
)
\end{lstlisting}

Computing IDF directly in Cypher avoids the overhead of transferring large numbers of edges to the Python environment. The $+ 2$ term in the denominator prevents division by zero and ensures that singleton nodes receive a finite weight. As in-degree increases, the relative weight of the edges decreases, effectively down-weighting hub nodes.

\subsection{BM25 Index Lifecycle}
\label{subsec:bm25-lifecycle}

The BM25 index is constructed by \texttt{prepare\_bm25\_index}, which retrieves all searchable nodes from Neo4j and initializes a \texttt{BM25Okapi} object. Construction time varies between 100\,ms and 500\,ms depending on the repository size.

For interactive use, the index is rebuilt on every call. However, the evaluation harness optimizes this by building the index once per repository group and reusing it across instances, resulting in a significant performance gain.

\subsection{Auto-Entity Augmentation}
\label{subsec:auto-entity}

Each retrieval pipeline invocation automatically extracts entity names from the task description. These names are then merged with any user-supplied entities to ensure that all relevant identifiers are considered:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={Auto-entity augmentation in \texttt{run\_retrieval\_pipeline()} (\texttt{pipeline.py:51--55}). Automatically extracted names augment caller-supplied entities, ensuring that identifiers in the task text are always searched even when the caller does not pass \texttt{mentioned\_entities}.}, label={lst:auto-entity}]
auto_entities = extract_entity_names(task_description)
existing = set(mentioned_entities or [])
augmented_entities = list(mentioned_entities or []) + [
    e for e in auto_entities if e not in existing
]
\end{lstlisting}

This augmentation ensures that identifiers in the task text are always indexed for retrieval. User-supplied entities are prioritized and processed first in the resulting list.

\section{PPR Execution via Neo4j GDS}
\label{sec:ppr-impl}

\Cref{sec:ppr-config} established the mathematical role of Personalized PageRank and the rationale for the damping factor and top-$k$ parameters. This section details the GDS API implementation.

\subsection{Graph Projection}
\label{subsec:gds-projection}

Before PPR can execute, the Neo4j graph must be projected into an in-memory GDS representation. The \texttt{project\_graph} function creates this projection:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={GDS graph projection (\texttt{ppr.py:96--106}). All four node labels and four relationship types are included. Orientation is \texttt{UNDIRECTED} so PPR can follow edges in both directions. The \texttt{weight} property is exposed to GDS as the edge weight for the \texttt{relationshipWeightProperty} parameter in PPR.}, label={lst:gds-projection}]
node_spec = ["File", "Function", "Class", "Method"]
relationship_spec = {
    rel_type: {
        "orientation": orientation,   # "UNDIRECTED" by default
        "properties": "weight"
    }
    for rel_type in relationship_types
}
create_result = gds.graph.project(
    _PROJECTION_NAME, node_spec, relationship_spec
)
projection = create_result.graph
\end{lstlisting}

The \texttt{UNDIRECTED} orientation is a critical algorithmic choice. PPR on a directed graph cannot propagate probability against an edge direction, meaning a seed in a callee function would never reach its callers. An undirected projection treats every relationship as bidirectional, allowing probability to flow symmetrically between callers and callees.

\subsection{Uniform PPR Mode}
\label{subsec:uniform-ppr}

The default retrieval mode, uniform, executes a single \texttt{gds.pageRank.stream} call with seed node IDs supplied via the \texttt{sourceNodes} parameter:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={Uniform PPR execution (\texttt{ppr.py:232--243}). GDS handles the personalization internally when \texttt{sourceNodes} is provided: it distributes the restart probability uniformly across the listed nodes. The result is a pandas DataFrame sorted by \texttt{nodeId}.}, label={lst:ppr-stream}]
result_df = gds.pageRank.stream(
    projection,
    maxIterations=config.max_iterations,       # 20
    dampingFactor=config.damping_factor,        # 0.70
    tolerance=config.tolerance,                 # 1e-7
    sourceNodes=list(seed_weights.keys()),      # Neo4j internal IDs
    relationshipWeightProperty="weight",
)
top_rows = (result_df
    .sort_values("score", ascending=False)
    .head(config.top_k))
\end{lstlisting}

The \texttt{sourceNodes} parameter triggers the personalized variant of PageRank in GDS. Instead of distributing restart probability uniformly across all nodes, GDS concentrates it on the specified source nodes.

\subsection{Weighted PPR Mode and the GDS 2.x Workaround}
\label{subsec:weighted-ppr}

The weighted retrieval mode, retained as an ablation baseline, requires non-uniform personalization. Seeds with higher signal weights should receive proportionally more restart probability. However, GDS 2.x removed support for the \texttt{personalizationProperty} parameter, necessitating a workaround.

The implementation exploits the mathematical linearity of PPR. A weighted sum of per-seed PPR results is equivalent to a single PPR run with a weighted personalization vector:

\[
    \text{PPR}_{\text{weighted}} = \sum_{i} w_i \cdot \text{PPR}(\text{seed}_i)
\]

The \texttt{run\_ppr\_weighted} function executes \texttt{gds.pageRank.stream} once per seed, collects the resulting scores, and combines them with the appropriate weights. This approach adds approximately 50\,ms to the retrieval latency but ensures mathematical correctness for the ablation study.

\section{MCP Server Integration}
\label{sec:mcp-impl}

The MCP server in \texttt{src/codegraph/mcp/} exposes the retrieval pipeline to AI agents as a set of callable tools. This section describes the server lifecycle, tool registration, and configuration resolution.

\subsection{FastMCP Lifespan Pattern}
\label{subsec:lifespan}

The Neo4j driver and GDS client are long-lived resources that maintain connection pools. FastMCP's lifespan mechanism provides an \texttt{asynccontextmanager} that handles server startup, yields a state object into tool calls, and ensures proper shutdown:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={The \texttt{\_lifespan} context manager (\texttt{server.py:71--122}, condensed). \texttt{ServerState} carries the driver, GDS client, and retrieval configuration. The \texttt{yield state} statement hands control to FastMCP's tool dispatch loop; the \texttt{finally} block ensures the driver is closed on any exit path.}, label={lst:lifespan}]
@dataclass
class ServerState:
    driver: Driver
    gds: GraphDataScience
    project_root: str
    ppr_config: PPRConfig
    signal_weights: dict[str, float]

@asynccontextmanager
async def _lifespan(server: FastMCP) -> AsyncIterator[ServerState]:
    db_manager = get_database_manager()
    db_manager.initialize(str(config_path))
    driver = db_manager.get_driver()
    gds = create_gds_client(driver)
    state = ServerState(driver=driver, gds=gds, ...)
    try:
        yield state
    finally:
        db_manager.close_driver()    # Always runs.
\end{lstlisting}

The \texttt{ServerState} dataclass uses typed fields to ensure type safety in tool implementations. The \texttt{finally} block in \texttt{\_lifespan} ensures that the database driver closes its connection pool regardless of termination conditions.

\subsection{STDIO Transport and Protocol}
\label{subsec:stdio}

The server utilizes STDIO transport, which is the standard for local MCP servers integrated with environments like Claude Desktop. The host process launches the server as a child process and communicates via JSON-RPC messages piped through stdin and stdout. This ensures the server remains isolated to the user's local machine without requiring network sockets.

\begin{lstlisting}[style=pythonstyle, caption={JSON-RPC request to the \texttt{get\_relevant\_context} tool. The agent provides the task description and optional entities; the server responds with structured context.}, label={lst:mcp-json-rpc}]
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "get_relevant_context",
    "arguments": {
      "task_description": "Fix the SQL compilation error in the compiler.",
      "mentioned_entities": ["SQLCompiler"]
    }
  },
  "id": 1
}
\end{lstlisting}

\subsection{Tool Registration}
\label{subsec:tool-registration}

Each tool is registered using the \texttt{@mcp.tool()} decorator. The registration pattern keeps the functions thin, extracting state from the context and delegating logic to implementation functions:

\begin{lstlisting}[style=pythonstyle, language=Python, caption={Tool registration and delegation pattern (\texttt{server.py:130--143}). All logic lives in \texttt{get\_relevant\_context\_impl()} in \texttt{tools.py}, facilitating unit testing without MCP infrastructure.}, label={lst:tool-registration}]
@mcp.tool()
def get_relevant_context(
    task_description: str,
    mentioned_entities: list[str] | None,
    ctx: Context,
) -> str:
    """Find structurally relevant code for a task."""
    state = ctx.request_context.lifespan_context
    return get_relevant_context_impl(
        task_description, mentioned_entities, state
    )
\end{lstlisting}

\subsection{Configuration Resolution Chain}
\label{subsec:config-chain}

The server resolves configuration from three sources in priority order: a \texttt{--config} CLI argument, the \texttt{CODEGRAPH\_CONFIG} environment variable, and a default path. This allows a single binary to serve different project configurations by modifying the environment variables in the host agent.

\section{Evaluation Harness}
\label{sec:eval-harness}

The evaluation harness implements the SWE-bench Lite runner, the ablation framework, and the metric computation required for the experiments presented in \cref{ch:evaluation}. This section details the engineering components of the harness.

\subsection{SWE-bench Runner Architecture}
\label{subsec:runner-arch}

The runner, implemented in \texttt{swe\_bench\_runner.py}, executes five steps for each benchmark instance:

\begin{enumerate}
    \item \textbf{Repository preparation:} The repository is cloned or retrieved from a cache at the specified base commit.
    \item \textbf{Parsing:} The directory is parsed to produce a list of file entities.
    \item \textbf{Graph construction:} The database is cleared, and the graph is rebuilt for the current commit state.
    \item \textbf{Retrieval:} Seed nodes are extracted from the instance issue text, and PPR is executed to obtain a ranked result list.
    \item \textbf{Evaluation:} The predicted file list is compared against the gold file list from the instance patch to compute metrics.
\end{enumerate}

A critical detail in the retrieval step is that the harness bypasses the MCP layer to avoid truncation. While the MCP server applies a token budget for agent context, the evaluation runner uses the full ranked list to ensure a complete assessment of retrieval performance.

\subsection{Instance Grouping Optimization}
\label{subsec:grouping}

Many benchmark instances share the same repository and base commit. Since parsing and graph construction are computationally expensive, the harness optimizes this by grouping instances by their repository state. This ensures that the graph is built once per group, after which retrieval is executed for each instance in the group. This optimization significantly reduces the total execution time, amortizing the cost of graph construction across multiple instances.

\subsection{Ablation Framework}
\label{subsec:ablations}

The ablation framework allows for systematic variation of design decisions through the \texttt{AblationConfig} dataclass. This facilitates isolated testing of individual pipeline components.

\begin{lstlisting}[style=pythonstyle, language=Python, caption={\texttt{AblationConfig} dataclass (\texttt{ablations.py:13--31}). A single frozen dataclass captures the full parameter space of the retrieval pipeline.}, label={lst:ablation-config}]
@dataclass(frozen=True)
class AblationConfig:
    name: str
    relationship_types: list[str] | None = None   # None = all four
    orientation: str = "UNDIRECTED"
    apply_idf: bool = True
    ppr_config: PPRConfig = field(default_factory=PPRConfig)
\end{lstlisting}

Over 20 named configurations are defined to isolate variables such as edge types, graph orientation, and damping factors. These configurations are systematically evaluated to determine the contribution of each component to overall retrieval quality.

\subsection{Metric Computation}
\label{subsec:metrics}

The primary metrics computed are Recall@$k$ and Mean Reciprocal Rank (MRR). Both metrics operate on the ranked list of file paths produced by the retrieval pipeline.

\begin{lstlisting}[style=pseudostyle, caption={Recall@$k$ and MRR implementations (\texttt{metrics.py:6--33}). Both functions take a gold file list and a predicted ranked list. Recall@$k$ measures the fraction of gold files appearing in the top $k$ predictions; MRR reports the reciprocal rank of the first correct prediction.}, label={lst:metrics}]
function recall_at_k(gold_files, predicted_files, k):
    gold = set(gold_files)
    top_k = set(predicted_files[:k])
    return |gold $\cap$ top_k| / |gold|

function mrr(gold_files, predicted_files):
    gold = set(gold_files)
    for rank, pred in enumerate(predicted_files, start=1):
        if pred in gold:
            return 1.0 / rank
    return 0.0
\end{lstlisting}

Gold files are identified from the benchmark instance patch headers. Predicted files are extracted from the PPR results and deduplicated by file path. The harness aggregates these metrics to provide mean and median values across the dataset, alongside diagnostic counts such as the number of instances with zero recall, which helps identify systematic failure modes.

\section{Summary}
\label{sec:impl-summary}

This chapter detailed the engineering decisions made during the implementation of CodeGraph. The codebase includes approximately 6,370 lines across six library packages and 3,380 lines in the evaluation harness. Several key implementation choices diverged from the initial high-level design to address technical requirements:

\begin{itemize}
    \item \textbf{Resolution priority chain} (\cref{sec:graph-impl}): The call resolution algorithm prioritizes explicit imports and same-file definitions, dropping ambiguous edges to maintain graph reliability. This conservative approach prevents the PPR algorithm from being misdirected by spurious connections.

    \item \textbf{GDS 2.x weighted-mode workaround} (\cref{sec:ppr-impl}): Due to the removal of specific personalization parameters in GDS 2.x, a linear combination workaround was implemented. This approach maintains mathematical correctness and ensures the viability of the weighted retrieval mode for experimental comparison.

    \item \textbf{Per-call IDF recomputation} (\cref{sec:pipeline-orchestration}): Recomputing IDF weights and refreshing the GDS projection on each retrieval call ensures system consistency and eliminates potential bugs related to stale graph states.

    \item \textbf{Instance grouping in evaluation} (\cref{sec:eval-harness}): Grouping benchmark instances by repository and base commit optimizes the evaluation process by amortizing the cost of graph construction.
\end{itemize}

The technical foundation established in this chapter enables the systematic evaluation of CodeGraph. In \cref{ch:evaluation}, we present the results of the experiments and analyze the performance of the retrieval pipeline.
