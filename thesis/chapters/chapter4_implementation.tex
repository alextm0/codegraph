\chapter{Implementation}
\label{ch:implementation}

This chapter details the codebase structure, library integration, and execution logic of the CodeGraph system. While Chapter 3 established the conceptual architecture, this chapter focuses on the engineering realities of transforming a raw Python repository into a connected, searchable graph. We describe how CodeGraph realizes the retrieval architecture through two distinct pipelines: the \textbf{indexing path}, which utilizes \textbf{Tree-sitter} for resilient AST extraction and builds a structural model in \textbf{Neo4j}, and the \textbf{retrieval path}, which leverages the \textbf{Neo4j Graph Data Science (GDS)} library to rank repository context for AI agents. 

A central theme of the implementation is the enforcement of a strict system contract through a single orchestrator function. This ensures that regardless of the user interface—be it the command-line, an agent-oriented protocol, or an interactive web visualizer—the ranking behavior remains deterministic and identical. The following sections provide a descriptive walkthrough of the modular package layout, the components of the indexing and retrieval pipelines, and the technical realization of user-facing entry points.

\section{The Indexing Path}
\label{sec:indexing-path}
% =============================================================================

The indexing path is the foundational pipeline that transforms a raw repository on disk into a structured, queryable model. This process involves four major engineering stages: ingestion of source files, extraction of architectural entities, resolution of references between those entities, and the transactional persistence of the resulting graph.

\subsection{Tree-sitter Ingestion and AST Extraction}
\label{subsec:parser-ingestion}

CodeGraph implements code ingestion using the \textbf{Tree-sitter} library, an incremental parsing system that is particularly well-suited for the realities of software development. Unlike traditional compiler-based parsers that fail on syntax errors, Tree-sitter produces a Concrete Syntax Tree (CST) that maps directly to source byte offsets even when code is incomplete or malformed. This robustness is essential for our "always-on" indexing requirement, as source files in active development environments frequently contain intermediate states that would halt a standard parser.

The extraction logic walks the CST using dedicated visitor patterns implemented in \texttt{extractors.py}. Rather than modeling every variable assignment or arithmetic expression, the extractors focus on the four architectural entities established in our design: files, classes, functions, and methods. These entities are stored as frozen, immutable dataclasses defined in \texttt{models.py}. This immutability is an intentional implementation choice to prevent accidental side effects as entity metadata flows through the later stages of resolution and database insertion. \Cref{fig:parsing-example} provides a side-by-side visualization of how raw Python source code is mapped to the structured metadata containers that drive graph construction.

\subsection{Static Reference Resolution}
\label{subsec:static-resolution}

Once entities are extracted from individual files, the resolver module must connect them into a repository-wide graph. This resolution process is inherently challenging in Python due to its dynamic nature and the lack of explicit type information in many call sites. To address this, the implementation realizes the three-level resolution strategy through the \texttt{\_resolve\_symbol} routine shown in \Cref{lst:call-resolution}.

The resolver first attempts to match a symbol against the file's \texttt{import\_map}, which is constructed by mapping dotted package paths to physical filesystem locations relative to the project root. If no explicit import is found, the system checks for local definitions within the same file. Finally, it performs a global search for unique identifiers across the entire repository. A critical implementation policy is the dropping of ambiguous references: if a symbol name resolves to multiple candidates at a given level, the resolver creates no edge. This precision-first approach ensures that the resulting graph remains a reliable signal for structural retrieval, avoiding the introduction of false paths that would misdirect PageRank probability mass during the ranking phase.

To maintain performance during repository-wide analysis, the resolver caches normalized path representations and pre-aggregates class-level member tables. This caching prevents repeated disk reads or redundant symbol table lookups. Additionally, when mapping local definitions, the system explicitly distinguishes between top-level functions and class methods, checking the local hierarchy from the innermost nested scope outward. While more sophisticated dynamic typing systems could theoretically reconstruct ambiguous execution paths, CodeGraph prioritizes static predictability; by omitting unresolved references, it prevents the propagation of noise in the graph projection stage.

\begin{cgpython}[label=lst:call-resolution, unbreakable]{Call resolution logic}
def _resolve_symbol(self, symbol_name: str, lookup: dict[str, list[str]], file_path: str, import_map: dict[str, str]) -> Optional[str]:
    candidates = lookup.get(symbol_name, [])
    if not candidates:
        return None
        
    # 1. Check if the symbol maps to a resolved import
    imported_file = import_map.get(symbol_name)
    if imported_file:
        for qname in candidates:
            if qname.startswith(imported_file + "::"):
                return qname
                
    # 2. Check if there is a local definition in the same file
    norm_fp = normalize_path(file_path)
    same_file = [qname for qname in candidates if qname.startswith(norm_fp + "::")]
    if len(same_file) == 1:
        return same_file[0]
    if len(same_file) > 1:
        return None  # Ambiguous local naming drops the connection
        
    # 3. Check for a single globally unique definition
    if len(candidates) == 1:
        return candidates[0]
        
    return None  # Ambiguous global naming drops the connection
\end{cgpython}

\subsection{Two-Pass Database Construction}
\label{subsec:two-pass-construction}

The persistence of the connected model to Neo4j requires careful transaction management to handle forward references. A function in one module may call a class defined in another; if the database attempted to create this relationship before both modules were indexed, the write would fail due to missing nodes. We resolve this by implementing a two-pass construction strategy. Pass 1 iterates through the repository to insert all architectural nodes and establish local \texttt{CONTAINS} edges, ensuring the complete node population exists before any cross-module dependencies are added. Pass 2 then adds the \texttt{CALLS}, \texttt{IMPORTS}, and \texttt{INHERITS\_FROM} relationships using the global lookup table populated during the first pass.

The implementation uses idempotent Cypher queries to ensure that repository updates modify existing properties rather than creating redundant data. By utilizing the \texttt{UNWIND} and \texttt{MERGE} clauses shown in \Cref{lst:cypher-merge}, the system can re-process files safely without corrupting the graph state. This idempotency is foundational for the incremental update mechanism described in the next subsection.

In addition to ensuring relational consistency, this two-pass insertion is optimized for database transaction throughput. Rather than issuing individual Cypher commands for each entity or relationship, the parser aggregates results into memory buffers and flushes them in batched, parameterized transactions. To accelerate the \texttt{MERGE} and \texttt{MATCH} lookups, we define uniqueness constraints on the \texttt{qualified\_name} property of all node types during database initialization. This indexing turns what would otherwise be costly full-table scans into fast $O(1)$ index seek operations, allowing CodeGraph to handle repositories with tens of thousands of entities in a few seconds.

\begin{cgcypher}[label=lst:cypher-merge, unbreakable]{Idempotent Cypher operations}
// Pass 1: Batched node insertion using MERGE
UNWIND $nodes AS n
MERGE (f:File {qualified_name: n.qualified_name})
SET f.name = n.name, f.file_path = n.file_path
RETURN count(f) AS created

// Pass 2: Batched cross-file relationship resolution
UNWIND $edges AS e
MATCH (src {qualified_name: e.src})
WHERE src:File OR src:Function OR src:Method
MATCH (dst {qualified_name: e.dst})
WHERE dst:Function OR dst:Method OR dst:Class
MERGE (src)-[r:CALLS]->(dst)
SET r.weight = e.weight
RETURN count(r) AS created
\end{cgcypher}

\subsection{File Watcher and Incremental Updates}
\label{subsec:watcher-updates}

To support real-time developer workflows, CodeGraph implements an incremental update system through the \texttt{codegraph watch} command. This feature utilizes the \textbf{watchdog} library to run a background monitor that observes file system events within the repository. When a file save event occurs, the monitor triggers an incremental re-indexing routine. This routine first deletes the existing entities associated with the modified file path from the database, then re-parses the source and executes a local version of the two-pass builder to refresh the changed nodes and relationships. This surgical update mechanism allows the graph to remain synchronized with the developer's working tree without the prohibitive latency of a full repository rebuild.

\section{The Retrieval Path}
\label{sec:retrieval-path}
% =============================================================================

The retrieval path is the query-time pipeline that identifies the most relevant code context for a given task. This path involves selecting starting points (seeds) from natural language, reweighting the structural edges of the graph to avoid common hubs, executing the ranking algorithm, and post-processing the results for agent consumption.

\subsection{Seed Selection Pipeline}
\label{subsec:seed-selection}

The retrieval process begins with the construction of a personalization vector that determines where PageRank mass is placed during the random walk. We implement a multi-signal pipeline that extracts seeds using entity name matches, path hints, and BM25 keyword search. A critical challenge in this stage is the "lexical mismatch" between natural language and code identifiers, where a query might mention a concept (e.g., "SQL") that is part of a larger identifier (e.g., \texttt{SQLCompiler}). 

To bridge this gap, the implementation uses the compound tokenization routine shown in \Cref{lst:compound-tokenize}. This logic decomposes camelCase and snake\_case identifiers into individual terms before indexing them for BM25. This allows the system to resolve partial name matches that would otherwise be missed by traditional keyword search. The matched entities from all signals are then combined and normalized such that their weights sum to $1.0$, producing a valid probability distribution for the ranking engine.

To ensure that lexical searches do not dominate structural matches, the seed selection module applies different weight multipliers to each signal before combining them. For example, direct entity name matches receive a higher confidence multiplier than general BM25 text search hits, while path hints are weighted proportionally to their depth in the repository directory tree. By applying L1 normalization to the combined seed vector, the orchestrator guarantees that the GDS library accepts the values as starting probabilities, preventing any single query-time keyword hit from disproportionately biasing the PageRank mass away from nearby structural hubs.

\begin{cgpython}[label=lst:compound-tokenize, unbreakable]{Compound identifier tokenization}
def tokenize(text: str) -> list[str]:
    # Split CamelCase identifiers (e.g., SQLCompiler -> SQL Compiler)
    text = re.sub(r"([a-z0-9])([A-Z])", r"\1 \2", text)
    text = re.sub(r"([A-Z]+)([A-Z][a-z])", r"\1 \2", text)
    # Split on all non-alphanumeric characters (including underscores)
    tokens = re.split(r"[^a-z0-9]+", text.lower())
    return [tok for tok in tokens if len(tok) > 1]
\end{cgpython}

\subsection{Query-Time IDF Edge Reweighting}
\label{subsec:idf-reweighting}

Structural code graphs often contain "sink" nodes—generic utility functions or logging frameworks—that are called from hundreds of locations. Without attenuation, these hubs would absorb a disproportionate share of PageRank probability, diluting the relevance of task-specific code. CodeGraph addresses this by implementing query-time edge reweighting. Before projecting the graph for ranking, the engine calculates an Inverse Document Frequency (IDF) weight for every relationship based on the in-degree of its target node. Using the formula $w_{ij} = 1 / \log_2(\text{in-degree}_j + 2)$, the system automatically weakens the influence of ubiquitous utility nodes, forcing PageRank mass to propagate through more informative structural paths.

\subsection{Personalized PageRank via Neo4j GDS}
\label{subsec:ppr-gds}

CodeGraph utilizes the **Neo4j Graph Data Science (GDS)** library to execute the ranking algorithm. For every query, the engine projects the repository graph into an in-memory representation, incorporating the latest query-time IDF weights and any incremental updates from the file watcher. This projection is modeled as an undirected graph to allow relevance to flow both "downstream" (to dependencies) and "upstream" (to callers), which is essential for capturing the full context of a bug or feature.

The ranking is performed using the uniform restart configuration shown in \Cref{lst:ppr-gds}. By distributing restart mass equally across all seed nodes, the engine lets the topology of the codebase arbitrate final relevance: seeds that are structurally connected to many other task-related nodes will naturally accumulate higher scores, while isolated or erroneous matches will see their probability mass dissipate.

The configuration properties specified in the GDS runtime call directly control the performance and convergence of the random walk. We configure the restart probability (damping factor) to $0.70$, which provides a balanced spread of probability mass without diluting the retrieval focus. The stream operation is executed with a tolerance limit of $0.0001$ or a maximum of $30$ iterations, ensuring that PageRank converges quickly to a stable distribution. This execution is designed to complete in under 50 milliseconds even for massive graphs, matching the response requirements of real-time developer interfaces.

\subsection{Post-Processing and Context Delivery}
\label{subsec:post-processing}

The raw output of the ranking engine is a list of node identifiers and their associated scores. The post-processing module is responsible for transforming this list into a structured context package that is usable by an AI agent or a developer. This stage involves three critical engineering sub-tasks: real-time token counting, file-level deduplication, and dynamic budgeting.

We utilize the **tiktoken** library to calculate the token size of every candidate code snippet in real time, using the same Byte Pair Encoding (BPE) tokenizer employed by the downstream Large Language Models. To maximize information density within the agent's limited context window, the module implements a deduplication policy: if two or more sub-entities (e.g., functions) from the same file appear in the top results, the parent file entity is dropped. This ensures the agent receives precise code spans rather than redundant file-level content. The process continues until the configured token budget—defaulting to 6,000 tokens for agent tools—is exhausted, at which point the system performs \textbf{explanation generation} for each result to provide transparency into the retrieval logic.

\section{User and Agent Interfaces}
\label{sec:user-agent-interfaces}
% =============================================================================

The final layer of the implementation consists of the interfaces through which users and agents interact with CodeGraph. By routing all interfaces through the same orchestrator, the system maintains a consistent "context contract."

\subsection{Command-Line Interface}
\label{subsec:cli-interface}

The CLI, implemented using the \textbf{Typer} library, serves as the primary tool for repository management and manual verification. It provides commands for initializing new projects (\texttt{codegraph init}), building the full index (\texttt{codegraph rebuild}), and executing ranking queries (\texttt{codegraph query}). \Cref{fig:cli-query} illustrates the ranked retrieval output in the terminal, where results are presented with their qualified names, file coordinates, and syntax-highlighted source snippets. This terminal layout allows developers to quickly verify retrieval accuracy and trace the reasoning behind the ranking.

\subsection{Model Context Protocol Server}
\label{subsec:mcp-server}

For autonomous AI assistants, CodeGraph implements a Model Context Protocol (MCP) server using the \textbf{FastMCP} framework. This server communicates via standard input/output and registers a set of tools that allow agents to retrieve context directly from their prompt loops. To sustain the sub-250\,ms query latencies required for seamless agent interaction, the server utilizes an ASGI lifespan context manager. This manager maintains a persistent Neo4j driver and GDS client throughout the server's lifecycle, eliminating the significant connection overhead that would otherwise occur on every tool call. \Cref{fig:mcp-seed-trace} shows the structured seed provenance and metadata returned to the host agent, enabling it to "understand" why certain files were prioritized. This transparency helps the agent trust and attribute the retrieved code context.

\subsection{Interactive Visualizer}
\label{subsec:visualizer}

The interactive visualizer is a browser-based application designed for the inspection and debugging of the code graph. Built with a \textbf{Vite/React} frontend and a \textbf{FastAPI} backend, it uses \textbf{D3.js} to render force-directed visualizations of repository subgraphs. The application supports four core validation workflows: navigation of the repository hierarchy via a file tree, dynamic project switching, visual analysis of PPR probability flow, and a lexical delta comparison that highlights how structural ranking differs from baseline BM25 results. \Cref{fig:visualizer-tree,fig:visualizer-query-results} provide examples of these visual interfaces, which have proven essential for diagnosing missing structural edges and isolating probability sinks during the system's development. By turning the opaque ranking process into an inspectable visual workspace, the visualizer enables developers to build intuition about the graph's topology and the propagation of structural relevance.
