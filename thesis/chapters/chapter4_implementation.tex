\section{System Architecture}
\label{sec:system-architecture}
% =============================================================================

Chapter~3 established the design of CodeGraph's retrieval pipeline. CodeGraph's implementation is governed by a strict system contract: every interface surface must route through a single, deterministic ranking core. The reader will see how the pipeline, from byte-level parsing through graph construction, retrieval, and context delivery, preserves this single path across the CLI, the MCP server, and the interactive visualizer.

We separate stable core logic from user-facing interfaces. Parser and graph modules build the Neo4j representation; retrieval modules select seeds, run PPR, and format context; CLI, MCP, and visualizer modules call the same retrieval pipeline rather than reimplementing ranking logic. \Cref{tab:implementation-modules} summarizes these boundaries.

We follow a conservative engineering policy throughout: prefer deterministic extraction over heuristic guessing, skip ambiguous edges rather than risk false connections, and route every interface through the same retrieval core. Project-wide settings live in \texttt{config.yaml} at the repository root; the Neo4j password is read from \texttt{NEO4J\_PASSWORD} in \texttt{.env} and never stored in the config file. File discovery respects both \texttt{exclude\_patterns} in the config and an optional \texttt{.cgignore} file parsed with the same pathspec rules as \texttt{.gitignore}. The following sections describe each component in the order they execute during indexing and retrieval.

\section{The Parser: Extracting Structure from Code}
\label{sec:the-parser}
% =============================================================================

The foundational stage of CodeGraph is the ingestion pipeline. We transform raw source files into structured entity records that later stages use to build the graph and rank results. The reader will learn what information the parser extracts, how those records are shaped in code, and why those specific fields are the right inputs for graph construction and seed selection.

We use Tree-sitter, an incremental parser accessed through its Python bindings, for extraction. Tree-sitter produces a Concrete Syntax Tree (CST) that maps directly to source byte offsets. This byte-level mapping lets the parser preserve formatting and tolerate syntax errors, which matters in development environments where code is often in an intermediate state.

\noindent For each Python file, the parser executes four steps:
\begin{enumerate}
    \item Read source bytes from disk.
    \item Parse the bytes into a CST with Tree-sitter.
    \item Walk the CST with dedicated extractors to populate a \texttt{FileEntities} container.
    \item Return one \texttt{FileEntities} object per file; a directory walk aggregates the full repository batch.
\end{enumerate}

Rather than indexing every variable assignment or loop, the extractors identify four architectural entities: \texttt{File}, \texttt{Class}, \texttt{Function}, and \texttt{Method}. Parsed values are stored as frozen dataclasses in \texttt{models.py}, which makes them immutable after construction and safe to pass between parsing, resolution, and graph-write stages without accidental mutation. \noindent For each entity, we store the following metadata:
\begin{itemize}
    \item \textbf{Qualified Name (QN):} A globally unique identifier used as the primary node key, formed as \texttt{file\_path::name}. An example is \texttt{auth.py::login} for a top-level function.
    \item \textbf{Line Boundaries:} The start and end line numbers used to extract code snippets for the context package.
    \item \textbf{Signatures and Docstrings:} The textual corpus used for BM25 keyword matching during seed selection.
\end{itemize}

\section{The Resolver: Connecting the Pieces}
\label{sec:the-resolver}
% =============================================================================

Entity extraction produces a set of independent records per file. The resolver converts raw string references into concrete graph edges so that Personalized PageRank can propagate relevance along dependencies. The reader will learn how import and call resolution work, and why we prefer precision over recall when linking entities.

\subsection{Import Resolution}

Import statements declare cross-file dependencies. Our implementation maps Python import strings into physical filesystem paths. For absolute imports, such as \texttt{import core.utils}, the resolver maps the dotted path relative to the project root. For relative imports, such as \texttt{from ..models import User}, it resolves parent directories before mapping. We identify external packages and standard library imports via dependency manifests and intentionally omit them to avoid creating dangling nodes that point outside the repository scope.

\subsection{Call Resolution: The Fallback Protocol}

Linking a function call expression, such as \texttt{verify()}, to the correct definition node in a dynamically typed language like Python requires a conservative strategy. \noindent We use a three-level resolution protocol, executed in descending order of confidence:

\begin{enumerate}
    \item \textbf{Explicit Imports:} We first check the file's import statements. If the called name matches a name imported from another module, we link the call to the corresponding entity in that module.
    \item \textbf{Local Scope:} If no import matches, we search for a function or method defined within the same file. This handles intra-file calls and class-level method invocations.
    \item \textbf{Global Scope:} As a final resort, we query the entire repository index for any entity with a matching name. This broad search captures calls where the import logic is too complex for static analysis.
\end{enumerate}

\subsection{Precision over Recall}

Across all resolution logic, we prefer precision over recall. If a global search finds multiple candidates due to ambiguous naming, such as multiple \texttt{update} methods, the resolver skips the connection. Dropping these ambiguous connections prevents false edges from routing relevance mass into unrelated subgraphs, but it also reduces structural recall. Because Personalized PageRank propagates relevance along every active edge, a single false link can cause severe probability leakage. Dropping ambiguous connections preserves the integrity of the structural traversal at the expense of completeness.

Real-world edge cases support this decoupled approach. The system handles circular imports without recursive loops because it analyzes files independently. Runtime \texttt{importlib} calls, plugin loaders, and dynamically registered modules cannot be resolved statically without execution tracing, so the resolver skips them. This limitation appears in evaluation as well: repositories with plugin-driven architectures, such as pylint-dev/pylint, show higher zero-recall rates because the graph lacks edges to dynamically loaded modules (\cref{sec:eval-synthesis}).

\section{The Database: Storing the Graph}
\label{sec:the-database}
% =============================================================================

After parsing the code and resolving connections, we persist the data into a structural graph. CodeGraph uses Neo4j, a property graph database optimized for relationship-centric storage. This architectural choice allows multi-hop traversals to execute in milliseconds, providing a performance advantage over the recursive joins required by traditional relational databases.

\subsection{Schema and Constraints}

We designed the graph schema to reflect our four-entity model (\texttt{File}, \texttt{Class}, \texttt{Function}, \texttt{Method}). We connect these nodes using four relationship types, as shown in \cref{fig:database-schema}. We use a visual hierarchy where containers (\texttt{File} and \texttt{Class}) are structurally prominent, while functional units (\texttt{Function} and \texttt{Method}) represent the leaf nodes of the hierarchy.

\subsection{Two-Pass Construction: Handling Forward References}

We load the graph in two sequential passes to resolve forward references. We face a sequencing challenge when loading source code into a graph: a function in \texttt{main.py} may call a utility defined in \texttt{utils.py}, but if we process \texttt{main.py} first, the target node does not yet exist and the relationship creation fails.

\noindent We resolve this with a two-pass loading mechanism:
\begin{enumerate}
    \item \textbf{Pass 1 (Entity and Containment):} We traverse the entire repository and create all structural nodes (\texttt{File}, \texttt{Class}, \texttt{Function}, and \texttt{Method}) together with their intra-file \texttt{CONTAINS} edges. By the end of this pass, every possible entity exists as a unique node in the database with its local structure intact.
    \item \textbf{Pass 2 (Cross-File Edges):} With the complete node population in place, we execute a second pass to add \texttt{IMPORTS}, \texttt{CALLS}, and \texttt{INHERITS\_FROM} edges, safely linking nodes whose definitions may span multiple files.
\end{enumerate}

We execute all database writes using parameterized Cypher queries with batched \texttt{UNWIND} and \texttt{MERGE} clauses. This approach ensures idempotency: if we re-process a file, the system updates existing properties rather than creating duplicate nodes. Listing~\ref{lst:cypher-merge} demonstrates the MERGE pattern for both node and relationship creation.

\begin{cglistingfigure}
\begin{cgcypher}{Neo4j write pattern}
// Pass 1: nodes (idempotent)
UNWIND $nodes AS node
MERGE (n:Function
  {qualified_name: node.qn})
  ON CREATE SET n.file_path = node.path
  ON MATCH  SET n.file_path = node.path

// Pass 2: relationships
UNWIND $edges AS rel
MATCH (a {qualified_name: rel.source}),
      (b {qualified_name: rel.target})
MERGE (a)-[:CALLS]->(b)
\end{cgcypher}
\captionof{lstlisting}{Cypher pattern for idempotent two-pass construction using MERGE.}
\label{lst:cypher-merge}
\end{cglistingfigure}

\subsection{Incremental Updates}

Full re-indexing via \texttt{codegraph rebuild} clears the graph and re-parses the entire repository. For day-to-day development, \texttt{codegraph watch} monitors the filesystem and applies incremental updates through \texttt{update\_file\_in\_graph} in \texttt{incremental.py}. For each changed file, the watcher deletes all existing entities for that path, re-parses the file, and writes the new entity batch through the same two-pass \texttt{build\_graph} path used during a full rebuild. This keeps the graph consistent with the working tree without requiring a full re-index on every save.

\subsection{GDS Projection}

Standard Cypher queries operate on the transactional database. However, executing graph algorithms like PageRank over millions of edges requires an in-memory representation. We use the Neo4j Graph Data Science (GDS) library to create an optimized undirected projection of the underlying graph. This projection allows the ranking algorithm to navigate bidirectionally, identifying both dependencies and their usage. We drop and recreate this projection on every query to ensure it incorporates query-time IDF weights and reflects the latest state of the repository.

\section{The Engine: Ranking with PageRank}
\label{sec:the-engine}
% =============================================================================

When an AI agent requests context, the implementation invokes the retrieval orchestrator \texttt{run\_core\_retrieval}. The reader will learn how seeds are extracted, how edge weights are adjusted, and how the pipeline hands ranked entities to post-processing.

\noindent The orchestrator executes the following steps on every query:
\begin{enumerate}
    \item Build or reuse a BM25 index over searchable entity metadata.
    \item Extract seed nodes from the task description and normalize them into a personalization vector.
    \item Apply query-time IDF reweighting to edge properties in Neo4j.
    \item Drop and recreate the GDS projection with the updated weights.
    \item Run Personalized PageRank and return ranked \texttt{PPRResult} records.
\end{enumerate}

All CLI, MCP, and visualizer entry points call this function; no interface reimplements seed selection or PPR locally.

\subsection{Seed Extraction and Personalization Vector}

The ranking process begins with seed extraction, which bridges the semantic gap between natural language task descriptions and the structured code graph. We identify initial entry points (seeds) and construct a personalization vector by combining three complementary signals defined in \texttt{seed\_selection.py}:
\begin{itemize}
    \item \textbf{Entity Match:} Regex extraction identifies code identifiers, such as \texttt{AuthError}, in the prompt, matching them directly to graph nodes.
    \item \textbf{BM25 Search:} The engine executes a keyword search against an expanded corpus of entity names, file paths, signatures, and docstrings.
    \item \textbf{Issue Path Hint:} File paths or directory fragments mentioned in the task add weak location evidence.
\end{itemize}

These signals are summed using configurable weights from \texttt{config.yaml} (defaults: entity match 0.6, BM25 0.3, issue hint 0.2) and normalized into a probability distribution that sums to 1.0. The implementation stores both the seed weight and its source, allowing later explanations to report whether a result came from an entity match, a path hint, or BM25. The MCP surface still accepts \texttt{current\_file} for compatibility, but the retrieval pipeline ignores it because the active editor location was not a reliable relevance signal.

Compound tokenization is the key lexical mechanism that connects issue text to code identifiers. Listing~\ref{lst:compound-tokenize} shows how camel-case and snake-case identifiers are split before BM25 indexing, which allows a query mentioning ``compiler'' to match an entity named \texttt{SQLCompiler}.

\begin{cglistingfigure}
\begin{cgpython}{Compound tokenization (seed\_selection.py)}
def tokenize(text: str) -> list[str]:
    # Split CamelCase: "SQLCompiler" -> "sql compiler"
    text = re.sub(r"([a-z0-9])([A-Z])", r"\1 \2", text)
    text = re.sub(r"([A-Z]+)([A-Z][a-z])", r"\1 \2", text)
    tokens = re.split(r"[^a-z0-9]+", text.lower())
    return [tok for tok in tokens if len(tok) > 1]
\end{cgpython}
\captionof{lstlisting}{BM25 tokenization with compound identifier splitting.}
\label{lst:compound-tokenize}
\end{cglistingfigure}

\subsection{Query-Time IDF Reweighting}

Before running the traversal, we must mitigate the influence of hub nodes: highly connected helper functions that absorb excessive relevance mass during the random walk and obscure domain-specific logic.

To address this challenge, we implement a query-time Inverse Document Frequency (IDF) reweighting step. Prior to building the GDS projection, a Cypher update calculates the in-degree for every target node. We adjust the weight of an incoming edge $(i, j)$ using an inverse-logarithmic formula:
\begin{equation}
    w_{ij} = \frac{1}{\log_2(\text{in-degree}_j + 2)}
\end{equation}
Consequently, highly connected utility nodes receive lower edge weights than specialized domain methods. A logging helper such as \texttt{logger.info} is penalized more heavily than a domain-specific method. This attenuation prevents relevance mass from pooling in generic nodes and concentrates it on task-specific code.

\subsection{PPR Execution}

With the personalization vector constructed and the weighted GDS graph projected, the engine invokes Personalized PageRank through Neo4j GDS. The production configuration uses uniform restart, damping factor $0.70$, and \texttt{top\_k = 30}. The final output is a list of code entities ranked by their relevance score, which post-processing turns into source snippets for the caller.

\section{Post-Processing and Context Packaging}
\label{sec:post-processing}
% =============================================================================

Once Personalized PageRank identifies the highest-ranked entities, we transform these abstract graph nodes into a formatted text package. A strict, token-aware greedy algorithm governs this construction process in the post-processing module. The reader will learn how the system respects a fixed token budget while maximizing information density.

We use a local Byte Pair Encoding (BPE) tokenizer to calculate the token count of every candidate code snippet in real time. The construction loop iterates through the ranked results, reading raw source code from the filesystem based on the line boundaries stored in the graph. \noindent To maximize the information density of the final package, we apply two primary filters:
\begin{itemize}
    \item \textbf{File-Level Deduplication:} If the top results contain two or more sub-entities (functions or methods) from the same file, we drop the parent \texttt{File} node to avoid wasting the token budget on the entire file's content. We retain the individual, highly relevant sub-entity snippets instead.
    \item \textbf{Dynamic Budgeting:} We maintain a running sum of tokens during package construction. If adding the next ranked entity would exceed the token budget (default $6{,}000$ tokens for MCP calls), we skip that entity and finalize the context package.
\end{itemize}

When explanation mode is enabled (the MCP default), the \texttt{explanations} module attaches a seed provenance trace and a short structural reasoning path to each result. The CLI exposes the same metadata through \texttt{codegraph explain} and \texttt{codegraph query --trace}.

\section{User and Agent Interfaces}
\label{sec:the-interface}
% =============================================================================

We expose the retrieval pipeline through three distinct interfaces, each tailored to a different operational workflow: an agent-facing Model Context Protocol server, a command-line interface for local queries and scripting, and an interactive visualizer for topological debugging. While each interface serves a different environment, they all route their queries through \texttt{run\_core\_retrieval}.

\subsection{Model Context Protocol Server}
\label{subsec:mcp-server}

We implement the server using the FastMCP Python framework, which provides a high-level abstraction over the JSON-RPC 2.0 communication layer. By default, the server communicates with the host application via Standard Input/Output (stdio). This transport layer ensures that the server can run as a lightweight subprocess, minimizing the resource footprint on the developer's machine.

The implementation exposes exactly two tools, matching the MCP contract described in \cref{sec:tool-interface}. The primary tool runs the retrieval pipeline and returns ranked source snippets. The second tool performs targeted structural lookup for known entities, including dependency traversal, symbol search, and class hierarchy queries. FastMCP registers both tools through Python decorators and derives the JSON-RPC schemas from their type annotations.

To sustain sub-250\,ms query latencies, the server must avoid the overhead of re-establishing database connections for every reasoning step. We initialize a persistent Neo4j driver and GDS client through a FastMCP lifespan context manager. The server maintains this state throughout its lifecycle. When an agent invokes a tool, the engine reuses the connection pool but drops and recreates the GDS projection on every query to incorporate query-time IDF weights, as shown in Listing~\ref{lst:mcp-server-impl}.

\begin{cglistingfigure}
\begin{cgpython}{MCP server registration (server.py, simplified)}
from contextlib import asynccontextmanager
from mcp.server.fastmcp import Context, FastMCP
from codegraph.mcp.tools import (
    get_relevant_context_impl,
    query_dependencies_impl,
)

@asynccontextmanager
async def _lifespan(server: FastMCP):
    state = ServerStateFactory().create()
    try:
        yield state
    finally:
        ServerStateFactory.shutdown()

mcp = FastMCP("codegraph", lifespan=_lifespan)

@mcp.tool()
def get_relevant_context(
    task_description: str,
    mentioned_entities: list[str] | None,
    top_k: int,
    token_budget: int,
    ctx: Context,
) -> str:
    state = ctx.request_context.lifespan_context
    return get_relevant_context_impl(
        task_description,
        mentioned_entities,
        None,
        top_k,
        token_budget,
        state,
    )
\end{cgpython}

\subsection{Error Handling and Feedback Loops}
\label{subsec:error-handling}

The implementation returns explicit error payloads instead of silent empty context. If the graph is empty, the response includes a rebuild hint and may trigger a background re-index. If Neo4j or GDS is unreachable, the response points the user to \texttt{codegraph doctor}. If no relevant result is found after retrieval, the agent still receives structured metadata with \texttt{result\_count: 0} and can retry with more specific \texttt{mentioned\_entities}. This design keeps retrieval failures diagnosable without replaying an LLM sample, which matters both for interactive use and for reproducible evaluation.

\subsection{Command-Line Interface}

\subsection{Interactive Visualizer}
\label{subsec:visualizer}

The interactive visualizer offers a graphical environment for debugging and inspecting graph topologies. The visualizer is not a separate retrieval algorithm; it is a debugging and demonstration interface over the same graph and retrieval pipeline used by the CLI and MCP tools.

The primary visualization pane renders the repository structure as a force-directed graph served on port 8474 by default. Nodes represent parsed entities and edges represent relationships such as \textsc{contains}, \textsc{calls}, and \textsc{imports}. The left sidebar supports both file browsing and natural-language queries; the right panel switches between source code, inspector metadata, ranked results, and seed explanations. The Explain panel mirrors \texttt{codegraph explain}: it shows which seeds were selected and how PPR propagated relevance through the graph. These views are useful when diagnosing why a query succeeded or failed, but they remain supporting tools rather than part of the retrieval algorithm itself.
