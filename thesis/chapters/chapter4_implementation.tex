\chapter{Implementation}
\label{ch:implementation}

This chapter shows how the design established in \cref{ch:design} is realized as a working system. The implementation is organized around two functional flows: the \textbf{indexing path}, which builds the structural model from source code, and the \textbf{retrieval path}, which traverses that model to select context for a specific task. A strict system contract enforces that every interface surface, whether CLI, MCP server, or visualizer, routes through a single, deterministic ranking core. The following sections describe each component in the order it executes, from source parsing through context delivery.

% =============================================================================
\section{System Architecture}
\label{sec:system-architecture}
% =============================================================================

The implementation is governed by a single contract: every interface must route through the same ranking core. This contract has three concrete manifestations that together provide trust and transparency:
\begin{enumerate}
    \item \textbf{Seed Provenance:} Every retrieved entity identifies which seeds (entity names or text matches) triggered its selection.
    \item \textbf{Traceable Paths:} The system exposes the structural relationship between the task description and the retrieved code via the \texttt{explain} interface.
    \item \textbf{Shared Retrieval Core:} All interfaces route through the same ranking logic, ensuring identical behavior across tools.
\end{enumerate}

We separate stable core logic from user-facing interfaces. Parser and graph modules manage the indexing path; retrieval modules manage the retrieval path by selecting seeds, running PPR, and formatting context. \Cref{tab:implementation-modules} summarizes these boundaries.

The implementation adheres to a deliberately narrow scope: CodeGraph is a \textbf{Python-first, agent-oriented} retrieval system that provides structurally precise context for a single repository. This focus allows the system to prioritize deterministic extraction over heuristic guessing.

\section{The Parser: Extracting Structure from Code}
\label{sec:the-parser}
% =============================================================================

The indexing path begins with entity extraction. The implementation challenge is producing structured records from code that may be syntactically incomplete, since files under active development often contain errors that would halt a traditional compiler-based parser.

We use Tree-sitter, an incremental parser accessed through its Python bindings, for extraction. Tree-sitter produces a Concrete Syntax Tree (CST) that maps directly to source byte offsets. This byte-level mapping lets the parser preserve formatting and tolerate syntax errors, which matters in development environments where code is often in an intermediate state.

\noindent For each Python file, the parser executes four steps:
\begin{enumerate}
    \item Read source bytes from disk.
    \item Parse the bytes into a CST with Tree-sitter.
    \item Walk the CST with dedicated extractors to populate a \texttt{FileEntities} container.
    \item Return one \texttt{FileEntities} object per file; a directory walk aggregates the full repository batch.
\end{enumerate}

Rather than indexing every variable assignment or loop, the extractors identify four architectural entities: \texttt{File}, \texttt{Class}, \texttt{Function}, and \texttt{Method}. Parsed values are stored as frozen dataclasses in \texttt{models.py}, which makes them immutable after construction and safe to pass between parsing, resolution, and graph-write stages without accidental mutation. \noindent For each entity, we store the following metadata:
\begin{itemize}
    \item \textbf{Qualified Name (QN):} A globally unique identifier used as the primary node key, formed as \texttt{file\_path::name}. An example is \texttt{auth.py::login} for a top-level function.
    \item \textbf{Line Boundaries:} The start and end line numbers used to extract code snippets for the context package.
    \item \textbf{Signatures and Docstrings:} The textual corpus used for BM25 keyword matching during seed selection.
\end{itemize}

The parser ignores local implementation details and stores only the metadata needed by later stages: identity, location, signatures, and docstrings. Standard-library imports are filtered during extraction so they do not create dangling nodes that point outside the repository scope. If a file contains syntax errors, Tree-sitter still produces a partial tree; the extractors skip unrecoverable nodes and continue, which keeps indexing robust during active development.

\section{The Resolver: Connecting the Pieces}
\label{sec:the-resolver}
% =============================================================================

Entity extraction produces independent records per file, but Personalized PageRank requires a connected graph. The resolver converts raw string references into concrete graph edges by determining which definition each import statement and call expression refers to.

The design rationale for the resolution strategy is established in \cref{sec:import-resolution,sec:call-resolution}: import strings are mapped to filesystem paths, calls are resolved through a three-level protocol (explicit imports, local scope, global scope), and ambiguous references are omitted to preserve graph precision. This section describes how the implementation realizes that strategy.

\subsection{Import Resolution}

Import statements declare cross-file dependencies. The resolver maps Python import strings to physical filesystem paths. For absolute imports, such as \texttt{import core.utils}, it maps the dotted path relative to the project root. For relative imports, such as \texttt{from ..models import User}, it resolves parent directories before mapping. External packages and standard-library imports are identified via dependency manifests and omitted to avoid creating dangling nodes that point outside the repository.

\subsection{Call Resolution}

Linking a function call expression to the correct definition node in a dynamically typed language requires the conservative three-level protocol from \cref{sec:call-resolution}. When the global scope search yields multiple candidates due to ambiguous naming, the resolver drops the connection rather than guessing. This precision-first policy means some duck-typed calls and ambiguous references remain absent from the graph, but it prevents false edges from misdirecting PPR probability mass. Parser-specific edge cases such as dynamic module loading are discussed in \cref{sec:parser-limitations}; broader design limitations are summarized in \cref{sec:design-limitations}.

\section{The Database: Storing the Graph}
\label{sec:the-database}
% =============================================================================

With entities extracted and references resolved, the graph must be persisted to Neo4j. The core implementation challenge is ordering: a function in one file may call a definition in another, and if that target node does not yet exist, the relationship write fails.

\subsection{Schema and Constraints}

The graph schema reflects the four-entity model from \cref{sec:graph-schema}: \texttt{File}, \texttt{Class}, \texttt{Function}, and \texttt{Method} nodes connected by four relationship types. \Cref{fig:database-schema} shows the schema as implemented.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{assets/database_schema.png}
    \caption[Graph database schema]{Neo4j schema used in CodeGraph. Files and classes are containers; functions and methods are leaves. Structural edges (\textsc{contains}, \textsc{imports}, \textsc{inherits\_from}) and behavioral \textsc{calls} edges are stored separately.}
    \label{fig:database-schema}
\end{figure}

Database constraints enforce the identity rules from \cref{ch:design}. A uniqueness constraint on \texttt{qualified\_name} prevents duplicate entities during repository updates. Indexes on \texttt{file\_path} and \texttt{name} accelerate the lookups used during seed selection.

\subsection{Two-Pass Construction: Handling Forward References}

We load the graph in two sequential passes to resolve forward references. A function in \texttt{main.py} may call a utility defined in \texttt{utils.py}, but if we process \texttt{main.py} first, the target node does not yet exist and the relationship creation fails.

\noindent We resolve this with a two-pass loading mechanism:
\begin{enumerate}
    \item \textbf{Pass 1 (Entity and Containment):} We traverse the entire repository and create all structural nodes (\texttt{File}, \texttt{Class}, \texttt{Function}, and \texttt{Method}) together with their intra-file \texttt{CONTAINS} edges. By the end of this pass, every possible entity exists as a unique node in the database with its local structure intact.
    \item \textbf{Pass 2 (Cross-File Edges):} With the complete node population in place, we execute a second pass to add \texttt{IMPORTS}, \texttt{CALLS}, and \texttt{INHERITS\_FROM} edges, safely linking nodes whose definitions may span multiple files.
\end{enumerate}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{assets/two_pass_sequence.png}
    \caption[Two-pass graph construction sequence]{Two-pass Neo4j loading. Pass~1 creates all entity nodes and intra-file \textsc{contains} edges. Pass~2 adds cross-file \textsc{imports}, \textsc{calls}, and \textsc{inherits\_from} edges once every target node exists.}
    \label{fig:two-pass-sequence}
\end{figure}

We execute all database writes using parameterized Cypher queries with batched \texttt{UNWIND} and \texttt{MERGE} clauses. This approach ensures idempotency: if we re-process a file, the system updates existing properties rather than creating duplicate nodes. Listing~\ref{lst:cypher-merge} demonstrates the MERGE pattern for both node and relationship creation.

\subsection{Incremental Updates}

Full re-indexing via \texttt{codegraph rebuild} clears the graph and re-parses the entire repository. For day-to-day development, \texttt{codegraph watch} monitors the filesystem and applies incremental updates through \texttt{update\_file\_in\_graph} in \texttt{incremental.py}. For each changed file, the watcher deletes all existing entities for that path, re-parses the file, and writes the new entity batch through the same two-pass \texttt{build\_graph} path used during a full rebuild. This keeps the graph consistent with the working tree without requiring a full re-index on every save.

\subsection{GDS Projection}

Standard Cypher queries operate on the transactional database. However, executing graph algorithms like PageRank over millions of edges requires an in-memory representation. We use the Neo4j Graph Data Science (GDS) library to create an optimized undirected projection of the underlying graph. This projection allows the ranking algorithm to navigate bidirectionally, identifying both dependencies and their usage. We drop and recreate this projection on every query to ensure it incorporates query-time IDF weights and reflects the latest state of the repository.

\section{The Engine: Ranking with PageRank}
\label{sec:the-engine}
% =============================================================================

When an agent requests context, the system invokes \texttt{run\_core\_retrieval}, the single orchestrator for the retrieval path. This function guarantees that every interface executes the same seed-selection, IDF-reweighting, and PPR ranking logic.

\noindent The orchestrator executes the following steps on every query:
\begin{enumerate}
    \item Build or reuse a BM25 index over searchable entity metadata.
    \item Extract seed nodes from the task description and normalize them into a personalization vector.
    \item Apply query-time IDF reweighting to edge properties in Neo4j.
    \item Drop and recreate the GDS projection with the updated weights.
    \item Run Personalized PageRank and return ranked \texttt{PPRResult} records.
\end{enumerate}

All CLI, MCP, and visualizer entry points call this function; no interface reimplements seed selection or PPR locally.

\subsection{Seed Extraction and Personalization Vector}
\label{subsec:seed-extraction}

Seed extraction translates a natural-language task description into starting points in the code graph. The design of the three seed signals (entity match, BM25, and path hints) and their combination into a personalization vector is established in \cref{sec:seed-selection}. The implementation contributes two mechanisms that matter for retrieval quality.

First, the implementation stores both the seed weight and its provenance source with each seed node. This metadata allows the \texttt{explain} interface to report whether a result was triggered by an entity match, a path hint, or BM25, supporting the transparency guarantee from \cref{sec:system-architecture}. \Cref{fig:mcp-seed-extraction} shows a representative MCP tool response where the agent receives not only the ranked results but also a trace of how each seed was extracted, from entity matching through BM25 to vector construction.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{assets/mcp_tool_response.png}
    \caption[MCP seed extraction trace]{MCP tool response detailing the seed extraction process for a query about seed extraction implementation. The structured output shows the three extraction phases, the normalization step, and how the personalization vector is consumed by PPR.}
    \label{fig:mcp-seed-extraction}
\end{figure}

Second, compound tokenization is the key lexical mechanism that connects issue text to code identifiers. Camel-case and snake-case identifiers are split before BM25 indexing, which allows a query mentioning ``compiler'' to match an entity named \texttt{SQLCompiler}.

\subsection{Query-Time IDF Reweighting}

IDF-based edge reweighting (\cref{sec:idf-reweighting}) attenuates edges toward highly connected hub nodes so that PPR probability concentrates on task-specific code rather than generic utilities. The implementation realizes this as a Cypher update executed before each GDS projection: for every edge $(i, j)$, the weight is set to $1/\log_2(\text{in-degree}_j + 2)$. Because this update runs at query time, the weights always reflect the current state of the graph, including any incremental changes since the last full rebuild.

\subsection{PPR Execution}

With the personalization vector constructed and the weighted GDS graph projected, the engine invokes Personalized PageRank through Neo4j GDS. The production configuration uses uniform restart, damping factor $0.70$, and \texttt{top\_k = 30}. The final output is a list of code entities ranked by their relevance score, which post-processing turns into source snippets for the caller.

\section{Post-Processing and Context Delivery}
\label{sec:implementation-post-processing}
% =============================================================================

PPR returns a ranked list of graph nodes, but an agent needs source code, not node identifiers. Post-processing bridges this gap by reading code from disk, enforcing a token budget, and packaging the result as structured JSON.

We use a local Byte Pair Encoding (BPE) tokenizer to calculate the token count of every candidate code snippet in real time. The construction loop iterates through the ranked results, reading raw source code from the filesystem based on the line boundaries stored in the graph. \noindent To maximize the information density of the final package, we apply two primary filters:
\begin{itemize}
    \item \textbf{File-Level Deduplication:} If the top results contain two or more sub-entities (functions or methods) from the same file, we drop the parent \texttt{File} node to avoid wasting the token budget on the entire file's content. We retain the individual, highly relevant sub-entity snippets instead.
    \item \textbf{Dynamic Budgeting:} We maintain a running sum of tokens during package construction. If adding the next ranked entity would exceed the token budget (default $6{,}000$ tokens for MCP calls), we skip that entity and finalize the context package.
\end{itemize}

When explanation mode is enabled (the MCP default), the \texttt{explanations} module attaches a seed provenance trace and a short structural reasoning path to each result. This trace identifies which seeds triggered the result and through which graph edges the relevance propagated. The CLI exposes the same metadata through \texttt{codegraph explain} and \texttt{codegraph query --trace}.

\section{User and Agent Interfaces}
\label{sec:the-interface}
% =============================================================================

The system exposes the retrieval pipeline through three thin interfaces: a Model Context Protocol (MCP) server, a command-line interface (CLI), and an interactive visualizer. Rather than reimplementing ranking logic, each interface delegates all context requests to \texttt{run\_core\_retrieval}. 

\subsection{Model Context Protocol Server}
\label{subsec:mcp-server}
The primary agent interface is a FastMCP server running over Standard Input/Output. To sustain sub-250\,ms query latencies, the server avoids re-establishing database connections per query by initializing a persistent Neo4j driver and GDS client through a lifespan context manager. It registers exactly two tools: one for retrieving ranked context and one for targeted structural lookups. Both tools translate JSON-RPC requests directly into \texttt{run\_core\_retrieval} arguments.

\subsection{Command-Line Interface}
\label{subsec:cli-interface}
The CLI, built with Typer, provides local evaluation and scripting access. The \texttt{codegraph query} command executes the standard \textbf{retrieval path} and prints ranked entities with their qualified names, line ranges, token counts, and inline source snippets. \Cref{fig:cli-query} shows a representative query. Callers can request machine-readable JSON or append \texttt{--trace} to emit a structured provenance trace detailing seed selection weights and PPR propagation paths. The \texttt{codegraph explain} command further enhances transparency by providing a human-readable summary of why specific code was retrieved.

\subsection{Interactive Visualizer}
\label{subsec:visualizer}

The interactive visualizer is the most inspection-oriented interface in CodeGraph. Whereas the MCP server and CLI primarily return ranked context, the visualizer exposes the retrieval process itself as an interactive workspace for exploration, debugging, and explanation. We implement it as a browser-based React frontend with D3.js-based graph rendering, but it does not introduce a separate retrieval path. Like the other interfaces, it delegates all context requests to \texttt{run\_core\_retrieval}, so every graph view, seed list, and ranked result corresponds to the same production \textbf{retrieval path} described earlier in this chapter.

The interface supports two closely related workflows. In browse-and-inspect mode (\Cref{fig:visualizer-interface}), the left panel presents a searchable repository file tree together with summary counts for indexed files and entities, while the center panel renders the local structural neighbourhood of the selected file. This view allows us to inspect the topology of a module, identify its nearby entities, and navigate the repository visually rather than only through paths or terminal output. The graph view also includes zoom controls and a legend, which make the visual encoding readable even when the visible neighbourhood contains several node and edge types.

In query-and-analysis mode (\Cref{fig:visualizer-query-results}), the same interface becomes a retrieval-analysis surface. The query panel accepts a natural-language task description and exposes retrieval controls such as the result budget, token budget, and the extracted seed list with per-seed scores. After a query is executed, the center panel shows the propagated subgraph reached from those seeds, and the right panel presents ranked entities together with their PPR scores. The retrieval-comparison panel further distinguishes structural, lexical, and delta views, which allows us to compare the final graph-based ranking against its lexical baseline rather than treating the PPR output as an opaque score list.

This design makes the visualizer valuable for transparency. The interface shows not only what was retrieved, but also why it was retrieved. Seed nodes are listed explicitly, the propagated subgraph reveals the region through which relevance mass flowed, and the ranked-results panel reports each entity's structural score together with baseline lexical information. In practice, this supports three kinds of diagnosis: we can see when retrieval succeeds because structurally connected entities reinforce one another; we can identify cases where lexical seeds exist but the graph does not provide a strong path to the target region; and we can detect when a result is present mainly because of lexical matching rather than structural support. The visualizer therefore operationalizes the system contract from \cref{sec:system-architecture} by turning seed provenance, structural paths, and ranking outcomes into inspectable interface elements rather than hidden intermediate state.

Although the visualizer is not intended to be a full graph-database client, it still needs to remain responsive on repository graphs that are too large to inspect as raw node tables. D3.js manages layout, zooming, and node positioning at the interaction layer, while the frontend keeps the visual encoding deliberately compact: node appearance communicates entity type, edge styling communicates structural role, and non-essential details are pushed into side panels rather than rendered directly into the graph. Because the visualizer attaches to the same retrieval core as the other interfaces, it also serves as a research instrument for validating interpretability and trustworthiness. We use it to debug seed selection failures, diagnose missing structural edges, and identify cases where probability mass concentrates in an unhelpful region of the graph.

\section{Summary}
\label{sec:summary}
% =============================================================================

This chapter described how CodeGraph translates its pipeline design into a working system. The indexing path uses Tree-sitter's byte-level parsing and two-pass graph construction to build a structural model that tolerates syntax errors and handles forward references through idempotent MERGE writes. The retrieval path uses dynamic seed extraction, query-time IDF reweighting, and Personalized PageRank to rank code entities, then packages the results within a token budget for agent consumption.

A single shared execution function (\texttt{run\_core\_retrieval}) guarantees that all three interfaces produce identical results. This is the implementation's central contribution: the system contract from \cref{sec:system-architecture} is enforced in code, not just in documentation. \Cref{ch:evaluation} evaluates how effectively this implementation retrieves the correct files on the SWE-bench Lite benchmark.
