\section{Results and Analysis}
\label{sec:results}

We evaluate CodeGraph on the 300 instances of SWE-bench Lite. We first compare CodeGraph against lexical and structural baselines to isolate the value of global graph ranking. We then examine sensitivity to restart strategy and candidate budget, report runtime measurements together with the experimental environment, and finally interpret the remaining failures through the lens of structural reachability.

\subsection{Quantitative Performance}

The main result of Table~\ref{tab:main-results} is that CodeGraph reaches 74.0\% Recall@10 at the main operating point, $k=30$, substantially improving over the strongest lexical baseline while preserving a deterministic retrieval pipeline. These results place the final score within a coherent performance trajectory rather than presenting it as an isolated endpoint.

The strongest lexical baseline, BM25-only (Seed-Engineered Lexical Baseline), achieves 58.0\% Recall@10 and an MRR of 0.354. By contrast, a naive one-hop ego-graph expansion reaches only 51.0\% Recall@10, showing that structural context alone is not sufficient when it is expanded without a ranking mechanism. CodeGraph’s gain therefore does not come from merely appending neighboring nodes, but from ranking structurally reachable files through Personalized PageRank.

The initial graph-ranking configuration, which uses a confidence-weighted restart distribution, reaches 68.0\% Recall@10. Switching to a uniform restart distribution raises performance to 74.0\% Recall@10 at $k=30$, reducing the zero-recall count from 96 to 78. This result suggests that lexical confidence scores are too brittle to control restart mass directly. Under repository ambiguity, allowing structural connectivity to determine where relevance mass accumulates produces a more reliable ranking.

At the main operating point, CodeGraph improves over the BM25-only (Seed-Engineered Lexical Baseline) by 16.0 percentage points in Recall@10, from 58.0\% to 74.0\%. Expanding the candidate pool to $k=50$ yields a smaller additional gain to 75.7\%; we therefore report it as a sensitivity setting rather than as the main operating point. Relative to the earliest 42.0\% baseline, the final 74.0\% operating point reflects three sequential gains: +18.7 percentage points from uniform restart, +11.6 points from seed engineering, and +1.7 points from increasing the candidate pool to the final $k=30$ setting. Taken together, these results support a simple interpretation: lexical matching is necessary to place initial seeds, but deterministic global structural ranking is what converts those seeds into high-recall repository retrieval.

The trajectory from the basic lexical foundation to the final configuration is defined by three sequential observations:
\begin{itemize}
    \item The final $k=30$ operating point reaches 74.0\% Recall@10.
    \item One-hop expansion underperforms BM25, proving structural filtering is required.
    \item Uniform restart materially outperforms weighted restart.
\end{itemize}

\subsection{Practicality and Sensitivity}

CodeGraph is designed as a deterministic retrieval layer for interactive coding workflows, so latency and reproducibility matter alongside accuracy. All runtime measurements were collected in a single reported evaluation environment: Apple M4 MacBook Pro, 16.0 GB RAM, macOS, Python 3.12.13, and Neo4j 2026.04.0. Across the full benchmark run of 4,200 query instances, CodeGraph achieved a median latency of 0.27s, a mean latency of 0.71s, and a P95 latency of 2.05s. These results indicate that the retrieval pipeline remains fast and predictable enough for interactive use, while remaining deterministic and free of retrieval-time API calls.

Table~\ref{tab:runtime-stats} reports repository statistics together with indexing cost and query latency. Across the tested repositories, indexing remains under one minute and median query latency remains below 210ms, which supports the practical single-machine profile of the system.

We also evaluated context-constrained retrieval by measuring whether the target file fits within fixed token budgets when files are added in ranked order. Context-constrained recall increases from 21.0\% at 2,000 tokens to 49.0\% at 10,000 tokens, showing that a substantial fraction of successful retrievals can be delivered within relatively small context windows. The remaining gap relative to Recall@10 highlights a practical limitation of file-level retrieval: some correct targets are ranked highly but reside in files that exceed tight context budgets.

We also tested sensitivity to candidate pool size and damping factor. Performance increases from 68.7\% Recall@10 at $k=10$ to 74.0\% at $k=30$, and then to 75.7\% at $k=50$, indicating that broader candidate coverage can recover a small number of additional reachable targets. By contrast, the damping sweep is comparatively stable: Recall@10 varies from 72.7\% at $\alpha=0.30$ to 74.0\% at $\alpha=0.70$, suggesting that CodeGraph is not highly sensitive to this parameter within the tested range.

\subsection{The Reachability Bottleneck}

A defining characteristic of the final CodeGraph configuration is its polarized rank distribution: target files are usually retrieved in the top-5 or missed beyond the top-10. At the $k=30$ operating point, 65.0\% of instances place the target file within the top-5, while only 9.0\% fall into the intermediate ranks 6 to 10 and the remaining 78 cases fall outside the top-10. Figure~\ref{fig:bimodal} reports this distribution for the final system, aligning the reachability argument with the main reported operating point.

This bimodal pattern supports our central empirical diagnosis: the retrieval ceiling is determined primarily by reachability rather than by fine-grained reranking among already retrieved candidates. If the system places seeds in the correct structural neighborhood, Personalized PageRank tends to rank the target file highly. Zero-recall failures occur when the target file lies outside the reachable subgraph induced by the extracted seeds.

This observation highlights an important boundary condition of the method. In the current $k=30$ operating point, CodeGraph still produces 78 zero-recall cases, divided between Connectivity Gaps and Semantic Gaps. The distribution of these failures clarifies that retrieval quality is bounded by whether the initial lexical signals can place probability mass into a structurally connected region of the repository.

\subsection{Qualitative Retrieval Cases}

\textbf{Success Case (Structural Amplification):} In \textit{matplotlib/matplotlib-23562}, the bug report requests support for a new 3D surface attribute and includes a traceback pointing to \texttt{art3d.py}. The lexical index identifies \texttt{Poly3DCollection} as a strong seed but also extracts noisy generic terms like \texttt{color} and \texttt{facecolors} across dozens of unrelated files. In a purely lexical baseline, the target file \texttt{lib/mpl\_toolkits/mplot3d/art3d.py} is ranked at position 31. During structural propagation, CodeGraph dissipates the probability mass of generic seeds across disconnected utility modules, while the specific \texttt{Poly3DCollection} seed propagates mass locally through direct \texttt{CALLS} and \texttt{INHERITS\_FROM} edges. The target file absorbs this structural signal and is ranked at position 1, demonstrating the system's ability to filter lexical noise through graph structure.

\textbf{Failure Case (Semantic Gap):} In \textit{django/django-10914}, the bug report requests changing the default value of the \texttt{FILE\_UPLOAD\_PERMISSIONS} setting. The issue uses conceptual terms like ``tempfile'' and ``permissions'' that match several functional modules (e.g., \texttt{storage.py}, \texttt{uploadedfile.py}), which are selected as lexical seeds. However, the target fix is in the global configuration hub, \texttt{django/conf/global\_settings.py}. Because this configuration file contains only constant definitions and lacks incoming structural dependency edges from the functional seeds, Personalized PageRank cannot propagate relevance to the target. This failure is therefore not only a lexical mismatch, but also a schema limitation: because configuration constants are not modeled as first-class graph entities, entity matching and structural propagation cannot directly represent the symbol that the issue asks to modify. This resulting zero-recall failure illustrates the reachability ceiling: sophisticated graph routing cannot recover a target that is logically related but structurally isolated from the initial lexical entry points.
